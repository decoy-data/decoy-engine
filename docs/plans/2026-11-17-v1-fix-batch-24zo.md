### 3.1 24zo: tests on every PR head before merge

Facts at base:

- `.github/workflows/gate-selfhosted.yml` triggers on `push` (with `branches-ignore`) and `workflow_dispatch`. Job `fast` (hosted, push only) runs `gates.sh --steps env,ruff,format,mypy,sentry`: no tests. Job `gate` (self-hosted `decoy-gate`, 2 shards) runs only on dispatch or a main push. The workflow never runs on `pull_request`, by design: the repo is public and a PR trigger must never reach a self-hosted runner (`test_self_hosted_jobs_are_pr_free_and_actor_guarded` in `ET:tests/sentry/test_ci_config.py`).
- `ci.yml` jobs `regression-gate`, `ruff`, `mypy`, `layers-gate` carry `if: github.event_name != 'pull_request'` (`docs/ci-regression-gate.md`, "Who runs what"). A PR is meant to get its tests from the dispatched gate.
- Branch protection on main requires the profile gates and companion legs. None of them runs the default suite. No gate context is required.
- `scripts/dev/required_checks.py verify --tier merge` checks only the check runs of `pull_request` runs, derived from `ci/required-jobs.toml`.

Root cause: the merge gate exists but nothing makes it a merge precondition. A PR head with no dispatch, or a red one, shows only green checks.

V1 behavior:

1. New hosted job `gate-verdict` in `gate-selfhosted.yml`: `needs: gate`, `runs-on: ubuntu-latest`, `timeout-minutes: 5`, `if: always() && github.event_name == 'workflow_dispatch'` plus the same owner guards as `gate`. Job-level `permissions: {statuses: write}`; the workflow-level permissions stay as pinned. One step posts a commit status on `github.sha` with context `engine-gate/verdict`: `success` only when `needs.gate.result == 'success'` (a matrix result is success only when both shards are), else `failure`. The description names the mode (`baseline` or `full`); `target_url` is the run URL. Token: `${{ github.token }}`, never `secrets.`.
2. Why a commit status and not the job's check run: a job skipped by its `if` reports a check run that branch protection counts as passing (GitHub docs, "Troubleshooting required status checks"). On a branch push `gate-verdict` is skipped, so its check-run name would pass protection with no gate. A status context that only a dispatch run posts cannot be satisfied by a skip: a head with no dispatch has no `engine-gate/verdict` status and stays blocked.
3. `scripts/dev/required_checks.py verify --tier merge` also reads `GET repos/{repo}/commits/{sha}/status` and requires context `engine-gate/verdict` with state `success` on `--sha`. A missing, pending or failed status fails verify with the line `engine-gate/verdict: dispatch gate-selfhosted.yml on <sha>`. This works the day the slice merges, with no settings change.
4. The context name is in one place: `ci/required-jobs.toml` `[[merge_status]]` with `context`, `app_id` (15368) and `reason`. `required_checks.py` reads it; a sentry checks the workflow posts exactly that string.
5. `docs/ci-regression-gate.md` "Who runs what": one paragraph on the verdict status and on dispatching once per PR head.
6. Owner Q1 is part of E5, applied before E5 merges, so there is no window: (a) dispatch the gate on the E5 head (a dispatch runs the workflow from the dispatched ref, so the E5 branch's `gate-verdict` posts the status on that head); (b) add `engine-gate/verdict` to main's required status checks with its source pinned to the GitHub Actions app (`app_id` 15368); (c) bootstrap check, run by hand and pasted into the merge handoff: `gh api repos/decoy-data/decoy-engine/branches/main/protection/required_status_checks --jq '.checks[] | select(.context=="engine-gate/verdict") | .app_id'` prints `15368`; (d) merge E5 through the merge steps (main's `verify`, plus protection, which now needs the E5 head's status). From then on, an open PR whose branch predates E5 cannot get the status until it is rebased onto main and dispatched (fails closed).
   Bootstrap source: `verify` reads `ci/required-jobs.toml` from main, never from the PR branch (`read_tree`, `main_tree`, lines 150 and 162), so a branch cannot edit its own merge requirements. Before E5 merges, main has no `[[merge_status]]`, so main's `verify` has nothing to enforce; the trusted source for that one merge is the owner's settings change and the hand check in (c). After E5 merges, main's table holds the context and app id, and every later `verify` enforces step 7.
7. `verify --tier merge` also reads `GET repos/{repo}/branches/main/protection/required_status_checks` and requires a `checks` entry with the `[[merge_status]]` context and `app_id` 15368. A missing entry, any other or null `app_id` (any source), or a failed read (403, 404, network) fails verify with `branch protection does not require engine-gate/verdict from GitHub Actions` (fails closed). The merge steps run with the owner's token, which can read protection. The app id lives beside the context in `[[merge_status]]` (`app_id = 15368`), so there is one copy. When main's table has no `[[merge_status]]` entry, `verify` skips the status and protection checks, which is only the pre-E5 state of main.

Failure modes:

| Case | Behavior |
|---|---|
| PR head pushed after a green dispatch | new SHA has no status; verify and protection block until a new dispatch |
| protection loses the context or its app pin (settings change) | every merge verify fails on the protection check until restored |

| branch push (not a dispatch) | `gate-verdict` skips; no status; merge stays blocked |

| status API call fails | step exits non-zero; no status, so merge stays blocked (fails closed) |
| tree-proof skip on main | unchanged; `gate-verdict` is dispatch only |

### 3.3 24zp: bottom and top coding for datetime years

Facts at base (`E:src/decoy_engine/profiling/_snapshot_values.py`):

- `fold_year_bins` (line 216) clamps each year to `MAX_SAMPLED_YEAR`, then `fold_ranges_under_k` (line 179) merges adjacent ranges until each holds `MIN_RELEASE_COUNT` rows, then keeps the ranges only when the total is K or more (line 230).
- The first range's `start_year` is the true minimum year and the last range's `end_year` is the true maximum year. One row at 1850 among 1990s rows makes the first range `1850-199x`: the release names that row's year.
- `_year_edge` (line 140) reads the folded ranges for the flagged bound, so it carries the same leak.
- Numeric columns already top and bottom code at the K-th smallest and K-th largest cell (`_top_coded_stats`, line 288 and line 301; sdcMicro `topBotCoding`).

V1 behavior:

1. In `fold_year_bins`, after the sentinel clamp and before the fold: walk the per-year counts in year order and find `low`, the year that holds the K-th smallest row, and `high`, the year that holds the K-th largest row (row weighted, not distinct years).
2. When total >= 2K-1 (then `low <= high`): move the counts of every year below `low` onto `low` and every year above `high` onto `high`, then fold as today.
3. When total < 2K-1 (10 to 18 rows): release no range and no plain `min` or `max`. One predicate decides it: a new `_year_total_releasable(year_bins) -> bool` (total row weight at least 2K-1) in `_snapshot_values.py`, the only place the 2K-1 threshold appears. Two callers use it: (a) `fold_year_bins` keeps no range when it is false (this replaces today's below-K test, which it covers), which serves the flagged path, where `_year_edge` already returns `None` on empty ranges; (b) `_too_small_to_release` (line 361) withholds a datetime column when it is false, so a plain column of 10 to 18 rows is withheld and listed as redacted (G5) before `_floor_column` runs, exactly as numeric columns below 2K cells are. `_kept_year_edge` therefore never sees empty ranges: today a 10 to 18 row single-year column passes `_too_small_to_release` (its one bin holds K) and would index an empty list. The tails overlap, so the K-th row from each end is one of the K-1 rows at the other end, and any range would name a tail row's year (Dennis code review of #649). This holds whether `low > high` or `low == high`; the rule tests the total, not the order of `low` and `high`. Numeric columns use a floor of 2K finite cells (`_too_small_to_release`, line 363); datetime uses 2K-1 because at 2K-1 rows the K-th row from each end is the same middle row, which is not a tail row.
4. When total < K: no range (today's rule).
5. `_year_edge` (flagged path) and `_kept_year_edge` (`E:src/decoy_engine/profiling/_snapshot_values.py:333`, plain `min` and `max` under `Rule.KEPT_YEAR_START` and `Rule.KEPT_YEAR_END`, set at line 390) need no code change (step 3 guarantees non-empty ranges reach `_kept_year_edge`): both read the coded ranges after `fold_year_bins`. Today the plain `min` is `1850-01-01T00:00:00` in the outlier case; after E1 it is the K-th row's year. Tests pin both.
6. The docstring cites sdcMicro `topBotCoding` and Hundepool et al. (2012) on top and bottom coding, as `_top_coded_stats` does.
7. A changelog fragment states the release change: plain fit snapshots may show narrower outer year ranges.

Failure modes:

| Case | Behavior |
|---|---|
| one extreme low year | coded up to the K-th row's year; the outer edge no longer names it |
| K-1 extreme rows at each end | all coded; moving any of them further out leaves every range unchanged |
| all rows in one year, total >= 2K-1 | one range of that year (unchanged) |
| total between K and 2K-2 (tails overlap), `low > high` or `low == high`, including all rows in one year | plain path: column withheld and listed as redacted (G5), no `min`/`max`, no `IndexError`; flagged path: no range, `_year_edge` gives `None` |
| 9999 sentinel rows | clamped to `MAX_SAMPLED_YEAR` first, then top coded like any year |
| fractional counts (weighted bins) | cumulative weight decides the K-th position; same rule |
| empty `year_bins` | return early (unchanged) |

### 3.5 24zu: name-hint-gated detector hits on pattern-destroying masks

Facts at base:

- `E:src/decoy_engine/execution/_strategies/_redact.py`: `redact` replaces every non-null value with the constant `REDACTED` (`_DEFAULT_REDACT_WITH`). It keeps nothing of the source. Redact is correct.
- `E:src/decoy_engine/detection/_patterns.py:76`: `_MRN_RE = [A-Z0-9\-]{4,20}`, case-insensitive fullmatch. `REDACTED` matches.
- `E:src/decoy_engine/detection/detectors.py:513`: `detect_mrn` returns None unless `_hits_name_hint("mrn", col_name)`. The healthcare name-hint list includes `customer_id`. A name hint gives confidence `high`. So on a text_redact column, identity under 100% only shows that some other span (an email) was replaced; a cell "John Smith, j@x.com" can still hold a name. text_redact is not a whole-cell strategy.

Identity counts only rows where both cells are non-null (`_source_identity`, `:248`).

Custom detectors are not in the facts, so a custom detector id cannot collide with a gated id today.
- Run evidence (report guide run, 2026-11-17, engine 0.27.0): the demo pipeline redacts `customer_id`, `ssn`, `dob`, `zip`; `report integrity` shows `customers customer_id mrn fail redact` and exits 4.

Decision: the detector and redact are both right. The classifier is wrong. For a gated detector the "pattern" is the column name plus a loose shape that any constant or hash output can match, so a hit after a destroying mask proves nothing. The source comparison does prove whether the mask fired, and the classifier already computes it. Under the V1 threat model (accidental leaks) the fix must keep failing a mask that did not fire.

V1 behavior:

1. New private module `E:src/decoy_engine/detection/_hint_gated.py`: `NAME_HINT_GATED_DETECTORS: frozenset[str]`, the detector ids whose function returns None without a name hint. `detectors.py` is at its 920-line size ceiling (`ET:tests/sentry/test_module_size.py`), so the set goes in its own module. The detection facade `E:src/decoy_engine/detection/__init__.py` re-exports it and adds it to `__all__`; `residual_pii.py` imports it from `decoy_engine.detection`, never from the private module.
2. A sentry `ET:tests/sentry/defects/test_hint_gated_registry.py` parses `detectors.py` and collects every `detect_*` function whose first statement after the docstring is `if not _hits_name_hint("<id>", ...): return None`. That set must equal `NAME_HINT_GATED_DETECTORS`. It also asserts that, in each gated function, the id passed to `_hits_name_hint` equals the id passed to `_evaluate`, so the registry id is the id that appears in the facts. Seeded self-tests show it fails on a gated detector missing from the set, on a set entry whose detector no longer gates, and on mismatched ids.
3. In `residual_pii_findings`, a column takes the gated path when the configured strategy is in `_WHOLE_CELL_DESTROYS` = {hash, redact, bucketize} (a subset of `_DESTROYS_PATTERN`, defined beside it; text_redact is left out because it replaces spans, not cells), every detector in `fact.detectors` is in `NAME_HINT_GATED_DETECTORS`, and the source comparison ran (`rate is not None`). On that path the base severity is `info` with the fixed message "column matched '<id>' only through its column name; strategy '<s>' replaced the values". The message carries no rate, count or value; the existing `source_identity_rate` field is unchanged and out of scope.
4. The gated path does not call `_escalate`. A whole-cell strategy never legitimately leaves a non-null cell equal to its source, so one small function `_grade_gated(identical_rows, comparable_rows)` decides, with no source-distinct or minimum-row exception:
   - `identical_rows == comparable_rows` (full identity, any row count, constant source included): `fail`, message "column matched '<id>' only through its column name, and the output equals the source under strategy '<s>'; the mask did not fire".
   - `identical_rows >= _LEAK_FAIL_MIN_ROWS` and identity >= `_LEAK_FAIL_RATE`: `fail`, same message.

   - `identical_rows == 0`: `info` with the message in point 3.
   All three messages are fixed text with no rate, count or value. `_escalate` and its rate-bearing messages for other paths are unchanged (existing behavior, out of scope; recorded in section 12).
5. No comparison (no source column, row-count mismatch) or `identity_error`: today's behavior (fail, or error).
6. Changelog fragment: residual PII no longer fails redact, hash or bucketize columns on name-hint-only detector hits when the source comparison shows no row kept its source value.

## 9. Established solutions

Searches run during planning: web search "GitHub required status check skipped job reports success path filter workaround"; web search for sdcMicro `topBotCoding`; codebase search for existing coding (`_top_coded_stats`) and CI aggregation (`_ci_lanes.py` R2, `required_checks.py`).

- Top and bottom coding: sdcMicro `topBotCoding` (R package), Hundepool et al., Statistical Disclosure Control (Wiley, 2012). The engine already follows it for numeric columns; E1 applies the same rule to years. The web search gave no useful hit, so the citation rests on the existing in-code reference.
- Required checks and skipped jobs: GitHub docs "Troubleshooting required status checks" say a job skipped by a conditional reports success and a path-filtered workflow leaves a required check pending. The common fix is one always-running final job that needs the conditional jobs and fails only on a real failure, and is the only required check (GitHub community discussion 44490; Mergify blog "Path filters are not a CI gate"). E5 follows that pattern. It writes the few lines inline instead of adding a third-party action (`re-actors/alls-green`, `dorny/paths-filter`), to keep the supply chain small.
- Gate verdict as a commit status: the GitHub commit status API, matched by context name and SHA in branch protection. This is the documented way an external system reports a required check.

## 10. Design notes

- E5 posts the verdict as a commit status, not a check run, because a skipped job's check run passes protection (3.1, point 2).
- E5 adds no hosted test job on `pull_request`. The default suite takes about 65 minutes on a hosted runner (note in `ci.yml`), and CI-E2 chose the self-hosted gate as the one test lane. Owner Q4 covers this.
- E2 keeps the decision in the one builder and adds one registry with a guard. It does not special-case the `REDACTED` constant: a hashed or bucketized id column has the same false fail.
- New structure: one module (`_hint_gated.py`, a registry with a guard, re-exported by the detection facade), one test helper (`_reexport_init.py`), one stdlib CI script (`native_scope.py`: the path decision and the aggregator's decision), two registry tables. No new abstraction. Each fact lives in one place: the gated set in `_hint_gated.py`, the status context and aggregator in `ci/required-jobs.toml`.
