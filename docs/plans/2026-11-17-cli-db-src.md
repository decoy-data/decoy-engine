## 1. Guarantee and non-goals

### 1.1 What this change promises

1. A pipeline config may declare a source `sources.<table>: {type: postgres, connection_ref:
   <secret ref>, schema: <ident>, table: <ident>}`. The config holds no host, user, password
   or database name. The whole libpq connection string is behind `connection_ref`, an F13
   secret reference (`env:NAME` or `file:/PATH`) resolved through the engine's default secret
   provider registry.
2. `decoy run` stages every postgres-sourced table of the pipeline from **one** Postgres
   snapshot (one transaction, one REPEATABLE READ snapshot) to Parquet in a protected scratch
   directory, then runs the unchanged file pipeline over that Parquet.
3. Scratch cleanup, stated exactly: the scratch is removed on normal exit, on any raised error
   and on Ctrl-C (SIGINT). SIGKILL and power loss cannot be caught. Inside a project the scratch
   is under the library scratch root, which `decoy library fsck --repair` already sweeps of
   stale temp directories. Outside a project the scratch is under the system temp directory and
   a killed run leaves it there (V2 row: SIGTERM handler and a temp sweep).
4. CONFIG-EXPLICIT holds for Postgres. Every column of each relation must be declared, and
   every declared column must exist. The check runs on the Postgres catalog **before any data
   row is read**. The snapshot refuses if the relation's columns changed between that check and
   the snapshot.
5. Value-free. The connection string, the password, the host and the resolved secret never
   appear in an error, a log line, the run card, `--json` output, SARIF, the run folder,
   telemetry or a traceback chain (`__cause__` and `__context__` are `None` on every refusal).
   This holds also when a user pastes a raw connection string into `connection_ref`. Errors
   carry a registered reason code and a config location (`sources.<table>.<field>`) or a
   relation location (`schema.table`, `schema.table#<column position>`).
6. The reference text (for example `env:DECOY_PG_DSN`) is a locator like `credentials_ref`: it
   names where the secret is, not the secret. It is kept in the declared config inside run and
   scan records, and record export lists such a record as unstripped (section 5.5). It is not
   echoed in error text.
7. The engine never fetches the DuckDB `postgres` extension during a run. `decoy setup
   --postgres` installs it once. A run with the extension absent is refused with exit 1 and a
   hint that names that command.
8. Both repositories get a merge-required `pg-gate` CI job that runs every `pg_integration`
   test against a GitHub Actions Postgres service container and fails on any skip.

### 1.2 Non-goals (findings here become follow-ups, not blockers)

- More than one Postgres connection per pipeline (refused in V1, owner Q3).
- Consistency between a Postgres table and a file table (documented, not guaranteed).
- A `WHERE` filter, a column subset, a custom `ORDER BY`, a SQL query or a view expression as a
  source. The relation is read whole. Subsetting stays the subset stage's job inside
  `decoy run`.
- `decoy validate`, `decoy ci check` and `decoy validate preflight` opening a database
  connection (owner Q4). They stay local and network-free, as
  `C:src/decoy/cli/preflight.py:362` does today.
- Postgres for the standalone `decoy subset` command, `decoy demo`, `decoy scan`, and
  `--evidence-out` or `--resume` with a Postgres source (owner Q8, Q13).
- Postgres as a target (row 86), the F13 external adapters (row 83), the platform.
- Streaming straight from Postgres without staging (V2).
- Hostile in-process attackers or a hostile database server (V1 threat model: accidental leaks
  only).

## 4. Behaviour

### 4.1 Config and layer placement

```yaml
sources:
  customers:
    type: postgres
    connection_ref: env:DECOY_PG_DSN      # whole conninfo or URI is in the variable
    schema: public
    table: customers
  orders:
    type: postgres
    connection_ref: env:DECOY_PG_DSN
    schema: public
    table: orders
tables:
  - name: customers
    columns: [...]      # every column of public.customers; passthrough allowed
  - name: orders
    columns: [...]
```

`PostgresSource` (new member of `SourceDescriptor`): `type: Literal["postgres"]`,
`connection_ref: str` (required, marked `x-decoy-locator`, so `SOURCE_LOCATOR_FIELDS` gains it),
`schema: str`, `table: str` (both required). `extra="forbid"`, strict strings,
`hide_input_in_errors=True`. The model checks shape only (non-empty strings).

Layer placement (`.importlinter`, tiers top to bottom; names joined by `:` in one tier are
independent and cannot import each other):

- `config` and `connectors` are independent siblings in the same tier, so the config model
  cannot use the identifier rule.
- `plan` is one tier above `connectors`, so a plan check can call `validate_identifier`.
- `secret_providers` is an independent sibling of `plan` in the same tier, so a plan check
  cannot parse a secret reference.
- `execution` is above both, so the staging module can use `connectors`, `secret_providers`
  and `profile`.

### 4.2 Static checks (no secret read, no connection)

Plan check `plan/checks/_postgres_sources.py` (compile layer, so `decoy validate` and `ci
check` run it) raises the first of:

- `source_postgres.identifier_invalid` at `sources.<t>.schema` or `.table` when the name fails
  `validate_identifier` (the one rule).
- the existing `connector.duplicate_relation` at `sources.<t>.table` when two tables name the
  same `schema.table`.
- `source_postgres.multiple_connections` at `sources.<t>.connection_ref` when two postgres
  sources carry different `connection_ref` text.

Reference check `check_postgres_source_refs(config)` (public, in the staging module, because
only the execution tier can see `secret_providers`) raises
`source_postgres.connection_ref_invalid` at `sources.<t>.connection_ref` when the text does not
parse with `parse_ref` or names a scheme the default registry does not hold (so `vault://` and a
pasted `postgresql://user:pw@host/db` are both refused). The parse failure is saved and the
coded error is raised after the `except` block closes. The text never appears in the error.
`stage_postgres_sources` calls it first; the CLI config layer calls it for `decoy validate`
and `decoy ci check`.

### 4.3 Engine staging

New public context manager `stage_postgres_sources(config, settings) ->
Iterator[StagedSources]` in `execution/pipeline/_postgres_source.py`:

1. No postgres source: yields the config unchanged and opens nothing.
2. `check_postgres_source_refs(config)`.
3. Resolves `connection_ref` once with `prepare_secret(..., requirements=(POSTGRES_DSN_V1,),
   purpose=SecretPurpose(field_key="sources.<t>.connection_ref", noun="Postgres connection"))`.
   `SecretPurpose` is new and typed; the mask root passes `MASK_SECRET_PURPOSE`, which carries
   today's `global_settings.mask_secret_ref` and "mask secret" text, so mask-secret errors do
   not change. The new requirement `postgres-dsn-v1` strips one trailing `\n` (or `\r\n`) from
   the material (a `file:` secret written by `echo` ends in one), then accepts non-empty UTF-8
   without NUL up to 8 KiB, and takes the material raw when the reference names no encoding
   (`implicit_encoding="raw"`, owner Q6). Every secret refusal (F29 reasons, file access, size,
   encoding) is caught, its F29 code saved, and re-raised after the `except` block closes as
   `source_postgres.connection_ref_unresolved` at `sources.<t>.connection_ref`, with the F29
   code as a value-free `cause_code` field. So the CLI never routes it into mask-secret
   guidance. The prepared secret is closed as soon as the `SecretStr` is built.
4. Reads catalog columns for every relation through `relation_columns(config, relations)` in
   the new `connectors/postgres_catalog.py` (read-only session from `_postgres_session.py`, no
   data row). A column whose name fails `validate_identifier` is refused with the new
   `connector.column_name_unsupported` at `schema.table#<position>` (1-based); the name is
   never echoed.
5. Builds one `pa.Schema` of names per table and calls `prepare_declared_execution_sources(
   DeclarationRequest.for_supplied(config, schemas))`. An undeclared column, a declared-but-
   missing column or an undeclared table raises the existing `source_file.*` refusals before
   any row is read. Those codes keep their `source_file` names; the guide explains that they
   apply to every source type.
6. Opens `protected_scratch_dir(settings.scratch_parent, prefix="decoy-pg-")` and calls
   `snapshot_tables_to_parquet` once with one `RelationSelection` per table, `columns` equal to
   the checked catalog list and the new field `whole_relation=True`. Inside the snapshot
   transaction the shape guard (a `postgres_query` catalog read on the attached database, in
   `postgres_catalog.py`) refuses with the new `connector.relation_shape_changed` when the
   relation's column set differs from the selection.
7. Yields `StagedSources(run_config=..., declared_config=...)`. `run_config` has each postgres
   descriptor replaced by `{type: file, format: parquet, path: <staged>}`. `declared_config` is
   the input config, unchanged. On exit the scratch directory and the DuckDB spill are removed.

`PostgresSourceSettings` (frozen, strict types): `extension_directory`, `scratch_parent`
(optional), `memory_limit`, `threads`, `row_group_size=100_000`, `statement_timeout_s=3600`,
`deadline_s=21600` (owner Q7).

Interrupt handling (M1): today every `except Exception` in the primitive maps a DuckDB
interrupt to `export_failed`. After this change the primitive checks, in this order, after the
`except` block closes: the deadline event set gives `deadline_exceeded`; a DuckDB
`InterruptException` without the deadline event gives `KeyboardInterrupt` re-raised (the CLI
exits 130); anything else gives the coded failure. `KeyboardInterrupt` itself is never caught
by an `except Exception`. Cleanup in `finally` runs in every case.

Exit classification (H3): the usage connector codes are `ambiguous_name`, `column_not_found`,
`duplicate_relation`, `extension_unavailable`, `extension_untrusted_location`,
`relation_not_found`, `unsupported_column_type`, `value_not_representable`, and the new
`relation_shape_changed` and `column_name_unsupported`. Their catalog entries get
`outcome=Outcome.CONFIGURATION`, `retry=RetryClass.CONFIGURATION_REPAIR`. The other connector
codes stay `EXECUTION`. The engine exports `POSTGRES_SOURCE_USAGE_CODES`, computed from the
registry by outcome at import, never a literal list. The CLI maps a `PostgresSnapshotError`
whose code is in that set to exit 1 and every other one to exit 3. The release stamps the
registry and manifests; this row changes neither `REGISTRY_VERSION` nor a manifest file.

Unstaged descriptors: `build_profile_source` raises `source_postgres.unstaged` at
`sources.<t>.type` for a `type: postgres` descriptor. `source_columns`, `run_pipeline`,
profiling, capacity and `prepared_sources` all reach it, so no route treats the table as empty.

Session split (L1, shared with `plan/f01-pg-target`): the connection, extension-load and
identifier helpers move from `postgres_snapshot.py` into `connectors/_postgres_session.py`
with one read-only session function `open_read_session(config)`. The F01 plan adds
`open_write_session` to the same module. The extension-directory setting is chosen there by
DuckDB major version (M7).

`install_postgres_extension(directory)` in the new `connectors/postgres_extension.py` is the
only engine function that may fetch the extension. `postgres_extension_installed(directory)`
checks without network. Neither is called by staging.

Hashes and bindings: `pipeline_config_hash` already drops `sources`, so the record config hash
does not see the staged path. Any per-table binding (the F23 `binding_digest`) and every record
is built from `declared_config`, never from `run_config`. AT-C10 checks two runs on the same
database state record the same config hash and the same source descriptor.

### 5.2 Routes

- Resident `run_pipeline` (plain `decoy run`): reads the staged Parquet through `read_source` (`C:src/decoy/cli/_sources.py:389`).
- `--chunked` and the automatic streaming route: Parquet chunks from the staged file (`C:src/decoy/cli/_sources.py:414`).
- Out-of-core FK route and the isolated subprocess route: the same staged `run_config`; the scope is entered on the parent's `ExitStack`, so it outlives the subprocess.
- Subset and `--sample` stages inside `decoy run`: operate on the staged Parquet, unchanged.
- Engine entry with an unstaged postgres descriptor: refused at `src/decoy_engine/profile/_readers.py:507`.
- `decoy.mask()`: refused at `C:src/decoy/cli/run/_execute.py:238`.

### 5.3 FK shapes

- Scalar FK between two postgres tables: both read in one snapshot, never torn (primitive gate 1, `tests/connectors/test_postgres_snapshot.py:71`).
- Composite FK whose child is a postgres table: its child columns count as declared (`src/decoy_engine/profile/_declared_columns.py:46`), so the catalog check accepts them.
- Self-referencing FK in one postgres table: one relation, one snapshot.
- FK between a postgres table and a file or generated table: no consistency promise across sources (non-goal, documented); masking FK semantics unchanged.

### 5.4 Descriptor fields

- `type`: `"postgres"`, the discriminator (`src/decoy_engine/config/_sources.py:343`).
- `connection_ref`: F13 secret reference; locator field, kept in records, never echoed in errors, never resolved before staging.
- `schema`: Postgres schema identifier; `validate_identifier`, exact case.
- `table`: Postgres relation identifier (table, view, materialized view, partitioned or foreign table, as `_CATALOG_SQL` allows); exact case.
- No `path`, `format`, `columns`, `where` or `order_by` field (`extra="forbid"`).

### 5.5 Output surfaces

- stderr error line, the `--json` error object (`decoy-error-v1`) and SARIF from `ci check`: code plus location only; no DSN, no reference text.
- Run card and the `--json` success document: table names and row counts only; no scratch path.
- Run folder records (RESULT document, run record) and scan-set records: built from `declared_config` (`C:src/decoy/cli/run/_prepare.py:431`); `connection_ref` is a locator, so `records/_kinds.py` lists the record as unstripped on export (`src/decoy_engine/records/_kinds.py:89`), as for `credentials_ref`.
- Engine log lines: `postgres_snapshot published relations=%d` and `failed code=%s location=%s` (`src/decoy_engine/connectors/postgres_snapshot.py:522`), plus one staging line with counts only.
- OTel telemetry: codes and counts only (existing CLI redaction sentries).
- `decoy setup --postgres` output: the extension directory path (a Decoy-owned path).

## 10. Design notes

- Principles: one place per fact (identifier rule and session setup in `_postgres_session.py`,
  catalog SQL in `postgres_catalog.py`, declared-column rule behind
  `prepare_declared_execution_sources`, exit classification as catalog outcomes, exit map in
  `exit_code_for`, secret purpose in `SecretPurpose`). Dependency direction by layer (4.1).
  Pattern followed: the CLI `--duckdb-source` stage-then-gate flow and the engine
  `execution/pipeline/` pre-run stages.
- New structure: one stage function; a second database source later adds its own `stage_*`.
  Typed context: `PostgresSourceSettings`, `SecretPurpose`. No flag argument: `whole_relation`
  is a field on the selection model.
- Choke points.
  - Unstaged postgres descriptors. Engine: `build_profile_source`; guard AT-E1; mutation:
    delete the postgres branch. CLI: `_require_local_io_endpoints`; guard AT-C6; mutation: drop
    the postgres arm.
  - Pre-read declared check: `prepare_declared_execution_sources` inside the stage function,
    before the scratch exists; guard AT-E4; mutation: move the check after the snapshot (the
    spy sees a `COPY`).
  - Value-free errors: raise outside `except`; guards AT-E3, AT-E12; mutation: restore one
    `from None` raise inside an `except` block.
  - Exit classification: the registry outcome; guard AT-E13; mutation: set one usage code back
    to `EXECUTION`.
