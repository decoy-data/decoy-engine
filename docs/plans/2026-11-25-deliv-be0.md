## 1. Frame

Today a pipeline can say `delivery: {mode: best_effort}` (YAML) or `delivery(best_effort)` (`.decoy`). The engine accepts it (`config/_delivery.py:10`, `DeliveryMode = Literal["strict", "best_effort"]`), dumps it and moves the config hash. Nothing reads it in a run: `plan_delivery` (`delivery/_plan.py:106`) is not called outside its package, and the CLI's `delivery_facts` (`cli:src/decoy/cli/run/_result.py:97`) reports `in_place` for every run. So a user who asks for best-effort delivery gets a normal run that exits 0 and is never told that the setting did nothing. The owner moved best-effort to row 61b (1.3) on 2026-11-22 and kept this 1.0 slice that refuses it.

BE0 refuses `best_effort` with one coded, value-free config error at validate, on every surface that validates a pipeline, before any source read. A refusal in 1.0 lets row 61b turn it into a success in 1.3 without a breaking change. Exit 6 (`EXIT_PARTIAL`, `cli:src/decoy/cli/exit_codes.py:103`) stays reserved and unreached.

## 2. Guarantee and non-goals

Guarantee: every path that validates a pipeline config through `PipelineConfig` (the engine's `parse_pipeline_config` and `PipelineConfig.model_validate`; in the CLI `decoy validate`, `decoy run`, `decoy gate`, `decoy explain`, `decoy demo`, `decoy convert`, the `.decoy` compiler and `decoy.api`), and the engine's `compile_plan` on a raw mapping (which `decoy validate compile` calls without `PipelineConfig`, `cli:src/decoy/cli/compile_explain.py:245`), refuses `delivery.mode == "best_effort"` with the problem code `delivery_best_effort_unreleased` (`str(reasons.config.DELIVERY_BEST_EFFORT_UNRELEASED)`) at the location `delivery`, before any source path is read and before any pipeline target, run output folder or `--output` plan file is written. A failure report the user asked for (`decoy run --result PATH`, `cli:src/decoy/cli/run/_result.py:321`) is still written; it is not pipeline output. `decoy.api` with in-memory `data=` stages the frame to a temporary Parquet file before validation, as today (`cli:src/decoy/api.py:532`); the refusal then removes it with the existing cleanup, and no user source or target is touched. `strict`, an omitted block and `{mode: strict}` behave exactly as today.

Non-goals:
- No best-effort behaviour. That is row 61b (DELIV C3).
- No change to `DeliveryConfig`, `parse_delivery_config` or `plan_delivery`. They keep accepting `best_effort` so 61b only removes one validator (section 5.1).
- No change to the frozen `pipeline-config.schema.json` or `run-result.schema.json`. The enum keeps `best_effort` (section 9).
- No change to `RunResult.delivery.mode` or `derive_outcome` (`run_result/_outcome.py:47`). A record that says `best_effort` cannot be produced in 1.0 but stays readable.
- No new exit code. The refusal exits 1 like every config error.
- No `.decoy` grammar change. `delivery(best_effort)` still parses and lowers; the engine refusal reaches it through `lang.config` (section 5.3).

## 3. Established solutions

- Search run: how configuration-driven tools reject a documented but unreleased value. Kubernetes feature gates keep alpha fields in the API schema and reject them at admission when the gate is off, with a message naming the gate; Terraform providers keep an argument in the schema and return a validation diagnostic for a value the provider does not yet support. Both keep the value in the schema and refuse it at validation, so turning it on later is additive, and the user gets a specific message instead of a generic "unknown value".
- The engine already follows this model for the `masked.` prefix in `when:`: `reasons.config.WHEN_MASKED_REFERENCE_UNSUPPORTED` ("planned for 1.x; V1 reads original values only", `reasons/config/_part1.py:199`). BE0 copies it.
- Pydantic: a `field_validator` on the parent model reports at the field location (`("delivery",)`), and `PydanticCustomError(code, message)` carries the reason code as the error type. `PIPELINE_NAME_INVALID` uses this pattern at `config/_pipeline.py:193`.

No custom code beyond one validator and one reason.

## 5. Design

### 5.1 Choke point

One `field_validator("delivery")` on `PipelineConfig` in `config/_pipeline.py`, next to `_name_is_a_valid_slug` (`config/_pipeline.py:186`):

```python
@field_validator("delivery")
@classmethod
def _best_effort_is_not_released(cls, value: DeliveryConfig) -> DeliveryConfig:
    """Best-effort delivery is not built yet; row 61b removes this refusal when it ships."""
    if value.mode == "best_effort":
        raise PydanticCustomError(
            str(reasons.config.DELIVERY_BEST_EFFORT_UNRELEASED),
            _BEST_EFFORT_TEXT,  # the registry summary, so one text on every surface
        )
    return value
```

`_BEST_EFFORT_TEXT` is a module constant in `config/_pipeline.py` set from the reason's registry summary (the builder uses the registry's existing summary lookup; if none exists, a literal equal to the summary plus an AT-5 assertion that the two match).

Second refusal site, `compile_plan`. `compile_plan` (`plan/_compile.py:124`) takes a raw mapping and never builds a `PipelineConfig`; it only calls raw checks such as `refuse_unapplied_subset` (`config/_subset_run.py:27`, called at `plan/_compile.py:192`). `decoy validate compile` validates the schema only through `shared_destination_findings`, which drops every refusal except `target_shared_destination` (`cli:src/decoy/cli/gate/_layers.py:165`), and then calls `compile_plan` on the raw mapping and can write `--output` (`cli:src/decoy/cli/compile_explain.py:245`, `:260`). So BE0-E adds `refuse_unreleased_delivery(config: Mapping[str, Any]) -> None` in `config/_delivery.py` (22 lines today), next to the shared predicate, and exports it from the `decoy_engine.config` package. `compile_plan` imports it from `decoy_engine.config`, not from a private module (the existing `_subset_run` import at `plan/_compile.py:53` is not copied), and calls it right after `refuse_unapplied_subset`. It raises `PipelineValidationError(_BEST_EFFORT_TEXT, path="delivery", code=reasons.config.DELIVERY_BEST_EFFORT_UNRELEASED)` when `config.get("delivery")` is a mapping whose `mode` is `"best_effort"`. The validator and this function share one predicate, `_is_unreleased_delivery_mode(mode)`, so the fact stays in one place, and 61b deletes both sites with the reason. This mirrors the subset precedent (same exception type, same reason group).

Why on `PipelineConfig` and not on `DeliveryConfig.mode`:
- Every user-facing entry point validates through `PipelineConfig`. `parse_delivery_config` (`config/_parse.py:48`) is only called by `plan_delivery`, on a dump that has already passed `PipelineConfig`. So the pipeline validator closes every user path that validates; `compile_plan` is the one raw-mapping path and gets the second site above. This is the choke point; the guard is AT-1 plus AT-6 (end to end), and M-1 (delete the validator) turns both red.
- `DeliveryConfig` keeps its contract, so `plan_delivery`'s best-effort branch and its tests (`tests/unit/delivery/test_plan_delivery.py`) stay for 61b. 61b deletes this validator and retires its reason; nothing else moves.
- The location is `delivery`, which the `.decoy` span map already holds (section 5.3).

The message names config keywords (`best_effort`, `strict`). It holds no config value, path, table name or data. `PipelineConfig` already sets `hide_input_in_errors=True` (`config/_pipeline.py:108`).

Design notes: no new structure. One validator in an existing model, one row in an existing registry. The fact "best-effort is not released" lives in one place (the validator); the reason text and the CLI docs point at it.

### 5.2 The reason

`DELIVERY_BEST_EFFORT_UNRELEASED = _d("delivery_best_effort_unreleased", "Delivery mode best_effort is planned for 1.x; this release delivers strict only. Remove the delivery block or write mode: strict.", since=UNRELEASED)` in `reasons/config/_part2.py`, in the `PipelineValidationError` group (`reasons/config/_part2.py:243`), added to that file's `__all__`. The release stamp sets `since`. `validation_problems` reports the registry summary, not the `PydanticCustomError` text (`safe_output/_validation.py:244`), so the fix hint lives in the summary and the validator passes the same summary (`_BEST_EFFORT_TEXT`, read from the reason) as its message. No product version number goes in the text (precedent: `WHEN_MASKED_REFERENCE_UNSUPPORTED` says "planned for 1.x").

Spelling of the code: the problem code that tests assert, that `decoy validate --json` prints in `messages[].code` and that `lang.config` puts in brackets is the bare `delivery_best_effort_unreleased`. Docs and QA tables write `config.delivery_best_effort_unreleased`. The changelog fragment names it `` `config/delivery_best_effort_unreleased` `` with a slash in backticks, which `pending_fragment_violations` (`scripts/release/reason_manifest_policy.py:569`) and `test_every_live_pending_identity_is_named_by_a_fragment` require. No `plan.` or `runtime.` twin: the refusal happens only at config validation.

No `docs/reasons.md` edit at merge: its anchor rule is checked only at release (`scripts/release/reason_manifest_policy.py:427`, `:586`), and the release stamp writes it.

### 5.3 The `.decoy` path

No grammar or lowering change is needed for the refusal. `delivery(best_effort)` lowers to `{"delivery": {"mode": "best_effort"}}` and records `spans[("delivery",)]` (`cli:src/decoy/lang/_safety.py:134`). `compile_text` then runs `validate` (`cli:src/decoy/lang/_validate.py:44`), which turns the engine problem into `lang.config` with text ending `[delivery_best_effort_unreleased]`, located on the `delivery(...)` statement. This is the roadmap's "refused in the `.decoy` grammar's lowering": the `.decoy` author sees the refusal on the source line through the existing bridge, and the engine stays the one source of truth.

CLI edits that follow (BE0-C):
- The docstring example at `cli:src/decoy/lang/_safety.py:8` becomes `delivery(strict)`. The `written` text at `cli:src/decoy/lang/_safety.py:61` becomes "`delivery(strict)`": the `options { }` refusal quotes it as the way to write the block and must not offer a refused mode.
- `cli:docs/guides/decoy-language/agent-card.md:229` lists `delivery(strict)` and adds one sentence: `best_effort` is refused in 1.0 with the code `delivery_best_effort_unreleased`.
- `cli:docs/qa/cli-v1-checklist.md:309` row DLV-02 already states the V1 expectation (refused at validate, exit 1, both file kinds). BE0-C changes only its status text from "Not built" to built for the V1 half; QA owns the tick.
- `decoy explain exit-codes` (`cli:src/decoy/cli/explain.py:497`) already says exit 6 is reserved. No change.
