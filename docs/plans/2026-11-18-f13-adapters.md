### Guarantee

After E3, the Vault provider reads only values frozen at construction, its failures carry no
secret, token or vendor text in their text, chains or frame locals, and its DEBUG logging shows no
secret or token. Every adapter module is checked by one shared contract kit. After E4 and E5, a
well-formed `gcp-sm://` or `azure-kv://` reference reads the pinned version once, before any
output, vault or evidence file is written, and the run masks exactly as it would with the same
bytes given through `env:NAME?encoding=raw&key_version=v<version>`. Every failure stops the
command with a registered code and constant text that never repeats the reference, project,
vault, secret name, a credential or a vendor message.

### Non-goals

Unpinned versions; JSON-field forms for GCP and Azure; sovereign Azure clouds and other Google
universes; regional GCP secrets; refreshing an expired frozen token; Vault auth other than a
token; live GCP and Azure checks; platform registration (parked with platform V1). Section 10
lists them.

## 1. Shared adapter rules

These rules come from the #663 review (Dennis round 1, M1, M2 and M5; the Codex note on
`botocore.endpoint`). They apply to every adapter: Vault, AWS, GCP, Azure and any later one. Slice
E3 makes them checkable by construction: one contract test kit that every adapter module must
join, enforced by a sentry.

- **SR-1 Value-free errors.** Every failure maps to a registered reason by exception class (and a
  fixed code string or HTTP status, never message text). The safe error is raised after the
  `except` block closes, so `__cause__` and `__context__` are `None` (recurring defect 3). On
  every failure path the provider deletes locals that hold a response or payload before it
  raises, so a `traceback.TracebackException(capture_locals=True)` render holds no secret, token
  or vendor text. Factories catch `Exception`, keep nothing of it, and raise
  `SecretProviderConfigError` with fixed text after the block.
- **SR-2 SDK DEBUG logging shows no body and no credential header.** With the root logger and
  every SDK logger (`urllib3`, `requests`, `hvac`, `botocore`, `boto3`, `google`, `azure`, `msal`)
  at DEBUG, propagating, and a handler that renders the message and the whole `record.__dict__`
  (so `extra=` payloads show), a successful and a failed resolve log no secret value, no access
  token, no refresh token, no client secret, no signed assertion and no `Authorization` or
  `X-Vault-Token` value. Where an SDK logs a body, the adapter adds a filter to that exact logger
  at import. A `logging.Filter` on a logger sees only records created on that logger, not records
  from its children, so the filter names the exact logger. A request line with a secret name or
  path may appear in admin DEBUG logs; that is V2-LOG.
- **SR-3 Frozen at build.** Construction resolves the endpoint, the credentials and the TLS trust
  (CA bundle) once and stores them in a frozen `repr=False` context. A read uses only the
  context. Where freezing needs the HTTP library's own environment lookup off
  (`requests.Session.trust_env`, azure-core `use_env_settings`), the proxies are resolved at build
  and frozen too, so turning the lookup off breaks no proxied user. A change to any environment
  variable, profile or config file after construction changes nothing a read uses. Frozen tokens
  expire, so the docs say "build the provider per run", and a provider whose frozen token has a
  known expiry refuses a read after it with `secret_provider_unconfigured` and fixed text.
- **SR-4 Never rendered.** Provider and context are immutable, `repr` and `str` are redacted,
  pickling is refused (the AWS plan, P5).
- **SR-5 Pinned version.** `describe` makes no call and returns `key_version = "v" + version`; the
  one read checks that the response names the pinned version. Unpinned aliases (`latest`, stage
  labels, an empty version) are refused by the grammar.
- **SR-6 Lazy, hoisted import; declared file reads; no direct consumer import.** The SDK import
  sets a flag in its `ImportError` handler and raises after it (the AWS `_boto3` shape). The
  semgrep consumer rule lists each new module in the five spellings of the AWS plan's AT-8. Every
  file the SDK opens from the operator's environment is declared in
  `tests/sentry/file_access_modules.toml` in the library-resolved form #663 added (`resolved_by`,
  `constructor`).
- **SR-7 Required SDK cells never skip.** One CI lane installs every adapter SDK and fails if a
  test that needs an adapter SDK is skipped there.

Choke point: the kit (`tests/secret_providers/adapter_contract.py`). Guard: the kit sentry
(E3 step 2) walks the syntax tree of `src/decoy_engine/secret_providers/` and fails on an adapter
with no harness. Mutation that must turn it red: delete one harness.

### HashiCorp Vault (hvac)

- External Secrets Operator, Vault Agent and the Terraform Vault provider build one client from
  explicit settings per store and read KV v2 at a version. The engine adapter already does this.
- hvac 2.4.0 falls back to the environment whenever an argument is `None` (`hvac/v1/__init__.py`,
  `Client.__init__`): `url=None` reads `VAULT_ADDR`; `token=None` calls
  `utils.get_token_from_env()` (`hvac/utils.py:358`), which reads `VAULT_TOKEN` and then the file
  `~/.vault-token`; `cert=None` uses `VAULT_CLIENT_CERT`/`VAULT_CLIENT_KEY`, read at hvac import;
  `verify=None` reads `VAULT_CAPATH`/`VAULT_CACERT`. The engine's `_connect` passes
  `context.token or None` and `context.address or None`, so a provider built from a client with an
  empty token reads `VAULT_TOKEN` or `~/.vault-token` at each read. That breaks SR-3 and is a file
  read the file-access registry does not declare.
- hvac's adapter uses a `requests.Session` (`hvac/adapters.py:51`). `requests` reads
  `REQUESTS_CA_BUNDLE`/`CURL_CA_BUNDLE`, the `*_PROXY` variables and `~/.netrc` per request while
  `trust_env` is true (`Session.merge_environment_settings`). So the CA bundle is not frozen when
  `verify=True`, and a `~/.netrc` entry for the Vault host adds a Basic `Authorization` header.
  hvac accepts `session=` and `proxies=` (public), so the read can pass a session with
  `trust_env=False` and the frozen values.
- hvac follows redirects by default. `requests` strips only `Authorization` on a cross-host
  redirect, not `X-Vault-Token`. Only the configured Vault server can send that redirect, so this
  is V2-LOG with a docs note.
- hvac and requests log no body; urllib3 logs the request line at DEBUG.

### GCP Secret Manager

- REST method `projects.secrets.versions.access`: `GET
  https://secretmanager.googleapis.com/v1/projects/{p}/secrets/{s}/versions/{v}:access`. The
  response is `{"name": ".../versions/{n}", "payload": {"data": <base64>, "dataCrc32c": <int64 as
  string>}}`. `name` carries the project number even when the request used the project id.
  Google's access sample verifies `dataCrc32c` with `google-crc32c` before using the data.
- External Secrets Operator (GCP provider), the Secrets Store CSI driver GCP provider and
  Terraform's `google_secret_manager_secret_version` read one version through Application Default
  Credentials (ADC). ESO and the CSI provider use the gRPC client `google-cloud-secret-manager`.
- `google-cloud-secret-manager` 2.32.0 needs `google-api-core[grpc]`, `grpcio`, `proto-plus`,
  `protobuf>=6.33.5` and `grpc-google-iam-v1`; `grpcio` and `grpc-google-iam-v1` are not in the
  engine lock. ADC (`google.auth.default`), `google-crc32c` 1.8.0 and `requests` 2.34.2 are already
  locked through the `cloud` extra (`google-cloud-storage` 3.12.0 depends on all three).
- google-auth 2.55.1 logs at DEBUG through `_helpers.request_log` and `response_log` with
  `extra={"httpRequest": ...}` and `{"httpResponse": ...}` once the `google` logger is configured.
  It hashes only `_SENSITIVE_FIELDS` (`google/auth/_helpers.py:46`: `accessToken`, `access_token`,
  `id_token`, `client_id`, `refresh_token`, `client_secret`). A service-account token request body
  (`assertion=<signed JWT>`) and an external-account STS body (`subject_token`) are logged in
  clear. `AuthorizedSession.request` logs the request line and the caller's headers, not the
  response body.
- Recommended V1 shape (owner question 3): get the token through ADC at build, then read with a
  plain `requests.Session` and a bearer header. No new library. The SR-2 filter on the exact
  logger `google.auth.transport.requests` drops records that carry `httpRequest` or
  `httpResponse`.

### Azure Key Vault

- `azure.keyvault.secrets.SecretClient(vault_url, credential).get_secret(name, version)` returns a
  `KeyVaultSecret` (`value`, `properties.version`, `enabled`, `not_before`, `expires_on`);
  `version=None` means latest. External Secrets Operator (Azure provider), the CSI driver Azure
  provider and Terraform's `azurerm_key_vault_secret` data source (`version`) use this client with
  service principal, managed identity or workload identity credentials.
- `DefaultAzureCredential` (azure-identity 1.27.0) tries Environment, WorkloadIdentity,
  ManagedIdentity, SharedTokenCache, VisualStudioCode, AzureCli, AzureDeveloperCli,
  AzurePowerShell and Broker; InteractiveBrowser is excluded by default. Each has an `exclude_*`
  keyword (`_credentials/default.py:189-233`). The operator variable `AZURE_TOKEN_CREDENTIALS`
  narrows the chain (`default.py:179`).
- azure-core `RequestsTransport` sets `session.trust_env = use_env_settings` (default true,
  `_requests_basic.py:276`, `:294`). `HttpLoggingPolicy` logs URL and headers at INFO and replaces
  every header outside its allowlist with `REDACTED` (`_universal.py:443-465`).
  `NetworkTraceLoggingPolicy` logs headers and bodies at DEBUG only with `logging_enable=True`
  (`_universal.py:285-298`); the default is false.
- The Key Vault `ChallengeAuthPolicy` sends one unauthenticated request, reads the 401 challenge,
  checks that the challenge resource matches the vault host (`verify_challenge_resource`, default
  true, `challenge_auth_policy.py:189`), then asks the credential for a token with
  `enable_cae=True`, through `get_token_info` when the credential has it, else `get_token`
  (`:383-393`).
- New libraries: `azure-keyvault-secrets` 4.12.0 (MIT), `azure-identity` 1.27.0 (MIT), and through
  them `azure-core`, `msal`, `msal-extensions`, `PyJWT` and `isodate`. None is in the lock (owner
  question 2). There is no established REST-only path for Azure that avoids azure-identity: the
  token chain (managed identity, workload identity federation, Azure CLI) is the part not to
  hand-write.

### E4 (engine): GCP Secret Manager adapter (`gcp-sm://`)

Starts only after owner question 1 is answered "yes" for GCP.

Scope: one grammar rule, one provider module on google-auth plus requests, docs and sentries. No
new library (owner question 3). Production consumer: CLI slice C3; library callers through
`register_secret_provider`.

Behavior:

1. **Grammar.** `gcp-sm://<project>/<secret-id>?version=<N>&encoding=<e>`.
   - `project` matches `^(?:[a-z][a-z0-9-]{4,28}[a-z0-9]|[1-9][0-9]{0,18})\Z` (a project id or a
     project number). No dot or colon is allowed, so a domain-scoped id is refused and the ref
     cannot steer the host.
   - `secret-id` is one segment matching `^[A-Za-z0-9_-]{1,255}\Z`.
   - `version` uses the Vault rule `^[1-9][0-9]{0,9}\Z`; `latest` and every alias are refused.
   - `encoding` is required; `field` is refused (owner question 7). The material is the whole
     payload, the shape the GCP console and `gcloud secrets versions add` write.
   - `RemoteRefRule` gains one fact, `payload: Literal["json_field", "whole"]`; `vault` and
     `aws-sm` are `json_field`, which keeps `field` required for them. `_parse_pinned_remote`
     reads it. The raw control-character check, the strict single decode, the `\Z` anchors and the
     duplicate, unknown, userinfo, port and fragment refusals are shared and unchanged.
2. **Build.** `gcp_provider_from_env(*, endpoint_url=None)`:
   - `google.auth.default(scopes=["https://www.googleapis.com/auth/cloud-platform"])`, then one
     `credentials.refresh(google.auth.transport.requests.Request())`.
   - Refuses with `SecretProviderConfigError` (fixed text) when the credentials' universe domain is
     not `googleapis.com`, when no token results, and on any exception (`DefaultCredentialsError`,
     `RefreshError`, `TransportError`, an unreadable file), per SR-1.
   - Freezes into `GcpContext(ResolveContext)` (`frozen=True, repr=False`): the access token, its
     expiry, `quota_project_id` (sent as `x-goog-user-project`), the endpoint
     (`https://secretmanager.googleapis.com` unless the explicit argument is given, for Private
     Service Connect and local test servers), `verify` (`REQUESTS_CA_BUNDLE`, then
     `CURL_CA_BUNDLE`, else `True`) and the proxies for the endpoint.
   - ADC never prompts, so no unattended-prompt guard is needed (unlike AWS MFA).
3. **Read.** `resolve` refuses an expired frozen token first (SR-3, `SecretProviderConfigError`),
   then builds a `requests.Session` with `trust_env=False`, the frozen `verify` and proxies, sends
   one `GET {endpoint}/v1/projects/{p}/secrets/{s}/versions/{N}:access` with
   `allow_redirects=False`, a fixed 30-second timeout and the bearer and quota headers, and closes
   the session in `finally`. The body is parsed only on status 200, with
   `_canonical.strict_json_loads`. `name` must end with `/secrets/{s}/versions/{N}` (the project
   part is not compared, because GCP returns the number). `payload.data` is decoded with
   `base64.b64decode(..., validate=True)`; when `dataCrc32c` is present it must equal
   `google_crc32c.value(data)`; the data must be non-empty. The bytes go into a `SecretBuffer`
   unchanged; a trailing newline is kept, as the `file:` provider keeps it. Locals holding the
   body, the parsed payload and the data are deleted before any raise.

   | Source | Code |

### E5 (engine): Azure Key Vault adapter (`azure-kv://`)

Starts only after owner questions 1 and 2 are answered "yes" for Azure.

Scope: a new exact-pinned extra, one grammar rule, one provider module, docs and sentries.
Production consumer: CLI slice C3; library callers through `register_secret_provider`.

Behavior:

1. **Grammar.** `azure-kv://<vault-name>/<secret-name>?version=<id>&encoding=<e>`.
   - `vault-name` matches `^[A-Za-z](?!.*--)[A-Za-z0-9-]{1,22}[A-Za-z0-9]\Z` (Azure's rule: 3 to 24
     characters, starts with a letter, ends with a letter or digit, no `--`). There is no dot, so
     the ref cannot choose the host; the provider builds `https://<vault-name>.vault.azure.net`.
   - `secret-name` is one segment matching `^[A-Za-z0-9-]{1,127}\Z`.
   - `version` matches `^[0-9a-f]{32}\Z`; an empty or missing version (latest) is refused.
   - `encoding` is required; `field` is refused (`payload = "whole"`, owner question 7).
2. **Build.** `azure_provider_from_env()`:
   - `DefaultAzureCredential` with `exclude_shared_token_cache_credential`,
     `exclude_visual_studio_code_credential`, `exclude_powershell_credential`,
     `exclude_developer_cli_credential`, `exclude_broker_credential` and
     `exclude_interactive_browser_credential` all true (owner question 4). Environment,
     WorkloadIdentity, ManagedIdentity and AzureCli stay. `AZURE_TOKEN_CREDENTIALS` is honored as
     azure-identity reads it.
   - Gets one token for `https://vault.azure.net/.default` with `enable_cae=True` (the option the
     Key Vault policy passes), then closes the credential.
   - Freezes into `AzureContext` (`frozen=True, repr=False`): the token and its expiry, `verify`
     (`REQUESTS_CA_BUNDLE`, then `CURL_CA_BUNDLE`, else `True`) and the proxies for
     `https://vault.azure.net`.
   - Any exception, including `CredentialUnavailableError` and `ClientAuthenticationError`, is
     `SecretProviderConfigError` with fixed text (SR-1). No credential left in the chain prompts.
3. **Read.** `resolve` refuses an expired frozen token (SR-3), then builds a `SecretClient` for the
   vault URL with a private `_FrozenCredential` (it implements `get_token` and `get_token_info`,
   returns the frozen token only for the scope `https://vault.azure.net/.default` with no
   `tenant_id` and no `claims`, and otherwise raises `ClientAuthenticationError`, which maps to
   access denied), `verify_challenge_resource=True`, `connection_verify=<frozen>`,
   `proxies=<frozen>`, `use_env_settings=False` and `logging_enable=False`. It calls
   `get_secret(name, version)` once and closes the client in `finally`. Checks:
   `properties.version` equals the pin (`secret_version_unavailable`); `enabled` is not false
   (`secret_version_unavailable`); `not_before` is not in the future
   (`secret_version_unavailable`); `expires_on` at or before now is `secret_expired` (as Vault maps
   `deletion_time`); `value` is a non-empty `str` (`secret_material_invalid`). The material is
   `value` encoded UTF-8. The secret object is deleted before any raise. A `clock` argument, as on
   the Vault provider, makes the time checks testable.
4. **Error map** (class and status code only):

   | Source | Code |
   |---|---|
   | `ResourceNotFoundError`, `HttpResponseError` 400 or 404 | `secret_version_unavailable` |
   | `ClientAuthenticationError`, `HttpResponseError` 401 or 403 | `secret_access_denied` |
   | `ServiceRequestError`, `ServiceResponseError`, 429, 5xx, any other exception | `secret_provider_unavailable` |
   | `azure.keyvault.secrets` or `azure.identity` not importable | `secret_provider_unavailable` (hoisted import) |

7. **Extra.** Engine `azure-keyvault = ["azure-keyvault-secrets==4.12.0",

   `pyjwt` and `isodate`. The SDK lane adds `azure-keyvault` to its extras.
8. **Docs.** The grammar row; an "Azure Key Vault" section (install, the credential chain and what

## 5. Design notes

- One new structure: the adapter contract kit and its sentry. The change pain it addresses: the
  #663 review found three rule classes (body logging, settings read after build, factory errors
  with vendor text) that the older Vault adapter also breaks. Without a shared check each new
  adapter meets them only through review rounds. The kit is the choke point; the sentry makes
  joining it mandatory.
- One new fact on an existing structure: `RemoteRefRule.payload`. The grammar stays one parser
  with one rule table; a scheme is one row.
- New provider modules mirror `vault.py` and `aws.py` point for point (immutable provider, frozen
  `repr=False` context, one round trip, class-based error map, hoisted import, factory catch-all).
  No shared base class: the three SDKs differ in every call, and the shared parts are short and
  already enforced by the kit.
- House style: typed context objects; one place per fact (endpoint and scope constants in each
  provider module, grammar facts in `_REMOTE_RULES`, CLI facts in `REMOTE_SCHEMES`); no flag
  arguments.

## 6. Recurring-defect check

1. Anchored validation: every new regex ends in `\Z`; each grammar corpus feeds every component
   plus `"\n"`; the shared raw control-character check covers both new schemes.
2. Strict wire types: GCP JSON is parsed with `strict_json_loads` and each field type is checked
   (`str` data, `str` name, a digit string for the CRC); Azure reads typed SDK properties.
3. No exception context: SR-1, kit-enforced for every adapter; E3 removes Vault's three baseline
   entries; E4 and E5 add none.
4. Versioned read models: N/A, no persisted format is added; the GCP response is read field by
   field and refused when malformed.
5. Normalized guard scanners: the semgrep consumer rule covers the five import spellings per new
   module (seeded); deliberate evasion is V2-LOG.
6. No private imports: the CLI imports only `decoy_engine.secret_providers` and the public `gcp`
   and `azure` modules; adapters use only public SDK names (`requests.utils`, `google.auth`,
   `azure.core.exceptions`).
7. No hidden CI failures: the E3 lane fails on a skipped SDK cell; live runs are recorded as NOT
   RUN, never as a pass.
8. One input, one trust class: refs are user input and go through `parse_ref` only; the explicit
   `endpoint_url` factory argument is program input and is never read from a ref.
9. Mutations on the final head: each slice reruns its named list on its final head and records
   the head.
10. Allowlisted helpers: each library-resolved file-access entry names one exact function; a
    seeded rename is red.
11. No raised caps: the `exception-context` baseline shrinks; the census grows only by deriver
    entries with checked verdicts named in the PR; no allowlist widens.

## 11. Owner questions

1. **Reopen the 2026-11-17 decision that put the GCP and Azure native adapters in V2-LOG?**
   Recommended: yes for both. GCP needs no new library (E4 uses google-auth, google-crc32c and
   requests, which the `cloud` extra already installs). Azure needs new libraries, kept in their
   own exact-pinned extra outside `all`, the bundle and the certified DP profile, the treatment
   the owner approved for `hvac`. If the answer is no, E4, E5 and C3 stay in V2-LOG as written
   here, and E3 and L1 still go ahead.
2. **Approve the Azure libraries** (`azure-keyvault-secrets==4.12.0` and `azure-identity==1.27.0`,
   MIT; they add `azure-core`, `msal`, `msal-extensions`, `PyJWT` and `isodate`)? Recommended:
   yes, as the `azure-keyvault` extra only.
3. **GCP transport: ADC plus one REST call, or the `google-cloud-secret-manager` client?**
   Recommended: ADC plus REST. It adds no library (the client adds `grpcio` and
   `grpc-google-iam-v1`), keeps the read on a session the adapter freezes, and avoids gRPC C-core
   tracing to stderr. Cost: the adapter builds one documented URL itself.
4. **Credential sources and the files they read** (the rule the owner approved for AWS on
   2026-11-17). GCP: ADC (`GOOGLE_APPLICATION_CREDENTIALS`, the gcloud ADC file, an
   external-account `credential_source` file, the metadata server). Azure: Environment
   (`AZURE_CLIENT_CERTIFICATE_PATH`), WorkloadIdentity (`AZURE_FEDERATED_TOKEN_FILE`),
   ManagedIdentity and Azure CLI (runs `az`); shared token cache, VS Code, PowerShell, azd, broker
   and browser are excluded. Recommended: approve as listed.
5. **Vault `~/.vault-token`.** Today hvac reads it silently, at build and at every read, when
   `VAULT_TOKEN` is unset. Recommended: read it once at build (it is what `vault login` writes),
   declared in the file-access registry. Alternative: never read it; an unset `VAULT_TOKEN` means
   no token (the Vault Agent proxy case).
6. **Vault live run.** OK to start `vault server -dev` bound to 127.0.0.1 on the Mac for one
   recorded run (L1)? Recommended: yes, before the CLI release that ships `vault://`. GCP and Azure
   live checks stay NOT RUN unless the owner provides test accounts.
7. **GCP and Azure read the whole secret value, with no `field=`.** Recommended: yes. It is each
   store's native shape and what the CSI driver writes to its file, so a user moving from the
   documented `file:` path keeps the same output when the label matches. A JSON-field form is
   V2-LOG.
