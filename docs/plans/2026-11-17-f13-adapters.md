## 1. FRAME

### Facts on main

- The engine admits the secret once, before any source read, through `admit_mask_key(config, *,
  key_provider=None, registry=None, cache_policy=None)` (`secret_providers/_preflight.py:389`).
  The registry maps a scheme to a provider (`secret_providers/_registry.py:11`); the process
  default holds only `env` and `file` (`default_registry`, `_registry.py:43`). An unregistered
  scheme raises `SecretProviderUnknown`.
- The ref parser has two grammars: the local `scheme:locator[?encoding=..&key_version=..]`
  (`_parse_local`, `secret_providers/_types.py:141`) and the Vault grammar
  `vault://<mount>/<path>?version=N&field=F&encoding=E` (`_parse_vault`, `_types.py:165`), chosen
  by scheme at `_types.py:126`. Every malformed ref is `bad_secret_ref` with no chained exception.
- `VaultKV2Provider` (`secret_providers/vault.py:173`) takes an authenticated `hvac` client, copies
  its settings into a frozen `VaultContext` (`:124`), reads once per resolve (`:206`), refuses a
  leased or wrapped response, and maps SDK errors by type (`_map_sdk_error`, `:273`).
  `client_from_env` (`:70`) builds the client from `VAULT_*` variables and raises
  `VaultClientConfigError` (`:58`, a plain `DecoyError` with no reason code) for a missing
  `VAULT_ADDR`, a set `VAULT_SKIP_VERIFY` or half a client certificate. `hvac==2.4.0` is the
  optional `hashicorp-vault` extra (`pyproject.toml:257`), owner-approved.
- Provider failure codes are registered in `reasons/runtime/_secret_provider.py` (86 lines):
  `secret_provider_unknown`, `secret_provider_unavailable`, `secret_access_denied`,
  `secret_version_unavailable`, `secret_expired`, `secret_lease_unsupported`,
  `secret_material_invalid`.
- Local providers are never cached (`_preflight.py:219`, `:248`); a remote provider is cached only
  under a positive TTL, which the CLI never sets.
- The CLI admits through one helper, `admitted_key_provider` (`src/decoy/_mask_secret.py:192`),
  which calls `admit_mask_key(checked)` with no registry. `_REF_SCHEMES` (`_mask_secret.py:35`)
  lets `env`, `file` and `vault` through its shape rule; the engine then refuses `vault://` with
  `secret_provider_unknown`. Constant text per code lives in `SECRET_REMEDIES`
  (`src/decoy/_mask_secret_guidance.py:111` for that code).
  `tests/sentry/test_mask_secret_ref_shape.py::test_vault_ref_is_refused_without_echo` pins that
  refusal on all five surfaces (CLI record `docs/records/2026-11-11-f13-5v1-closeout.md`).
- CLI extras pass through to engine extras (`cloud`, `ner`, `vault`); `all` bundles them. `otel`
  is kept out of `all` because every installed distribution enters the DP certification
  fingerprint (CLI `pyproject.toml`, comment above `otel`).
- `.semgrep/f13-secret-providers.yml` scans `src/decoy_engine/secret_providers/` for logging,
  printing, chained causes and rendered exception text, and forbids consumers from importing a
  concrete provider (`from decoy_engine.secret_providers.vault import $X`, rule near `:67-74`).
- The secret-material census (`tests/sentry/secret_material_census.json`, derived by
  `scripts/secret_material_census.py`) lists every binding that can hold secret material, with a
  checked verdict. New provider code adds entries.

### Guarantee

On every CLI keyed surface, a well-formed `vault://` or `aws-sm://` reference reads the pinned
version of the named secret field once, before any output, vault or evidence file is written, and
the run masks exactly as it would with the same key bytes given through
`env:NAME?key_version=v<uuid>` (AWS) or `env:NAME?key_version=v<N>` (Vault). The key version
label is part of the HKDF `info` (`keyprovider.py:168`), so a plain `env:NAME` (label `v1`) gives
different output. Every failure (extra not installed, client not
configured, access denied, version missing, wrong shape) stops the command before any output,
vault or evidence file is written, with a registered code and constant text that never repeats the
reference, secret name, field, region, a credential or a vendor message.

### Non-goals (V2 backlog)

- Google Secret Manager and Azure Key Vault native adapters (owner question 1).
- An unpinned version (`latest`, `AWSCURRENT` or any staging label). Rotation stays a deliberate
  config change, as for Vault, because a new key changes every masked value.
- AWS secrets stored as plain text or `SecretBinary`; ARNs and cross-account references; AWS
  version ids that are not UUIDs. V1 reads one field of a JSON `SecretString` (the console's
  key/value form), named by version id.
- Vault auth methods other than a token from `VAULT_TOKEN` (AppRole, Kubernetes, AWS IAM).
- A CI job with a live Vault service; any cross-run secret cache in the CLI.
- Platform registration of providers (platform V1, parked).

### Design notes

- Existing choke points stay single: `admit_mask_key` and the registry (admission), `parse_ref`
  (grammar), the reason catalog (codes), `SECRET_REMEDIES` (CLI text), `admitted_key_provider`
  (the one CLI admission site). This plan adds sites to them, not new paths.
- One new CLI fact table: `REMOTE_SCHEMES` in a new `src/decoy/_secret_providers.py` maps each
  remote scheme to the CLI extra that installs it, the module that extra provides and the engine
  factory that builds its provider. `_REF_SCHEMES` derives from it (`{"env", "file",
  *REMOTE_SCHEMES}`), the `secret_provider_unknown` text is built from it, and
  `admitted_key_provider` builds the registry from it. A later GCP or
  Azure scheme is one row. Guard: AT-9. Mutation: hard-code `vault` in `_REF_SCHEMES` again.
- Lazy and on demand: the CLI builds a remote provider only when the ref's scheme names it, so an
  `env:` or `file:` run never imports `hvac` or `boto3` and never reads `VAULT_*` or `AWS_*`.
  Guard: AT-10.
- Shared pinned-remote grammar: `_parse_vault` becomes `_parse_pinned_remote(text, rule)`, where a
  frozen `RemoteRefRule(scheme, authority_re, version_re, locator_check)` per scheme is the only
  per-scheme fact, held in `_REMOTE_RULES`. Vault's rule keeps today's behavior exactly (AT-1 runs
  the existing Vault ref corpus unchanged). Pattern: RFC 3986 `urlsplit` with strict single
  percent-decoding, as today.
- Provider shape: `AwsSecretsManagerProvider` mirrors `VaultKV2Provider` point for point
  (immutable, frozen `repr=False` context, one round trip, type-based error map, no pickling,
  never renders settings). Same contract (`secret-provider/v1`), no second admission path.
- Config errors get a code: a new `SecretProviderConfigError(SecretProviderError)` in
  `secret_providers/_errors.py` carries `code = secret_provider_unconfigured`, is in `_CLOSED`
  and is exported from `decoy_engine.secret_providers`. `VaultClientConfigError` becomes its
  subclass (name and fixed messages kept), and the AWS factory raises the base class. The CLI maps
  it through `SECRET_REMEDIES` like every other code.

Recurring-defect catalog check:
- 1 anchored validation: every new regex uses `\Z`; the raw ref is refused on any character
  below 0x20 or 0x7f before `urlsplit` (which drops `\t`, `\n`, `\r`); AT-1 feeds each AWS and
  Vault component plus `"\n"`, `"\t"`, `"\r"` and `"\x7f"`.
- 3 no exception context: AWS errors, in `resolve` and in the factory, are mapped after the
  `except` block closes; AT-5 and AT-14 assert `__cause__` and `__context__` are `None` on every
  mapped error. The two existing raise-from-None sites in `_parse_vault` are hoisted the same way.
- 5 normalized guard scanners: the semgrep consumer rule gains the `aws` module in both
  `from ... import` and `import ...` spellings (AT-8 seeded cases). Deliberate evasion is V2-LOG.
- 6 no private imports: the CLI imports only `decoy_engine.secret_providers` and its public `vault`
  and `aws` modules; its registry holds only the remote provider, so it needs no private local
  provider class.
- 7 no hidden CI failures: the live Vault run is recorded as run or NOT RUN, never as a pass.
- 11 no raised caps: the census grows by entries with verdicts; no allowlist widens.

## 3. Behavior

### E1 (engine): grammar, AWS provider, coded config errors

1. **Grammar.** `aws-sm://<region>/<secret-name>?version=<version-id>&field=<key>&encoding=<e>`.
   - `region` matches `^[a-z]{2}(-[a-z]+)+-[0-9]{1,2}\Z` (`us-east-1`, `us-gov-west-1`).
   - `secret-name` is the decoded path without its leading `/` and may contain `/`. Each segment is
     non-empty, not `.` or `..`, with no `\` or control character; the whole name matches AWS's
     charset `^[A-Za-z0-9/_+=.@-]{1,512}\Z`.
   - `version` is a lowercase UUID
     (`^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}\Z`). `AWSCURRENT`,
     `AWSPREVIOUS` and every other stage label are refused.
   - `field` and `encoding` are required, as for Vault. Duplicate keys, unknown keys, userinfo, a
     port, a fragment and malformed escapes are refused.
   - Raw text first (H2, both schemes): any character below 0x20, or 0x7f, anywhere in the raw
     ref is refused before `urlsplit`, because `urlsplit` silently drops `\t`, `\n` and `\r`
     (CPython bpo-43882). `_control_chars` (`_types.py:131`) also refuses 0x7f for the decoded
     components. This tightens Vault: a ref with a raw tab or newline that parses today is refused.
   - A dotted region (`us-east-1.evil.example`) fails the region rule, so no ref can steer the
     SDK's endpoint host (L2).
   - A secret name that is a full ARN fails the charset (no `:`). A name ending in `-` plus six
     characters can be matched by AWS as a partial ARN of another secret; V1 documents this, and
     the pinned version id still fixes the bytes read (L2).
   - Every refusal is `bad_secret_ref`, raised bare, after any `except` block closes: the two
     raise-from-None sites `_parse_vault` has today (`exception-context` baseline entries
     `_types.py::_parse_vault::0` and `::1`) are hoisted, so the baseline shrinks by two. The
     dispatch at `_types.py:126` looks the scheme up in `_REMOTE_RULES` (`vault`, `aws-sm`); any
     other scheme keeps the local grammar, so the registry still owns "unknown provider".
2. **Provider.** New `secret_providers/aws.py` with `AwsSecretsManagerProvider` (`scheme =
   "aws-sm"`, `api_version` the contract's).
   - Construction takes a `boto3.session.Session` built over an explicit
     `botocore.session.Session`. It copies the frozen credentials (access key id, secret key,
     session token, from `get_credentials().get_frozen_credentials()`) and the endpoint, resolved
     once now (M6: the explicit `endpoint_url` argument, else the botocore session's
     `get_config_variable("endpoint_url")`, which covers `AWS_ENDPOINT_URL` and the profile
     setting), into a frozen `AwsContext(ResolveContext)` with `repr=False`. It keeps no reference
     to either session and no profile name.
   - `describe(ref)` makes no call: `key_version = "v" + version-id` (37 characters), inside both
     `_LOGICAL_VERSION_RE` (`_types.py:44`) and `KEY_VERSION_PATTERN` (`keyprovider.py:276`,
     which the resume records check), `renewable=False`. This label is the HKDF `info`
     (`keyprovider.py:168`), so it is part of the key (H1).
   - `resolve(ref, context)` builds one `secretsmanager` client from a new `boto3` session made
     only from the frozen credentials and the ref's region (no profile), with the frozen endpoint
     and `botocore.config.Config(ignore_configured_endpoint_urls=True)`, so a later change to
     `AWS_ENDPOINT_URL` or the config files changes nothing. It calls
     `get_secret_value(SecretId=name, VersionId=version)` once and closes the client in `finally`.
     The response's `VersionId` must equal the pinned id. `SecretString` must parse with
     `json.loads(..., object_pairs_hook=...)`, the hook refusing a duplicate key, as an object
     whose `field` value is a non-empty `str`; that value, encoded UTF-8, is the material in a
     `SecretBuffer`. `SecretBinary`, a non-object, a duplicate key, a missing or an empty field
     fail `secret_material_invalid`. On every failure path `resolve` deletes `response` and the
     parsed payload (`del`) before raising, so no frame local holds secret text (M5).
   - `preflight` delegates to `prepare_secret`, as Vault does (`vault.py:257`).
   - `aws_provider_from_env(*, endpoint_url=None)` builds a default session (the standard chain:
     environment, shared config and profile, web identity, container and instance metadata) and
     the provider. It catches `botocore.exceptions.BotoCoreError` and `ClientError` (this covers
     `ProfileNotFound`, `CredentialRetrievalError`, `NoCredentialsError` and an STS `ClientError`
     from assume-role), records only the class, and raises `SecretProviderConfigError` with fixed
     text after the `except` block closes (H3). No credential found raises the same.
   - File reads (H6, owner 2026-11-17): through `boto3`, the factory may read `~/.aws/config`,
     `~/.aws/credentials` and the files named by `AWS_CONFIG_FILE`,
     `AWS_SHARED_CREDENTIALS_FILE`, `AWS_WEB_IDENTITY_TOKEN_FILE` and `AWS_CA_BUNDLE`. They are
     declared as one `[[operator_environment]]` entry in `tests/sentry/file_access_modules.toml`,
     shaped like Vault's (`:77`): module `decoy_engine/secret_providers/aws.py`, function
     `aws_provider_from_env`, those four variables, owner `cam`, a reason and a removal
     condition.
3. **Error map**, by exception type and, for `botocore.exceptions.ClientError`, by
   `response["Error"]["Code"]` compared with fixed strings:

   | Source | Code |
   |---|---|
   | `ResourceNotFoundException`, `InvalidParameterException`, `InvalidRequestException` (secret scheduled for deletion), response version mismatch | `secret_version_unavailable` |
   | `AccessDeniedException`, `DecryptionFailure`, `UnrecognizedClientException`, `InvalidSignatureException`, `ExpiredTokenException` | `secret_access_denied` |
   | `NoCredentialsError`, `EndpointConnectionError`, `ConnectTimeoutError`, `ReadTimeoutError`, any other `ClientError` or `BotoCoreError` | `secret_provider_unavailable` |
   | `boto3` not importable | `secret_provider_unavailable` (as Vault's `_hvac`, `vault.py:62`) |

   The handler records only the class; the error is raised after the block closes. No vendor
   message, ARN, name or request id leaves the module. The factory's own errors (step 2) map to
   `secret_provider_unconfigured`.
4. **Coded config errors.** `SecretProviderConfigError(SecretProviderError)` (H4) with class
   attribute `code = secret_provider_unconfigured` (new reason: phase `resolve`,
   `Outcome.CONFIGURATION`, `RetryClass.CONFIGURATION_REPAIR`) and one fixed default text. It is
   added to `_CLOSED` (`secret_providers/_errors.py:129`), so `failure_of` and `error_for`
   (`:258`, `:271`) carry it like the other provider codes, and it is exported from
   `decoy_engine.secret_providers`. `VaultClientConfigError` subclasses it; its three messages do
   not change.
5. **Docs.** `docs/security/secret-providers.md`: the `aws-sm://` grammar row; an "AWS Secrets
   Manager" section in the Vault section's order (install, construction, one round trip, JSON
   field only, minimum IAM policy `secretsmanager:GetSecretValue` on the one secret plus
   `kms:Decrypt` on its key, rotation by a new version id); the "Consumers" CLI paragraph
   rewritten (the CLI registers both); "Not shipped" updated; a "Secrets in GCP and Azure"
   paragraph showing the CSI-driver `file:` path. A "Key version label" paragraph (H1): the label
   is `v<version id>` for AWS and `v<N>` for Vault, and it is part of the derived key. So moving
   a dataset from `env:` to a remote store keeps its output only if the `env:` ref already carried
   `?key_version=v<id>` with the same bytes; a new version id (rotation) changes every masked value
   even when the bytes are unchanged, as rotating the bytes does. A short note on the partial-ARN
   case (step 1).
6. **Live Vault record.** The builder runs `tests/secret_providers/test_vault_live.py` against
   `vault server -dev` on the Mac or a test VM and commits a record
   (`docs/records/2026-11-<dd>-f13-vault-live.md`) with the Vault version, the head and the
   result. A failure is a finding for this slice, fixed at the root in `vault.py`.

### E2 (CLI): register the remote providers

1. **Fact table.** New `src/decoy/_secret_providers.py`: `REMOTE_SCHEMES: Mapping[str,
   RemoteScheme]`, `RemoteScheme(extra: str, module: str, build: Callable[[], SecretProvider])`
   (M1):
   - `vault`: extra `hashicorp-vault`, module `hvac`, build `VaultKV2Provider(client_from_env())`;
   - `aws-sm`: extra `aws`, module `boto3`, build `aws_provider_from_env()`.
   `registry_for(ref_text) -> SecretProviderRegistry | None` reads the scheme with the engine's
   public `parse_ref`. For a remote scheme whose module is importable it returns a fresh registry
   holding only that one provider (M2: no `env` or `file` provider, so no private import); for
   `env:` and `file:` it returns `None` (the engine default).
2. **Admission.** `admitted_key_provider` passes `registry=registry_for(ref)` to
   `admit_mask_key`. No second admission site. `_REF_SCHEMES` becomes
   `{"env", "file", *REMOTE_SCHEMES}`.
3. **Missing extra.** `registry_for` probes before it builds: `sys.modules.get(module)` is `None`
   (a hidden module) counts as missing, else `importlib.util.find_spec(module) is None` does
   (M1). A missing module gives an empty registry, so the engine raises
   `secret_provider_unknown`. That code's `SECRET_REMEDIES` text, built from `REMOTE_SCHEMES`,
   becomes: "the reference names a secret provider this install cannot load: env: and file:
   always work; vault:// needs decoy-cli[hashicorp-vault]; aws-sm:// needs decoy-cli[aws]. See
   `decoy explain keys`." When the module is present, the build runs and any error it raises
   passes through unchanged; nothing catches `ImportError` around the build.
4. **Config error.** `SecretProviderConfigError` from a build propagates as is (its text is fixed
   and value-free); `secret_error_text` maps `secret_provider_unconfigured` to new constant text:
   "the secret provider's client settings are missing or unsafe (Vault: VAULT_ADDR and
   VAULT_TOKEN set, VAULT_SKIP_VERIFY unset; AWS: a credential the standard AWS chain can find)."
5. **Extras (M7, owner 2026-11-17).** Users install pip extras. CLI `pyproject.toml` (distribution

   The keys guide says that installing either extra makes DP fits uncertified, because the DP gate
   fingerprints every installed distribution; the certification rule does not change.
6. **Help and docs.** `INVALID`, `FLAG_HELP` (`_mask_secret.py:43-53`) and `decoy explain keys`
   name `vault://` and `aws-sm://` with their required query keys and the key version label; the
   CLI keys guide gains the two setups, the label rule (H1) and the CSI-driver `file:` note for
   GCP and Azure. `docs/cli-reference.md` is regenerated in the same PR (L4; CLI
   `pyproject.toml:144` names the check). The `_mask_secret.py` module docstring loses "nothing
   here reads an environment variable" and says instead that the remote factories read `VAULT_*`
   or the AWS chain only when the ref names their scheme (L4).
7. **Tests without SDKs (H5).** CLI tests replace `REMOTE_SCHEMES[...].build` (and the module

- CLI `decoy run` (with and without `--vault`), `tokenize`, `unmask`, `report vault`,
  `decoy.mask()`: all through `admitted_key_provider`.
- Engine library callers: `admit_mask_key(..., registry=...)` with a provider they register.
- Platform: N/A in V1, parked with platform V1.

### FK shapes

- N/A: the change supplies key bytes only; FK handling in keyed strategies is untouched, and AT-2
  compares whole outputs.

### Fields

- `aws-sm` ref: region, secret name, `version`, `field`, `encoding`; the Vault ref keeps its
  fields (`secret_providers/_types.py:165`).
- `AwsContext`: scheme, profile, access key id, secret key, session token, endpoint URL, shaped
  like `VaultContext` (`secret_providers/vault.py:124`).
- `RemoteScheme` (CLI): extra, module, build.

### Output surfaces

- CLI console, `--json` and `--verbose` refusal text, chosen by code in
  `src/decoy/_mask_secret_guidance.py:111`.
- Engine exception `str`, `repr` and tracebacks; logs.
