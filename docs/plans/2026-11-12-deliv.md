### 0.5 Build-ready slices

#### E2a: the managed pointer (engine)

Behaviour. `CurrentPointer` reads and swaps one small pointer file under its F22 lock with a
compare-and-swap on raw bytes, through a `PointerStore`. `LocalPointerStore` writes through a new
private file-access label `pointer`, whose publish fsyncs the staged file, replaces the leaf and
fsyncs the parent. A parent fsync failure after the replace is reported, not swallowed.

Established solution. Git's ref update (`git update-ref <ref> <new> <old>`, `refs/files-backend.c`
lockfile protocol: take `<ref>.lock`, compare the old value, write, fsync, rename). DELIV keeps
F22's `.<leaf>.decoy-lock` as the lock and does the compare and the replace under it. The
`uncertain` result follows PostgreSQL's rule that an fsync failure after a rename leaves the state
visible but not known durable (already cited for `_publish.py` in `docs/methodology-registry.yaml`).

Contract (replaces the 4.4 pointer bullets; revision 4.1 after Dennis r1):

- `PointerState(raw: bytes | None, version: bytes | str | None)`, frozen.
- `PointerResult = Literal["replaced", "stale", "uncertain", "unknown", "failed", "conflict"]`.
  `unknown` is a store answer only; `CurrentPointer` never returns it. `failed` means the replace
  did not happen.
- `PointerStore` Protocol: `read() -> PointerState`; `replace_if(expected, new: bytes) ->
  PointerResult`. `locator() -> object` names what the store writes, for the check below.
- `LocalPointerStore(leaf: OutputDir)`. `leaf` is the `OutputDir` whose leaf is the pointer file
  (`out/<name>/LATEST`). There is no `name` argument: an `OutputDir` is a parent plus one leaf
  (`fileaccess/_types.py:281`). `read` calls `leaf.adopt_file(limit=4096)`. A regular read returns
  `PointerState(raw, raw)`. An absent leaf returns `PointerState(None, None)`. `replace_if` does a
  fresh read under the held lock and compares raw bytes with `expected.raw` (a mismatch gives
  `stale`). It then opens `leaf.begin("file", "replace", label="pointer")`, writes `new` through
  `txn.create_file("value")`, closes the file, and calls `txn.publish()`. `CommitUncertain` maps to
  `uncertain`. `FileAccessDenied` or any other pre-replace `OSError` maps to `failed`. Each mapping
  returns outside its handler, so no exception context survives. It does not
  sweep older pointer stages. `OutputDir` has no label-scoped sibling removal API. Adding one only
  for this cleanup would add a new destructive capability. A crash can leave a private 0600
  pointer stage beside `LATEST`; this is the named V2-LOG limit in section 12 beside F22 L2.
- Read-error map, for `read` and for the fresh read in `replace_if` (each raised or returned
  outside the handler, so `__context__ is None`):

  | Source | Exception | `read` | fresh read in `replace_if` |
  |---|---|---|---|
  | `adopt_file` absent | returns `None` | `PointerState(None, None)` | compared as absent |
  | `_adopt_at` link | `OSError` `ELOOP` | `PointerUnreadable` | `failed` |
  | `_adopt_at` not regular | `OSError` `EINVAL` | `PointerUnreadable` | `failed` |
  | over 4 KiB | `LeafTooLarge` | `PointerUnreadable` | `failed` |
  | strict policy refusal | `FileAccessDenied` (as `_publish.py:154` handles it) | `PointerUnreadable` | `failed` |
  | any other `OSError` (open, read, fsync) | `OSError` | `PointerUnreadable` | `failed` |
  | publish | `CommitUncertain` | n/a | `uncertain` |
  | publish | any other `OSError` | n/a | `failed` |

  `PointerUnreadable` is value-free (cause `publication_failed`). The store never gives
  `unknown`.
- `CurrentPointer(store, lock: OutputDir)`. `lock` is the same leaf `OutputDir`, so
  `lock.lock(timeout_s)` takes `.LATEST.decoy-lock`. The constructor refuses (`ValueError`) a
  `LocalPointerStore` whose `locator()` differs from the lock's leaf. `read()`;
  `locked(timeout_s) -> ContextManager[HeldPointer]`; `HeldPointer.swap(expected, new: str) ->
  PointerResult` writes `f"{new}\n".encode("ascii")`. On `unknown`, one outcome-check read:
  `replaced` if the store now holds those bytes, else `uncertain`. `HeldPointer` exists only
  inside `locked`; a swap after the context exits raises `RuntimeError`.
- `read_value(raw: bytes | None, accept) -> str | None`: absent returns `None`. More than 4096
  bytes, non-ASCII, no single trailing newline, another newline, or a value that `accept` rejects
  returns `None` and one value-free warning. A valid value has exactly one trailing newline
  stripped. The helper uses the same 4096-byte bound as `LocalPointerStore.read`.
- File-access label `pointer`: added to `StageLabel`, `STAGE_PREFIX` (its own prefix; `begin`
  looks the label up there and `CREATES_PARENTS` derives from it, so a missing entry is a
  `KeyError`) and `PRIVATE_LABELS` (mode 0600, no write-through of a link or special file at the
  leaf). A new `DURABLE_REPLACE_LABELS = frozenset({"pointer"})` beside `DURABLE_LABELS`
  (`_output.py:64`) selects the publish; no `if label == "pointer"`. The publish is
  `_durable.publish_replace_durable(parent_fd, stage, leaf)`, built from the existing pieces:
  fsync the file, `renameat`, then the parent fsync through `_fsync_dir` (`_durable.py:104`,
  which honours `_DIR_FSYNC_UNSUPPORTED`) run inside `_sync_bound` (`:211`, `CommitUncertain`
  raised outside the handler). No third fsync policy. `RootedOutputTxn.publish` and
  `LocalOutputTxn.publish` each gain one dispatch line.

## 1. Guarantee

> Under `delivery.mode: strict` (the default) a `decoy run` either makes every output of the run
> visible together, or makes none of them visible and leaves the previous delivery and its vault
> untouched. Under `best_effort` it makes visible every table that passed, and drops each failed
> table together with every table that depends on it. A post-scan block withholds the whole run
> in both modes. A run that asks for post-scan and cannot evaluate it delivers nothing.

"Visible" means reachable through the path a consumer reads: `out/<name>/LATEST` (and the
derived `current` link) for a project run (run-folder kind R), or the target paths for a fixed
folder (kind A). Crash behaviour differs by kind (4.3). After the visibility point nothing turns
a delivered run into a "nothing delivered" exit; a later durability failure is a warning.

## 2. Frame

### 2.1 Problem

- Each table is written to its target as soon as it is ready (`_write_mask_outputs`, P4
  `src/decoy/cli/run/_execute.py`; `write_targets`, `src/decoy/cli/io/_targets.py:436`). Each
  file is atomic (row 61a). The run is not: a failure in table 3 of 5 leaves 1 and 2 written.
- The chunked loop (P4 `_run_chunked_mask` in `_execute.py`) writes per table through
  `write_chunked_output`.
- Post-scan is report-only (`compute_post_scan_integrity`,
  `src/decoy_engine/execution/pipeline/_post_scan.py`; revision 4.1 redirect). On `--chunked` it never runs and
  nothing says so.
- `RunLayout.commit_latest` (P4 `io/_layout.py`) moves `LATEST` with "later run id wins", not a
  compare-and-swap. A failed `LATEST` write is a warning with exit 0.
- `--evidence-out` is written after the outputs (`src/decoy/cli/run/_flow.py:101`); its failure
  exits 3 (`_evidence.py`, `EXIT_RUNTIME`) with the outputs already in place.
- `_commit_vault` (P4 `run/_vault.py`) replaces the vault and drops its backup before any output
  is written. The CLI vault writer is new per run (`vault_writer_for_config`, P4 `_prepare.py`),
  so a failed publish leaves the previous dataset next to a vault that cannot reverse it.
- B-6 (engine #559, merged after `v0.23.0`) publishes a vault exclusively: `vault_exists` when
  the path exists, and a published vault is never replaced. Today's `_commit_vault` writes into
  a `mkstemp` file it made first, so it fails with `vault_exists` once the CLI repins past #559.

### 2.2 Terms

- **Stage.** Where outputs are written before any is visible. R: an F22 directory stage
  (`._decoy_publication_pending_<token>`) beside the run folder. A: a temp file per output.
- **Sink.** `DeliverySink` (`src/decoy/cli/io/_delivery.py`), the one CLI object every route and
  caller writes run outputs through. **Deliver** is its one step that makes the staged run
  current, after every table, the post-scan result and the vault and evidence writes.
- **Visibility point.** R: the `os.replace` of `LATEST`. A: the unlink of the batch journal.
- **Strict** delivers all or nothing (default). **Best-effort** delivers the good tables and
  drops a failed table with every table reachable from it (4.4); a post-scan block still
  withholds everything.
- **Single-root rule.** In both modes every file target and an enabled quarantine file resolve
  under one delivery root: the run folder (R) or one fixed folder with every output directly in
  it (A). Anything else is refused with `layout.delivery_root_split`, exit 1.

## 3. Established solutions

Search scope: the codebase (F22 publication, `src/decoy/_atomic.py`, P4) and the published
patterns below.

- Same-filesystem stage, fsync file and directory, `rename(2)`: PostgreSQL `durable_rename`
  (`src/backend/storage/file/fd.c`). F22 `publish_unit` (`origin/feat/f22-a3`,
  `publication/_publish.py`) does this for one directory unit; DELIV calls it.
- A pointer written last with an expected old state: git `update-ref <ref> <new> <old>`. DELIV's
  `LATEST` swap refuses any stale expected state.
- In-place replacement of several files: SQLite's rollback journal (sqlite.org/atomiccommit.html):
  backups, journal fsynced, directory fsynced, replace, then delete the journal as the commit.
  Kind A follows that order (4.3).
- Several independent files are not crash-atomic without a journal or a pointer; 4.3 says so.

Custom code left: the drop walk (`plan_delivery`) and the outcome mapping. Both are small and pure.

### 4.2 Run order (both kinds)

1. Gate: `layout_issues` refuses a split root (C1). P4 `_check_chunked_tables` in `_execute.py`
   handles `--chunked` when the post-scan gate applies. If integrity was requested, it refuses as
   it refuses quarantine (`_ChunkedQuarantineError`). If relationships alone make the gate apply,
   it gives the interim warning and run-result record from 11. CR uses
   `post_scan_integrity_requested(config)` plus direct relationship inspection until C5 replaces
   both applicability checks with `post_scan_gate_applies(config)` from POSTSCAN-STREAM.
2. `DeliverySink.open(layout, config)`: refuses a split root with the same code (for `api.mask()`
   and `demo`, which skip the gate); opens the stage; R reads the pointer's raw bytes; A runs
   journal recovery under the folder lock (4.3).
3. Every route writes through `sink.write_table` or `sink.write_chunked`, which call the file
   writers with stage paths and no ledger. `sink.place_quarantine(config)` gives the engine a
   staged quarantine path. The sink records each table as `ok` or a failure code.
4. Post-scan: the engine raised `PostScanBlockedError` (or an isolated outcome `blocked`), or the
   run returned without a report while `post_scan_gate_applies(config)` is true. C2a uses
   `post_scan_integrity_requested(config)` until C5. Either withholds the whole run, exit 4.
   `--post-validate-enforce` with failed checks also withholds the whole run (today it skips the
   `LATEST` move, `run/_render.py:49-57`).
5. `plan_delivery(config, outcomes)` returns a `DeliveryDecision`.
6. If nothing is to be delivered: `sink.abort()`. Stage removed, pointer untouched.
7. Else `sink.deliver(decision, before_visible)`, which calls the stage's
   `deliver(decision, before_visible)` (the `SinkStage` protocol, 4.6):
   a. take the locks (4.5); R: re-read the pointer and compare with step 2, else
      `delivery_pointer_moved`;
   b. `before_visible()`: write the evidence manifest to an attempt-scoped sibling of
      `--evidence-out`. On kind A only, first publish the new vault create-only. One helper,
      `PreVisible`, owns these steps (4.6);
   c. publish (4.3). On kind R, `publish_unit` first publishes the vault through rule V, then binds
      the unit. Set state `delivering`, pass the visibility point, and atomically publish the
      attempt evidence to `--evidence-out` only after a durable delivered outcome. An uncertain
      outcome leaves live evidence unchanged. An interrupt in this step is judged by the pointer
      re-read of 4.7 rule 2;
   d. while the pointer lock, or the A folder lock, and side-file locks are still held, reconcile the outcome and call
      `PreVisible.restore` or `discard`; both remove only attempt-scoped evidence. Every
      published vault is kept, including a not-delivered orphan. Release the locks only after
      reconciliation;
   e. fill the publication ledger (`ctx._published`) with final paths, only when delivered.
8. `_flow.py` `finally` calls `layout.abandon()` on an unfinished exit (`_flow.py:78-81`), which
   calls the abort callback the sink registered on the layout.

### 4.3 Root kinds

**Kind R (run folder).** All targets relative, inside a project. Root `out/<name>/<run-id>/`.

- Stage: an F22 directory transaction beside the run folder P4 made (`create_run_folder`, 0700,
  empty), so on one filesystem. Nested relative targets are allowed.
- Publish: `publish_unit(out, txn, request, ...)` judges the empty run folder and renames the
  stage onto it; then `HeldPointer.swap(expected, run_id)` replaces `LATEST`; then the CLI points
  `current` at the run (POSIX symlink, derived, warning on failure).
- The run folder takes the stage's mode on rename. AT-14 pins 0700.

| Crash point | Left on disk | Visible | Recovery |
|---|---|---|---|
| before bind | stage (F22 L2 litter), empty run folder | previous run | none |
| after bind, before `LATEST` | bound run folder, not current; the new vault (orphan) | previous run | none; the next run with that `--vault` refuses `vault_exists` until the orphan is deleted (12.1) |
| after `LATEST`, before `current` | `current` lags | new run | next delivery fixes `current` |

**Kind A (fixed folder).** Absolute targets, `--out-dir`, `api.mask()`, `demo`. Every output
directly in one folder.

C2a recognizes `fixed_folder` but passes it through to today's per-file writers. Between C2a and
C2b, `--out-dir` has exactly today's behaviour, and the sink becomes `delivered` once today's
writers (vault, outputs, evidence) return, so the result reports the tables as delivered (AT-49). Kind A has no strict delivery guarantee until C2b.
C2b replaces the pass-through with the batch below. The final V1 guarantee then covers kind A.

The batch in `_atomic_batch.py` owns the journal `.decoy-batch.journal`, a private file of the
batch protocol, not an engine record. Order (SQLite rollback journal):

1. Stage each output as a temp in the folder (`.<target>.decoy-<hex>.tmp`).
2. Take `_folder_lock(folder)`; if a journal exists, recover first (below).
3. Hard-link a backup of each existing target (`_backup`), and of each table dropped under
   best-effort (D-9).
4. Write the journal: per target its basename, its backup basename or `new`, and its staged
   basename or `drop`. The published vault is outside rollback. Evidence is still at its
   attempt-scoped sibling and is not live. Fsync the journal.
5. Fsync the folder.
6. Replace each target (or unlink a dropped one), then fsync the folder.
7. Unlink the journal (the commit point), fsync the folder.
8. On a durable commit, atomically replace `--evidence-out` from the attempt-scoped evidence and
   fsync its parent. On an uncertain commit, leave live evidence unchanged. Then remove output
   backups. `PreVisible` keeps the new vault in every outcome.

**Backup ownership.** The batch has one ordered in-memory ledger, in target order, and one
builder owns every transition. Each target records one of `proposed`, `linked` (`owned`),
`replaced`, `restored` and `settled`; transitions are monotonic and skip states the operation
does not reach. The batch owns a backup name only after the `os.link` that creates it returns
successfully in this run. A proposed name whose link fails
with `EEXIST`, `EPERM`, `EXDEV` or any other error is never owned and is never deleted. Any
pre-existing file at that name is untouched.

Cleanup is the one ownership decision point. Its delete-or-keep result is a pure function of
the ledger plus a filesystem check made by cleanup itself. It considers only `linked` backups
and deletes one when its target was restored from it, or when its target was never replaced and
is still the same inode as the backup, checked with `os.path.samefile` or `st_ino` plus `st_dev`.
It keeps an owned backup only when the target was replaced and was not restored; that backup is
value-bearing and is reported in `left`. Cleanup then marks the entry `settled`. Proposed but
unlinked names are outside cleanup.

`KeyboardInterrupt`, `SystemExit` and every other `BaseException` use that same cleanup at every
boundary. Cleanup re-checks same-file identity for every owned, not-restored backup instead of
trusting an earlier check or a later list append. The same inode means the target is unchanged,
so cleanup deletes the owned backup. Thus an interrupt after the same-file check and before the
restored mark cannot leave an owned backup beside an unchanged target. A different inode or a
missing target means the old bytes may still be needed, so cleanup keeps and reports the backup.

Recovery runs under the same lock at `open` and at the start of the batch: for each entry, put
the backup back, or unlink a `new` target; unlink staged output temps; leave unjournaled
attempt-evidence litter and every published vault in place; fsync; unlink the journal; fsync.
The new run's result carries `delivery_rolled_back`
(WARNING, exit unchanged). The reader is strict: schema 1, at most 64 KiB, entry names are
basenames of the batch shapes (`.<name>.decoy-<12 hex>.bak`, `.tmp`), extra entries only when
the backup is `.<name>.<16 hex>.bak` beside its target. Anything else refuses the run with
`publication_failed` and changes nothing.

Strict on A: all-or-nothing on every caught failure; after a crash the folder is mixed until the
next open or deliver in that folder rolls it back (Q1, Q3).

Nested relative targets on A are refused at `open` with `layout.delivery_root_split` (D-8
decision). The batch's lock is one `flock` on one folder (`_folder_lock`); nested targets need a
lock per subfolder in a fixed order, per-subfolder fsyncs and journal names with path components
(a wider trust class than basenames). That is over the 30-line bound, so V1 refuses and logs it.

| Kind | Lock file | Taken | Held across |

Order is always the sorted side-file leaf locks, then the pointer lock and run-id lock for R or
cloud, or the A folder lock.
`HeldPointer.swap` uses the held lock and never locks. Nothing re-locks a held file. F23 resume
takes the pointer and run-id locks in the same relative order.

The side-file leaf locks are the serialization rule for a `--vault` or `--evidence-out`
destination shared across pipelines. Each lock capability is opened on the
`destination_entry(final)` parent and leaf used by the writer, so symlinked parent spellings
converge on one lock. A contender fails closed with F22's existing lock refusal
instead of entering `PreVisible`; it does not wait. This reuses `OutputDir.lock`, not a second
lock protocol. AT-51 holds run 1 at restore and proves run 2 cannot publish shared evidence
until run 1 finishes reconciliation. Two cloud runs on one machine therefore cannot
interleave their vault and evidence commits. A run
on another machine has its own local vault and lock, so only the object-store pointer CAS
arbitrates between the machines.
For an all-cloud run, `DeliverySink.open` resolves the project through
`find_project(config.parent, project)`, whose implicit root is the config folder, and creates or
opens `<resolved-project-root>/out/<name>/` with the existing project output and claim machinery.
Every arena for that project and pipeline passes the `OutputDir` for that folder's `CURRENT` leaf as `lock`. A creation or
lock failure is a value-free refusal before any upload.

Order for one run:

- W1. Stage writes: every table output and the quarantine file go to stage paths (4.2 step 3).
- W2. Decision: post-scan and enforce withhold, then `plan_delivery` (4.2 steps 4 and 5).
- W3. `abort` when the decision delivers nothing, or on any exception or interrupt before W5.
  Before the stage is removed, a built post-scan report is copied from the stage and published
  outside the unit. R uses the create-only leaf `out/<name>/<run-id>.post-scan.json`. It takes

  `CLI_WARNING_CODES` registry and its existing sentry. No raw exception text is read. It does not change exit 4 or

  goes to W7.

  publishes the new vault create-only. On R, rule V publishes the vault in W5. The manifest
  hashes the staged bytes that W5 publishes unchanged. The live evidence path is untouched.
- W5. Publish. R: bind the stage onto the run folder and swap `LATEST` (the visibility point).

- W8. `_result.finish(ctx, outcome)`, once: build the document from the decision and the sink's

1. After W4 starts, nothing writes into the stage except `publish_unit`'s descriptor at bind,

2. Interrupt at the visibility point. Around W5 the stage catches `BaseException`. Under the

   restore the attempt file. The `delivering` flag never decides a restore. The outcome read,
   state transition and `PreVisible` call all occur before either pointer or side-file lock is

3. `delivery_facts` (C2a) reads the sink state when `finish` runs (the interim kind A

### 7.2 POSTSCAN-STREAM (row 60)

The contract is POSTSCAN-STREAM section 4.10 (`2ec7a0c3`). DELIV relies on exactly this:

> `verification.postmask._blocked.post_scan_verdict(report)` is the one blocking decision
> (slice PS-2b). On a block the engine raises `PostScanBlockedError` (`reason` the first code in
> 4.8 order, `report` the value-free report with `verdict.codes`) and nothing has committed. It
> is raised inside `observed_commit` before `sink.commit()` on a sink route, in `execute_route`
> after the route returns on a no-sink route (the CLI's plain call), and in the isolated child,
> which surfaces as `IsolatedRunResult` outcome `blocked` (wired by PS-8 and PS-9). The gate takes
> no delivery mode. A requested post-scan with no report is a block on the CLI side.

DELIV maps `PostScanBlockedError` and outcome `blocked` to row 6 (nothing, exit 4, both modes)
and owns the missing-report block (row 7) and the `--chunked` refusal (slice CR), which
POSTSCAN-STREAM names as its dependency on row 61 (its section 1, exemptions). DELIV reads no
severity and imports nothing from `_blocked.py` but the exception.

POSTSCAN-STREAM owns one predicate for whether the post-scan gate applies to a config:
`post_scan_gate_applies(config)`, beside `post_scan_integrity_requested` in
`config/_post_scan.py`. Its gate, DELIV's row-7 missing-report rule and DELIV's chunked gate are
the three callers. A sentry test asserts that all three call this function and that no second
predicate exists. Its seeded mutation replaces one call with local config inspection and must
turn the sentry red.

Until the engine release carrying that predicate is pinned, CR uses
`post_scan_integrity_requested` for refusal and direct relationship inspection for the interim
warning. C5, after the POSTSCAN release is pinned, replaces those applicability checks and the
row-7 check with `post_scan_gate_applies`. CR still uses `post_scan_integrity_requested` only to
choose refusal from the two gate outcomes. For `--chunked` with declared relationships but no
requested integrity, CR follows the working owner answer in 11: it warns with a value-free
message and records in the run result that the relationship key check did not run. This is an
interim behaviour only. POSTSCAN-STREAM removes it when the chunked route runs the key check.

## 12. Open risks, named limits and V2-LOG lines

1. Vault and evidence before publish (F22 rule V). The vault is create-only (B-6), so there is
   no old vault to keep. A SIGKILL after the vault publish and before the visibility point leaves
   a new vault (an orphan) with the previous dataset current; it reverses no visible output. The
   next run that names the same `--vault` refuses `vault_exists` before any row is read; the
   named remedy is to delete the orphan explicitly after confirming `LATEST` did not move. No
   CLI rollback, journal recovery or later run removes a published vault. Evidence is written to
   `.<evidence>.<invocation-id>.attempt` before visibility and atomically replaces the live path
   only after a durable visibility outcome while the locks are held. A SIGKILL can therefore leave attempt litter
   or stale live evidence, but never evidence for a run that is not current. Reclaiming attempt
   litter is a named V2 cleanup limit.

3. The `current` link is POSIX only and best-effort; `LATEST` is authoritative.

## 17. Pre-mortem

A new route writes straight to targets: G-ONE-DELIVERY-SINK (AT-25). The older of two racing
runs wins: CAS under the held lock (AT-19). Best-effort delivers an orphan through a cycle or a
generate reference: the reachability walk (AT-6, AT-7). Post-scan cannot run and the run
delivers: CR (AT-29), a missing report withholds (AT-37), an engine block gives exit 4 (AT-38).
A failed publish leaves a vault for outputs that never appeared: it is an explicit orphan and a
rerun refuses it until the operator deletes it (AT-33). An interrupt around the pointer move
publishes or removes only attempt evidence while keeping the vault: the pointer re-read decides
under the held locks (AT-48). A SIGKILL on a fixed folder
leaves a silent mix: journal order and recovery (AT-21, AT-34). A delivered run reports
nothing: the visibility point sets `delivered` (AT-12, AT-31). `_layout.py` or `_atomic.py`
passes its cap: C0 moves the batch, C2a moves the pointer logic.
