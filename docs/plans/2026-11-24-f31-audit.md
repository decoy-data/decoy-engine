## Part 1. Audit

### Scope and threat model

Only accidental leaks are in scope. A leak is a cell value, an expression's text, or a secret
that reaches an outbound text stream through an ordinary code path. Hostile in-process objects
(a crafted `__str__`, a malicious plugin) are V2.

Outbound text streams:

- engine log records (file handler, console handler, any host-attached handler);
- exception messages (every engine message is outbound, because the CLI prints it);
- `warnings.warn` text;
- report documents (run result, progress events, telemetry, records, scan and profile output);
- CLI stdout, stderr and the `--json` document;
- CLI notify payloads and CLI log handlers.

### Method

1. An AST walk over every `.py` file under engine `src/decoy_engine` (963 files) and CLI
   `src/decoy` (199 files). Each site gets a class (raise, log, warn, terminal, exception-text
   copy, `__str__`). Each interpolated expression gets a tag: EXC (an except-bound name or
   exception text), VALUE (a name such as `value`, `cell`, `row`, `expr`, `text`), LOC (a path,
   URI or DSN name), IDENT (any other name). A site's risk is its worst tag: leak (EXC or VALUE),
   review_loc (LOC), safe_ident (IDENT only), safe_const (no interpolation).
2. A second AST walk that finds every copy of exception text (`str(exc)`, `repr(exc)`,
   `f"{exc}"`, `exc.args`, `exc.message`, `exc.detail`, `format_exc`) and the sink it flows to.
3. A read of every existing choke point and sentry, listed below.
4. `graphify query` on the engine graph (built 2026-11-21) to confirm the callers of
   `approve_ref`, `safe_error_type` and `error_result`.

The counts are heuristic. The name tags are the same kind of heuristic that
`tests/sentry/test_log_interpolation.py` uses. Samples of 30 "leak" raises showed many false
positives: names such as `key`, `x` and `default` that hold config identifiers, and coded raises
whose fields are only locations. The engine "terminal" class is mostly `fail()` helpers in plan
checks, not prints. We did not measure an exact precision. Read the raise and terminal "leak"
rows as an upper bound. The exception-text copy counts (step 2) have high precision, because the
pattern is exact.

## Part 2. Plan

### Guarantee

Under default flags, a planted secret placed in a cell, an expression literal, a config default
or a connection secret does not appear in any engine or CLI outbound text stream, for every entry
point in the canary corpus. Exception text from stdlib, third-party and native errors reaches a
sink only as a type label or a reason summary.

### Non-goals

- Hostile in-process objects (V2).
- E0b, the `decoy-safe-output/v1` wire line. It stays parked.
- The Platform slices of F31. They stay parked.
- The two exception-label sets and the 18 `json.dumps(sort_keys)` sites (V2-LOG).
- Giving reason codes to the 933 uncoded project raises.
- F34, the text-span scanner over output data.
- Deliberate data outputs (owner question 5).

### Behavior

1. One renderer: `decoy_engine.safe_output.render_failure(exc) -> SafeText`.
   - A `DecoyError` with a reason code renders its registry summary and its approved refs.
   - A project error whose class is in the value-free message registry renders its message.
   - Anything else renders the class name from `safe_error_type`, plus the reason code if a
     `__cause__` carries one.
   - `SafeText` is a frozen type. Only the renderer and `SafeText.const(...)` (a string literal)
     build one. A sink typed to take `SafeText` cannot get raw text ("parse, don't validate").
   - If rendering raises, the renderer returns the type label.
2. One log filter: `decoy_engine.safe_output.SafeRecordFilter`, a `logging.Filter` (stdlib
   logging cookbook, "Using Filters to impart contextual information"). It runs in `filter()`,
   before any formatter:
   - an `args` item that is a `BaseException` becomes its type label;
   - `exc_info` becomes the type label plus `file:line` frames, with no message and no locals;
   - `stack_info` is kept, because it holds only code locations.
   The engine attaches it in `_new_engine_handler`. It is public so a host (the CLI, the
   platform) attaches it to its own handlers.
3. CLI sinks take `SafeText`: `emit_error(message: SafeText)`, `fail()`, the `--json` `error`
   field, notify payloads, and the `-v` detector handler.
4. A shrink-only ratchet on exception-text copies in both repos.

### Design notes

- Established practice. The OWASP Logging Cheat Sheet says to exclude sensitive data and
  exception detail from logs and to sanitize at the logging layer, not at each call. Python's
  `logging.Filter` on a handler is the stdlib place for that; structlog does the same thing with
  a processor chain between the call and every renderer. We use the stdlib filter because the
  engine does not use structlog and a host's handlers are stdlib handlers. RFC 9457 is the model
  for error text: a stable type and title from a registry, and separate closed occurrence fields.
  The engine's `ReasonRecord` already follows it.
- Principles that apply. One place per fact: reason summaries stay in the registry and the
  renderer reads them; the value-free message registry is the only list of classes whose
  message may print. Dependency direction: the CLI imports the renderer and filter from the
  engine; the engine does not know the CLI.
- No new flags that switch behavior. The renderer has one output per exception.
- Reuse: `safe_error_type`, `approve_ref`, the reason registry, and the AST tagger of
  `test_log_interpolation.py` (shared helper, not a copy).

### Pre-mortem

Assume the program shipped and a leak was still found. Likely causes, and what stops each:

| Failure | Stopped by |
|---|---|
| A platform or host handler prints engine records raw | `SafeRecordFilter` is public; the corpus attaches a host handler; platform adoption is a parked F31 slice |
| A new command prints `str(exc)` in its own way | `SafeText` sink types; C3 ratchet; the CLI corpus covers the new command by default |
| A registered class gains a value interpolation | the registry sentry |
| A third-party library puts a value in a warning | the corpus captures warnings; `warnings.warn` sites are counted in Part 1 |
| Error text becomes too vague and users file support tickets | reason summaries and refs; the `--verbose` hint; owner question 4 |
| The corpus passes because a failure shape never triggered | class 8: each case asserts its reason code before checking absence |

### Failure modes

| Failure | Detection | Response |
|---|---|---|
| A new raise copies `str(exc)` into its message | E3 or C3 ratchet fails | render the cause by type, or add a reason code |
| A sink receives a plain `str` | mypy on `SafeText`; C1 sentry | wrap with `render_failure` or `SafeText.const` |
| A third-party error message holds a value | renderer never prints third-party text | none needed |
| A value-free class gains a value interpolation | registry sentry | fix the raise or drop the class from the registry |
| A host handler lacks the filter | canary corpus with a host handler at DEBUG | attach the filter |
| A native error puts a value in `detail` | E4 native canary | fix the Rust site |
| The renderer itself raises | renderer catches it and returns the type label | unit test with a raising `__str__` |
| Users lose useful detail in error text | reason summaries plus refs; `--verbose` hint | owner question 4 |

### Acceptance tests

Written before code, in each slice's test file.

1. `render_failure`: a coded error gives its summary and refs; a registered class gives its
   message; `ValueError("bad 123-45-6789")` gives `ValueError`; a raising `__str__` gives the
   type label; a chained coded cause gives its code.
2. `SafeRecordFilter`: a record with `exc_info` from an error that holds the canary, formatted by
   a stock `Formatter`, has no canary; `%r` of an exception arg gives the label.
3. Engine canary corpus (`tests/sentry/defects/test_canary_corpus.py`): a fixture table whose
   cells, expression literals, defaults and connection password hold `DECOY_CANARY_F31_7Q4Z`.
   Failure shapes: bad numeric cast, FPE out-of-domain input, expression evaluation error, date
   parse error, unmask mismatch, connector auth error, native redaction error. Each public entry
   point (`run_pipeline`, scan, profile, validate, unmask, tokenize) runs with a DEBUG file
   handler, a console handler and a host handler. The canary must be absent from every handler
   output, every warning, the run result, the progress events, and `render_failure(exc)` of any
   raised error.
4. CLI canary corpus (`tests/sentry/cli_text/test_canary_every_command.py`): every registered
   command (47 `.command(` registrations today, enumerated from the Typer app so a new command is
   covered by default) runs as a subprocess against the canary project. It checks stdout, stderr,
   the `--json` document, the log file and the notify payload. Default flags only.
5. Ratchets: engine baseline 74, CLI baseline 74, shrink-only, checked against main.
