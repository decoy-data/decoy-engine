## 2. Guarantee and non-goals

### The guarantee (pinned)

1. **Retry.** Every engine-level retry of a `TransientError` runs in one executor,
   `connectors/_retry.py`, with the SDK's documented defaults (3 attempts, 1 s base, factor 2,
   plus or minus 25 percent jitter) under a total deadline. It retries only the operations the
   table in 4.1 marks idempotent, and each operation is retried at exactly one layer (SDK or
   engine, never both). A conditional write, a final rename, a lock create and a pointer swap are
   never resent blindly. Two named resends exist outside the executor, each after a state check
   and at most once: the SFTP rename resend in `_sftp_client._resolve_rename` (4.4 step 6, temp
   still present after a dropped connection) and CLI-CLOUD EC3's 409 re-read-then-resend inside
   `ObjectPointerStore` (`publication/_object_pointer.py`, CLI-CLOUD 4.3 step 8; the method name
   is EC3's). Both are listed by exact `(path, function)` in the
   AT-E1-6 sentry; no other code catches a connector error to call again.
2. **Resume reads the same object.** A streamed read that fails mid-object resumes from its byte
   offset only while the object is the one the read started on (S3 `ETag` through `IfMatch`; GCS
   `if_generation_match` on every chunk; SFTP size and mtime). A changed object fails with kind
   `source_changed`; the spool never holds bytes from two versions (SFTP within the 1 s mtime
   granularity, 4.4).
3. **Content digest.** `WriteResult` gains `sha256: str | None` (64 lowercase hex of the exact
   bytes the sink consumed). The three first-party sinks set it. A provider checksum mismatch (S3
   flexible checksums, GCS crc32c) fails the write with kind `digest_mismatch`. On S3 no object is
   created. On GCS the library raises `DataCorruption` after the resumable session finalized, so
   the object exists; the GCS writer wrapper in `connectors/_clients.py` deletes it best effort
   with `if_generation_match` set to the generation from the finalize response and records
   `cleanup_ok` (4.3). SFTP has no server
   checksum; it checks the stored size and records the digest.
4. **SFTP is value-free and credential-free.** SFTP errors carry fixed words and a `kind`, no SDK
   text, host, user or path, with `__cause__` and `__context__` both `None`. Pipeline files hold
   no SFTP secret: auth is the SSH agent, a referenced `identity_file` path, or the default key
   files. Host keys are checked strictly against `known_hosts`; an unknown or changed key is kind
   `host_key_rejected` and is never retried.
5. **SFTP writes stage then rename.** Every SFTP write goes through one staging core: a unique
   temporary name beside the target, a size check, then a rename. The SDK sink replaces with
   `posix-rename@openssh.com`; the delivery store creates with plain SFTP rename, which OpenSSH
   refuses when the target exists. A stopped transfer leaves the previous target untouched and
   removes its temporary file best effort, reporting whether removal happened.
6. **Remote sources for scan and subset.** `decoy scan` takes `s3://`, `gs://` and `sftp://`
   URIs; `decoy subset` and `decoy run` take `sftp` sources, and `decoy subset` takes `s3` and
   `gcs` sources. Each remote source is spooled whole into the private scratch arena and then read
   by the local readers, so a remote input and its local copy give the same scan, subset and mask
   output.
7. **SFTP targets** deliver through CLI-CLOUD's run-prefix and pointer layout
   (`<dir>/<pipeline>/runs/<run_id>/...`, `<dir>/<pipeline>/CURRENT`) with an `SftpObjectStore`
   behind the same `ObjectStore` protocol; concurrent writers are serialized by an exclusive
   remote lock file.

### Non-goals

- Ranged (no-download) cloud scan; prefix, glob or directory sources; `endpoint_url` targets;
  `credentials_ref` in the CLI (the CLI-CLOUD V2-LOG lines stay there).
- Password authentication in pipeline files; keyboard-interactive or GSSAPI auth; encrypted key
  files without an agent (refused with `credentials`).
- A full read-back digest check of SFTP uploads (OQ-6); source-object digests in evidence
  (F02-FU-2).
- FTP, FTPS, SCP, WebDAV, Azure Blob; database targets (row 86, F01).
- Platform surfaces of F02 (platform parked). Windows (out of the V1 build, as in CLI-CLOUD).
- Automatic cleanup of stale SFTP temporary files or locks left by a killed process (documented
  manual step; F02-FU-3).
- Hostile servers that lie about rename or size (V1 threat model: accidental only).

## 3. Established solutions

Search run (2026-11-17): AWS Architecture Blog "Exponential Backoff And Jitter" (Brooker, 2015);
AWS Builders' Library "Timeouts, retries, and backoff with jitter" (retry at one layer only);
tenacity documentation (`stop_after_attempt`, `stop_after_delay`, `wait_exponential`,
`wait_random`, `retry_if_exception_type`); google-api-core `Retry` (initial, multiplier, maximum,
deadline); botocore standard retry mode; AWS SDKs and Tools reference "Data Integrity Protections
for Amazon S3" (request checksums on by default, Boto3 default CRC32,
`request_checksum_calculation` and `response_checksum_validation` `when_supported`); S3 user guide
"Checking object integrity" (CRC32, CRC32C, SHA-1, SHA-256, CRC64NVME; full-object and composite
checksums for multipart); GCS "Data validation and change detection" (crc32c and md5; the client
library validates uploads with `checksum="auto"`, the default in the installed
google-cloud-storage 3.12 `blob.py`); paramiko 5.0.0 `SFTPClient.open` (mode `"x"` sets
`SFTP_FLAG_EXCL`), `SFTPClient.rename`, `SFTPClient.posix_rename`, `SFTPFile.check` (the
`check-file` extension, which OpenSSH does not serve); OpenSSH `sftp-server.c` `process_rename`
(regular files are renamed with `link` then `unlink`, so the rename fails when the target exists)
and the OpenSSH `PROTOCOL` file (`posix-rename@openssh.com`, atomic replace); the rclone SFTP
backend (since v1.63 uploads to `<name>.XXXXXX.partial` and renames, `--inplace` to opt out;
rclone forum threads report servers that refuse rename); fsspec `sftp` (a thin paramiko wrapper)
and asyncssh (async, a second SSH stack). In the codebase: `connectors/_clients.py` (EC1
classification and `_call`), `object_store.py`, CLI-CLOUD 4.3 to 4.7, F22 `publish_unit` (stage,
then one durable rename).

Followed:

- **Backoff**: capped exponential backoff with jitter at one layer per operation (AWS Builders'
  Library). The numbers are the SDK's own public promise (`sdk.py:151`), so the docstring becomes
  true rather than edited. Jitter is the documented plus or minus 25 percent, not AWS full
  jitter; a total deadline (120 s, the existing `GCS_RETRY_TOTAL_S` value) bounds the operation
  like tenacity's `stop_after_delay` and google-api-core's deadline.
- **Not tenacity**: the executor is about 90 lines over `time.monotonic` and an injected sleep,
  smaller than a dependency for one call-site family. If the owner prefers tenacity (Apache-2.0),
  only `_retry.py` changes (OQ-4).
- **Resume with a version precondition**: S3 `GetObject` with `Range: bytes=<n>-` and
  `IfMatch: <ETag of the first response>`, the pattern s3transfer uses for resumed downloads. GCS
  reads stay on the library's own per-chunk retry (`BlobReader`); the engine does not wrap them,
  but pins the generation: `BlobReader` sends one ranged GET per chunk with no generation
  (`fileio.py` `read`, google-cloud-storage 3.12), so the engine reloads the blob once and passes
  `if_generation_match` through `Blob.open`'s download kwargs (`VALID_DOWNLOAD_KWARGS`).
- **Digests**: provider checksums on the wire (botocore default CRC32 on `PutObject` and
  `UploadPart`; GCS crc32c on resumable uploads) plus an engine SHA-256 of the consumed bytes, the
  digest MANIFEST and evidence already use (CLI-CLOUD 4.6).
- **SFTP stage then rename**: rclone's partial-name pattern; OpenSSH's link-based rename gives a
  create-only publish, `posix-rename` an atomic replace. Exclusive create (`SFTP_FLAG_EXCL`) is
  the lock, the same primitive as an `O_EXCL` lock file on a local disk.
- **paramiko over asyncssh and fsspec**: paramiko is already the engine's SFTP stack, locked and
  imported by `sftp.py`; asyncssh adds a second stack and an event loop; fsspec adds a layer over
  the same paramiko without the rename primitives this plan needs.

Custom code left: the per-operation retry table, the resume loop, the SFTP pointer swap under the
lock (no SFTP compare-and-swap exists), URI parsing in the CLI. All small.

## 4. Behavior

### 4.1 Retry executor (F02-E1)

`connectors/_retry.py` holds `RetryPolicy` (frozen dataclass: `attempts=3`, `base_s=1.0`,
`factor=2.0`, `jitter=0.25`, `cap_s=20.0`, `deadline_s=120.0`) and `run_retrying(op, *,
policy=DEFAULT_POLICY, sleep=time.sleep, clock=time.monotonic, rand=random.random) -> T`.

- `op` is a zero-argument callable. A `TransientError` (kind `transient`) is retried after
  `min(cap_s, base_s * factor**(n-1)) * (1 + jitter * (2*rand() - 1))` seconds. Any other
  exception, including `PermanentError` and kinds `source_changed`, `host_key_rejected` and
  `digest_mismatch`, leaves at once.
- It stops after `attempts` calls, or when the next sleep would pass `deadline_s` from the first
  call, and re-raises the last `TransientError` object (already value-free, empty chain).
- Each scheduled retry is reported through `get_active_channel().retry_report(RetryInfo(scope=
  "operation", attempt=n+1, retries_completed=n, state="scheduled", delay_s=...),
  operation=<id>)`, and `state="exhausted"` on the last failure. No table name, key or host is
  reported.
- Per-operation attempt floor (E1, `progress.py`). Today `ProgressChannel.retry_report` keeps one
  `_retry_floor` per scope and never resets it (`progress.py:176`, `:315-318`), so after one
  operation reported attempt 3, the next operation's attempt 2 is refused and counted in
  `rejected_reports`. `retry_report` gains a keyword-only `operation: int | None = None`, and the
  floor key becomes `(retry.scope, operation)`. `run_retrying` takes a fresh id from a
  module-level `itertools.count(1)` per call, so each operation starts at floor 1 and attempt
  numbers still never go backwards inside one operation. Existing callers (the governor's
  `route` reports, `execution/_governor.py:348`, `:433`, `:444`) pass no id and keep the key
  `(scope, None)`, so their behavior does not change. The floor map holds one small entry per
  operation that retried at least once in the run; no other state is added. `progress.py` is
  561 lines; the change adds about 6.
- `run_retrying` is the only engine code that sleeps on a connector failure or catches
  `TransientError` to call again (sentry AT-E1-6), apart from the two named state-checked resends
  in guarantee 1. Its callers are pinned by exact `(path, function)` (AT-E1-9), so a new caller
  must add a row to the table below and to the pinned set in the same change. Expected set after
  E5: `(connectors/s3.py, _stream_object)`;
  `(connectors/_sftp_client.py, sftp_stat)`, `(connectors/_sftp_client.py, sftp_listdir)`,
  `(connectors/_sftp_client.py, iter_sftp_file)`, `(connectors/_sftp_client.py, sftp_put_new)`,
  `(connectors/_sftp_client.py, sftp_put_replace)` (seekable sources only). `sftp_session` is
  not in the set: it is the one-shot connect (4.4), and each retried SFTP operation connects
  inside its own attempt, so SFTP retries happen at one layer only (AT-E3-9). The builder records
  the final set; a set that differs from this list is reported, not silently widened.

Per-operation table (written once, in `_retry.py`'s module docstring, and here):

| Operation | Retried by | Why |
|---|---|---|
| S3 ordinary request (head, list page, `get_object` start, unconditional `put_object`, `upload_part`) | botocore standard mode, 2 attempts (unchanged, `_clients.py:295`) | the SDK already retries; a second layer multiplies attempts |
| S3 body read failing mid-stream (classified `transient`) | engine executor, resume from offset with `Range` and `IfMatch`; the resumed `get_object` goes to the single-request client | botocore retries the request, not the body stream; the single-request client keeps the resume at one layer |
| GCS chunk read | google-api-core `Retry` per chunk (unchanged), every chunk with `if_generation_match` | a 412 is not retried by the library and becomes `source_changed` |
| S3 conditional `put_object`, `create_multipart_upload`, `complete_multipart_upload`, `delete_object` with `IfMatch` | never (CLI-CLOUD rule R17, unchanged) | a resend after an applied write turns a win into a loss |
| GCS reads and ordinary writes | google-api-core `Retry` (unchanged) | library-owned |
| GCS conditional writes | never (`retry=None`) | same as S3 |
| SFTP connect | never by itself; `sftp_session` is one-shot, and a connect is retried only as the first step of an attempt of the outer operation below | a retried connect inside a retried operation multiplies attempts (3 x 3) |
| SFTP `stat`, `listdir_attr` (connect included in each attempt) | engine executor, at the operation | read-only |
| SFTP read failing mid-stream | engine executor, reopen and seek to offset while size and mtime match | no SDK retry exists |
| SFTP temporary-file upload from a seekable source | engine executor, whole upload again under a new temporary name | the temporary name is private to the attempt |
| SFTP final rename, lock create, pointer `posix_rename`, delete | never blindly; an unknown rename outcome is resolved by a state check and at most one resend (`_resolve_rename`, 4.4) | not idempotent |
| S3 pointer `put_object` after a 409 | one resend after a re-read shows the version unchanged, in EC3 `ObjectPointerStore` (CLI-CLOUD 4.3 step 8, unchanged by this row) | both racers can get 409 with the pointer unchanged |
| `FileSink.write` from a consumed iterator | never | the chunks cannot be replayed |

### 4.2 Resume and S3 parts (F02-E1; the GCS generation pin is F02-E2)

- `s3._stream_object` (shared by `S3ObjectStore.iter_object` and `S3FileSource.open`) records the
  `ETag` of the first `get_object` response and the bytes yielded so far. A `transient` failure
  inside the body loop closes the body and calls `run_retrying` around a new `get_object` with
  `Range=f"bytes={offset}-"` and `IfMatch=etag`, sent on the single-request client
  (`_build_s3_client(..., single_request=True)`), so the executor is the only retry layer for the
  resume. The first `get_object` stays on the two-attempt client (an ordinary request). The
  stream function therefore takes both clients. A 412 there is kind `source_changed`
  (`PermanentError`). Bytes already yielded are never yielded again.
- `gcs._stream_blob` (shared by `GCSObjectStore.iter_object` and `GCSFileSource.open`; built in
  E2, which already edits `gcs.py` and `_clients.py`, so E1 stays at 6 files) calls
  `gcs_reload(blob)` once, then opens the reader with `if_generation_match=blob.generation`
  through `_clients.gcs_open(blob, "rb", **download_kwargs)`. A 412 on any chunk is kind
  `source_changed`: the read loop maps `precondition_failed` raised inside the loop to
  `source_changed` (the general `_gcs_kind` mapping of 412 stays `precondition_failed` for
  writes). This replaces revision 1's follow-up F02-FU-6.
- `S3ObjectStore.put_new` keeps the single-request client for `create_multipart_upload`,
  `put_object` and `complete_multipart_upload` (the conditional calls) and sends `upload_part`
  through the ordinary two-attempt client (idempotent per part number). `s3_put` is unchanged.

### 4.3 Content digest (F02-E2)

- `WriteResult(path, bytes_written, sha256: str | None = None)`. `None` means "this sink does not
  report a digest" (third-party sinks written against SDK 1.0). Checked on construction: `None`
  or `re.fullmatch(r"[0-9a-f]{64}", value)` on a `str` (a bool, bytes or other type is refused).
- One helper module, `connectors/_digest.py`: `DigestingChunks` wraps a chunk iterator and exposes
  `hexdigest()` and `count` once exhausted; `sha256_hex(data: bytes)` for small payloads (the
  SFTP store's versions and the long-name temp names, 4.4). The hashing runs in
  `DigestingChunks.__iter__`, a generator method whose hasher is a local
  (`h = hashlib.sha256()`, bound once, `h.update(chunk)` per chunk), and stores the hex digest
  and count on the instance when the source is exhausted. The three first-party sinks and the
  SFTP store use these helpers; nothing else in `connectors/` calls `hashlib` (AT-E2-5).
- Outbound sentry and the digest (D11, owner question OQ-10). `update` is in the GCS name set
  that `tests/sentry/test_outbound_clients.py` derives from google-cloud-storage, so `h.update(`
  is a collision the walk counts. On main the walk's `seen` is 146 and `WALK_FLOOR` is 146; the
  baseline `gcs-call-kwargs.json` has 146 rows, and `scripts/dev/ratchet_check.py` fails on any
  added key (only `validation-name-messages` may re-key, only `secret-material-census` may
  re-home, `tests/sentry/_ratchet.py:35-39`). No existing helper can take the call: the one
  baselined streaming SHA-256 update is a private method of the quarantine sink
  (`declared_casting/_quarantine_local.py::LocalProtectedQuarantineSink._append_chunk`), not a
  reusable helper, and moving it would add a key too. A `.update` call on an incremental hasher
  cannot be avoided (`hashlib.file_digest` is Python 3.11+, the engine supports 3.10). So the
  plan takes no new row by default: OQ-10 option (b), recommended, makes AT-C10 skip a call
  whose receiver is a local name bound exactly once in the same function from a `hashlib` or
  `hmac` constructor (still counted in `seen`, never a finding). That removes the
  false positive at its source and lets 9 existing rows go (`_activation.py` 2, `_inputs.py` 2,
  `_shadow_snapshot.py` 5, each `digest = hashlib.sha256()` then `digest.update(...)`). Option (a)
  is one new row, which needs an owner exception to the ratchet. Never allowed: a bound method
  stored in a variable, `getattr`, or placing the hasher in `_clients.py` (the walk skips the
  factory module), each of which hides the call from the sentry instead of proving it is not
  GCS. E2 does not start before OQ-10 is answered.
- Provider checks: `_S3_KINDS` maps `BadDigest`, `InvalidDigest` and `XAmzContentSHA256Mismatch`
  to `digest_mismatch`; `_s3_kind` maps botocore `FlexibleChecksumError` to `digest_mismatch`;
  `_gcs_kind` maps the library's `DataCorruption` to `digest_mismatch`. All are `PermanentError`.
  On S3 a failed checksum creates no object (the request is rejected).
- GCS is different. `_validate_checksum` runs on the response that finalized the resumable
  session (`_media/_upload.py:785-812`, google-cloud-storage 3.12), so the object is already live
  when `DataCorruption` is raised. `Blob._do_resumable_upload` deletes it (`blob.py` around line
  2464), but the `Blob.open("wb")` writer (`fileio.py` `BlobWriter`) does not. The cleanup cannot
  sit in `GCSFileSink.write`: the sink writes through `_clients.gcs_open`, which returns
  `_TranslatingFile` (`_clients.py:206-229`), and its `close` and `__exit__` run `_guard`, so
  `gcs_error` turns the `DataCorruption` into a plain classified error and drops the original
  (and its response) before the sink sees it. So the cleanup lives in `_clients.py`:
  `gcs_open(blob, mode, **kwargs)` passes `blob` to the wrapper, and the wrapper's `close` and
  `__exit__` (the calls that send the finalizing request) go through one private `_finish`
  (write mode only; a read wrapper has no cleanup). On a
  `DataCorruption` it reads `exc.response.json()["generation"]` inside the handler and accepts it
  only when it is a `str` (not `bool`, `int` or `float`) that fully matches `[1-9][0-9]{0,18}` (at most
  19 digits, the int64 range GCS uses)
  (`re.fullmatch`, no sign, no whitespace, no leading zero), then converts it with `int`; any other
  shape counts as "no generation could be read" (the JSON API sends the generation as a
  decimal string), then, after the handler closes, calls
  `gcs_delete_generation(blob, generation)` (`blob.delete(if_generation_match=generation,
  timeout=GCS_TIMEOUT, retry=None)`, one attempt) and raises
  `PermanentError("GCS content check failed", kind="digest_mismatch", cleanup_ok=...)`:
  `True` when the delete returned, `False` when it failed or no generation could be read (no
  response, no `generation` key, a value `int()` refuses). No exception chaining: the error is
  built and raised outside every handler. The delete is conditional, so it never removes a newer
  object written by someone else. `GCSFileSink.write` does not change for this; it gets the
  error from the wrapper. `_clients.py` is the factory module the outbound walk skips, and both
  calls are GCS calls with `timeout=` and `retry=`, so no baseline row moves.
- `ConnectorError` gains `cleanup_ok: bool | None = None` in this slice (it was E3 in revision
  1), because the GCS sink is its first user. `errors.py` is at 600 lines with no census entry
  (`tests/sentry/test_module_size.py` goal); E2 keeps it at 600 or fewer by shortening an existing
  docstring in the same module, never by adding a census line.
- `SDK_VERSION` moves from `"1.0"` to `"1.1"` (additive field; OQ-5). Its docstring
  (`sdk.py:63`) says "Bumped on breaking changes"; E2 rewrites it to "major on a breaking change,
  minor on an additive one" so the bump matches the text.

### 4.4 SFTP (F02-E3, F02-E4, F02-E5)

**Session factory** (`connectors/_sftp_client.py`, E3). `sftp_session(params: SftpParams) ->
SftpSession` is the only place that builds a `paramiko.SSHClient`. It is one-shot: one connect
attempt, no executor. Cleanup (staging step 5), `_resolve_rename` (step 6) and the store's
reconnect call it directly. The retried operations (`sftp_stat`, `sftp_listdir`,
`iter_sftp_file`'s resume, the seekable `sftp_put_new` and `sftp_put_replace`) call
`run_retrying` once, around an attempt that first connects through `sftp_session` when it holds
no live session; so a black-holed host costs exactly `attempts` connects per operation. `SftpParams` is a frozen
dataclass: host, port, username, identity_file, known_hosts, plus the SDK's optional `SecretStr`
password and private key. It is exported from `decoy_engine.connectors` (`connectors/__init__.py`
and its `__all__`, E3), so the CLI imports the public name, never `_sftp_client` (recurring-defect
class 6). Its `__repr__` is value-free: `SftpParams(<redacted>)`, with no host, port, user, path or
secret (`dataclass(repr=False)` plus a fixed `__repr__`); AT-E3-8 pins it.

- Host keys: a private `_StrictHostKeys(paramiko.RejectPolicy)` subclass whose
  `missing_host_key` raises a private `_UnknownHostKey(paramiko.SSHException)` with no message.
  Plain `RejectPolicy` raises a bare `SSHException` carrying the host name, which `sftp_error`
  could only tell apart from other `SSHException`s by text; the private type lets it classify by
  exact type. Keys come from `params.known_hosts` if set, else `DECOY_SFTP_KNOWN_HOSTS`
  (existing, `sftp.py:139`), else `~/.ssh/known_hosts`. The file is loaded only when
  `os.path.isfile(path)` is true (today `os.path.exists`, `sftp.py:142`); `exists` is in the
  outbound sentry's GCS name set and `isfile` is not, and `isfile` is also the right test (a
  directory is not a key file). A missing file, or a directory, means no key is known, so every
  host is refused with `host_key_rejected` (fail closed, as today).
- paramiko logs to its own `paramiko` logger (transport and auth messages, which can name the
  remote version and auth methods). The engine attaches no handler and does not forward that
  logger anywhere. The CLI must not route it into the run log, `--json` output or evidence; C1
  confirms on the CLI head which loggers the CLI's handlers accept and adds AT-C1-6.
- Bounds: `timeout=15`, `banner_timeout=15`, `auth_timeout=15`, `channel_timeout=60`, and
  `sftp.get_channel().settimeout(60)` so a black-holed server ends a read inside a bound.
- Auth, in order: the SDK `private_key` and `password` (kept for SDK users, never set by the CLI);
  `identity_file` (a path, read by paramiko); the agent and default key files (`allow_agent=True`,
  `look_for_keys=True`). Key parsing tries Ed25519, ECDSA, RSA; DSS is removed.
- `sftp_error(exc) -> ConnectorError` classifies by exact type with fixed words from the shared
  `_PHRASE` table: `BadHostKeyException` and `_UnknownHostKey` give `host_key_rejected`; `BadAuthenticationType`, `AuthenticationException`,
  `PasswordRequiredException` give `credentials`; `ENOENT` gives `not_found`; `EACCES` and
  `PermissionError` give `access_denied`; `EEXIST` gives `precondition_failed`; `socket.timeout`,
  `EOFError`, `ConnectionResetError`, other `SSHException` and other `OSError` give `transient`;
  anything else `unexpected`. Every SFTP raise follows `_clients._call` (raise after the handler
  closes), so `__cause__` and `__context__` are `None`.
- `SFTPConfig` drops `_require_at_least_one_auth` (`sftp.py:110`) and gains `identity_file` and
  `known_hosts`, both `str | None`. Public SDK names stay.

**One SFTP staging core** (E4). In `_sftp_client.py`: a private `_stage(sftp, final, source) ->
(tmp, count, sha256)` and two public entry points that differ only in the rename primitive:
`sftp_put_replace` (SDK sink, `posix_rename`) and `sftp_put_new` (delivery store, plain rename,
create-only on OpenSSH). Two named functions instead of one flag argument (house style).

Every SFTP file open (read, staging write, lock create, `read_small`) goes through one private
`_sftp_open(sftp, path, mode)` (E3), which calls `sftp.file(path, mode)`. paramiko defines
`SFTPClient.file = open` (`sftp_client.py:385`, paramiko 5.0.0), so the behavior is the same
function. The `file` spelling is used because `open` is in the outbound sentry's GCS name set
and `file` is not: the call is a paramiko call, never a GCS one (a GCS `Blob` has no `file`
method), so it should not be a collision row. The open-mode sentry (AT-E4-7) watches both
spellings, so the SFTP open choke point stays guarded.

1. `tmp = f"{dirname(final)}/.{stem}.decoy-part-{token_hex(8)}"`, where `stem` is
   `basename(final)` when its UTF-8 length is 200 bytes or less, else the first 32 hex characters
   of `sha256_hex(basename(final).encode())`. The added parts are 29 bytes, so the temp name
   stays within the 255-byte `NAME_MAX` of common servers for any final name that fits there.
   Opened with mode `"xb"` (exclusive create) through `_sftp_open`.
2. Write the chunks through `DigestingChunks`; close.
3. `stat(tmp).st_size == count`, else remove `tmp` and raise `digest_mismatch`.
4. Rename (`posix_rename` or `rename`). For `sftp_put_new`, OpenSSH refuses a present target
   (`EEXIST`, or a generic failure after which `stat` shows the target present): mapped to
   `precondition_failed`.
5. Any failure before step 4 removes `tmp` best effort and sets `cleanup_ok` (a bool, never text)
   on the raised error (`ConnectorError.cleanup_ok`, added in E2). When the failure was a
   dropped transport, the removal first opens a new session through `sftp_session` (one
   attempt, no executor); a removal that cannot reconnect gives `cleanup_ok=False`.
6. A connection drop during the rename call is resolved in `_resolve_rename` after reconnecting
   through `sftp_session`: it stats `tmp`, then `final`. An `ENOENT` from either stat means
   "absent", not an error. `tmp` present means the rename did not happen: resend the rename once
   (the named resend of guarantee 1). `tmp` absent and `final` present with size `count` means it
   did. Anything else (both absent, `final` with another size, or a stat that fails with anything
   but `ENOENT`) is `unexpected` with `cleanup_ok=None`. The random token makes `tmp` private to
   the attempt, so "absent" can only mean "renamed by us" under the accidental threat model.

With a seekable source, steps 1 to 3 run inside `run_retrying` (each attempt reconnects through
the one-shot `sftp_session` if the previous attempt dropped the transport, seeks to 0 and uses a
new token). With an iterator source (the SDK `FileSink.write`), they run once.

`SFTPFileSink.write` becomes `sftp_put_replace(...)` and returns `WriteResult(path, count,
sha256)`. `SFTPFileSource.open`, `list` and `head` go through the session factory, the executor
and the resume rule in `iter_sftp_file`: size and mtime from the first `stat`; on a dropped
transport it reconnects, re-stats and compares before reopening. A difference, or `ENOENT` on the
re-stat (the file was removed), is `source_changed`, never `not_found` and never retried. SFTP v3
`mtime` has 1 s granularity (uint32 seconds), so a same-size rewrite inside the same second as
the first `stat` is not detected; accepted under the accidental threat model and stated in the
user docs.

**Config and store** (E5).

- `SFTPSource` (`type: sftp`, `format: csv | parquet`, `host`, `port=22`, `username`, `path`
  (absolute), `identity_file: str | None`, `known_hosts: str | None`; `extra="forbid"`,
  `hide_input_in_errors=True`, `StrictInt` port in 1 to 65535). `host`, `port`, `username`,
  `identity_file` and `known_hosts` carry `x-decoy-locator`; `path` carries `x-decoy-path`, so
  the existing record reduction covers them. `host` is a hostname or IP literal checked with
  `fullmatch` (no `@`, `/`, whitespace or control characters; IPv6 only in brackets); `username`
  is `fullmatch(r"[A-Za-z0-9._-]{1,64}")`; `path` is absolute, with no `..` segment and no
  control characters. No password or key field exists, so a secret cannot be written into a
  pipeline file (refused as an extra field, naming the field, not the value).
- `SFTPTarget`, the same fields; its identity for the duplicate-destination rule is `("sftp",
  host, port, username, path)`.
- `SftpObjectStore(params)` implements `ObjectStore`. It holds one session and replaces it
  through `sftp_session` whenever an operation finds the transport dropped (paramiko's
  `Transport.is_active()` false, or an `EOFError` or `socket` error on the channel), so cleanup
  and state checks after a drop never run on a dead channel. It keeps a private record of the
  objects it created in this process: `{key: (version, size)}`.
  - `put_new(key, fd)`: `sftp_put_new` under `run_retrying` (seekable `fd`); the version is the
    SHA-256 hex of the bytes; the key, version and size go into the record.
  - `read_small(key, limit)`: bounded read; `None` when absent; `pointer_invalid` past `limit`;
    version is `sha256_hex` of the bytes read.
  - `put_if(key, data, expected)`: create `<dirname(key)>/.decoy-lock` with mode `"xb"` (present:
    return `"conflict"`); re-read `key`; version differs from `expected` (or present when
    `expected is None`): remove the lock, return `"rejected"`; else `sftp_put_replace`, remove
    the lock, return `"won"`. A connection drop after the rename request returns `"unknown"`,
    which DELIV's W6 rule already handles. After any drop the store reconnects before it tries
    to remove the lock. A lock that cannot be removed (reconnect failed or remove failed) does not
    change the `PutResult`; it emits the warning code `sftp_lock_not_removed` (new, warning
    namespace, since=UNRELEASED) through `get_active_channel().warning(...)` with no table, path
    or host, so the next run's `conflict` has a recorded cause and the docs name the manual
    removal (OQ-9). On an error path it also sets `cleanup_ok=False`.
  - `delete_created(key, version)`: delete only when the record holds `key` with that `version`
    and a `stat` of `key` shows the recorded size; otherwise do nothing. No read-back: the
    record proves this process created the object, and the size check catches a replacement in
    the accidental model without downloading the file. The S3 store uses `IfMatch` for the same
    rule; SFTP has no conditional delete.
  - `iter_object(key)`: the resume-aware read loop.
  - `check_region()`: no-op.
- `DELIVERABLE_TARGET_TYPES` gains `"sftp"` (`delivery/_plan.py:24`).
- Lock exception to CLI-CLOUD: CLI-CLOUD 4.3 says "The object store takes no backend lock"
  (S3 and GCS have conditional writes). `SftpObjectStore.put_if` is the one store that takes a
  backend lock, because SFTP has no compare-and-swap; the CLI-side local lock (DELIV 4.5) is still
  taken first and unchanged. The matching sentence in the CLI-CLOUD plan is follow-up F02-FU-7.

(`ObjectStore.size(key) -> int`, new in E1 for S3 `head_object` and GCS `reload`, in E5 for SFTP

the same reason; the CLI reuses that predicate and keeps no errno list of its own. Both exit 3.

Why a new code and not `decoy.storage_capacity_exhausted` (Dennis round 2, M-d): that code is
registered with `outcome=Outcome.PUBLICATION` and the text "The output storage ran out of space
or quota." (`reasons/decoy/_core.py:69-74`), and `reason_adapter` emits it only for a publishing
phase (`reason_adapter.py:255-257`). A spool is input staging before any output exists, so the
record would name the wrong outcome and the wrong storage. One code covers both spool cases (the
bound and a mid-write `ENOSPC` or `EDQUOT`), because the user's fix is the same. It joins
`CAPACITY_EXCLUSIONS` under `_DISK` ("disk or quota, not memory", `errors.py:556` neighbors) in
E6, so the capacity table states that it is not a memory refusal and exit 5 never maps it.

### 4.8 Errors in the CLI

## 6. Design notes and choke points

Principles applied, each against a concrete change pain:

- **One owner per concern** (single responsibility; cross-cutting choke points). Retry policy:
  `_retry.py` only. SFTP client construction and classification: `_sftp_client.py` only. SFTP
  writes: the staging core only. Remote store selection in the CLI: one `type -> store` table in
  `C:cli/io/_cloud.py`. Pain removed: today each SFTP call site builds its own client and wraps
  its own errors, which is how the value leak and the DSS break went unnoticed.
- **Protocol reuse over a new route** (Liskov). SFTP delivery is one more `ObjectStore`
  implementation behind CLI-CLOUD's delivery kind; it must honor `PutResult` meanings exactly
  (AT-E5-4). No SFTP-specific delivery code exists.
- **Typed context**: `SftpParams` instead of long parameter lists; two named put functions
  instead of a `replace` flag.
- No new abstraction with one implementation: the store protocol already has two.

Choke points:

## 7. Value-free rules

- Connector error text is `"<Provider> <fixed phrase>"` from `_PHRASE`. New phrases:
  `source_changed` "object changed during read", `digest_mismatch` "content check failed",
  `host_key_rejected` "host key not trusted". The provider word for SFTP is `SFTP`.
- `CheckResult.detail` for SFTP is the fixed error text.
- `ConnectorError.cleanup_ok` is a bool or `None`.
- `SftpParams.__repr__` is the fixed text `SftpParams(<redacted>)`; the dataclass default repr is
  off.
- The warning `sftp_lock_not_removed` carries no table, path, host or user.
- paramiko's own logger is not forwarded by the engine or the CLI (4.4).
- Retry reports carry counts and seconds only.
- CLI output names tables, basenames, kinds and codes; never a bucket, host, user, port, key
  path, `known_hosts` path or remote path.
- No new log line prints a descriptor; the existing locator reduction covers records.

## 14. Enumerations

### Exit paths

- `run_retrying`: success; non-transient raise at once; exhausted by attempts; exhausted by deadline (`connectors/_retry.py`, new).
- Staging core: success; failure before the rename with `cleanup_ok` true or false (reconnect first after a drop); size mismatch; rename refused; rename outcome unknown, resolved by `_resolve_rename` three ways (4.4).
- GCS write wrapper (`_clients._TranslatingFile`, `close` or `__exit__`) on `DataCorruption`: `digest_mismatch` with `cleanup_ok` true (generation delete returned) or false (delete failed or no readable generation).
- `spool_source`: success; refused before download by the size bound; `ENOSPC` or `EDQUOT` mid-write (`is_capacity_oserror`); a connector error.
- `SftpObjectStore.put_if`: `won`, `rejected`, `conflict`, `unknown` (the `PutResult` literal, `connectors/object_store.py:45`).

- `decoy run` with remote sources: spool, then the resident loader (CLI-CLOUD CC3).

- `decoy subset` with remote sources: spool, then `subset_inputs_from_config` with copies (`subset/_api.py:365`).

- N/A for new behavior: no FK logic changes. Subset closure runs unchanged over spooled copies, so every FK shape the subset supports on local Parquet today is covered by AT-C3-1's local-copy equality, and every shape it refuses stays refused.

## 17. Owner questions

- **OQ-1. paramiko in the CLI distribution (new runtime dependency for the CLI).** paramiko is
  already an optional engine extra (locked 5.0.0, licence LGPL-2.1) and pulls `bcrypt`, `invoke`
  and `pynacl` (`cryptography` is already a base dependency). The engine licence policy accepts
  paramiko only behind the `sftp` extra (`tests/sentry/test_license_policy.py:144`, a `runtime`
  paramiko entry is a violation). The CLI has no licence gate: `scripts/release/sbom_checks.py`
  checks the pin grammar, hashes and that the SBOM lists exactly the pins, nothing about
  licences. So under option (a) no check anywhere looks at the LGPL package in the CLI bundle
  or image; the engine policy would not see it either, because there it stays behind the extra.
  Option (a) therefore needs either an owner sign-off recorded with the licence review or a new
  CLI licence check (not in this plan). Only C1 and C4 depend on this answer. Three options:
  - **(a) paramiko extra in the CLI, included in `all`, the signed bundle and the image.** SFTP
    works from the download. Costs: an LGPL package ships in the bundle and image (owner to
    confirm against the FSL licence review); every `all`, bundle and image install gains four
    distributions, and the engine DP gate fingerprints every installed distribution, so DP fits
    in those installs lose certification until the certified rows are re-pinned (the reason the
    CLI keeps `otel` out of `all`, CLI `pyproject.toml`); a re-pin of the certified rows rides
    with RD-n.
  - **(b) opt-in `decoy-cli[sftp]`, left out of `all`, the signed bundle and the image.**
    Recommended. Same code as (a). Costs: SFTP users run `pip install "decoy-cli[sftp]"`; a bundle
    or image user who names an `sftp` source or target gets the existing missing-extra message
    (`require_extra`) with that install line; DP fits in an environment with the extra installed
    are uncertified, as with `otel`, and the docs say so. Nothing in the default distributions
    changes, so no certified row, bundle manifest or image moves. Reason for recommending it: it
    follows the `otel` precedent exactly and keeps the LGPL and DP questions off the default
    install, while keeping one SSH stack (the engine's).
  - **(c) system OpenSSH `sftp -b` batch mode, no new Python dependency.** Uses the user's
    `~/.ssh/config`, agent and `known_hosts` natively. Costs beyond revision 1's list (parsing
    `sftp` output, no resume, weaker error classification, a hard need for an installed `sftp`
    binary): (1) batch mode has no exclusive create, so neither the staging core nor the lock can
    be built, so no SFTP targets (C4 and E5's store half drop); (2) `sftp`'s stderr names hosts,
    users and paths, so a value-free capture rule is needed: stderr is never printed or logged,
    only the exit status maps to a kind, and a sentry pins it; (3) the CLI must force
    `-o StrictHostKeyChecking=yes -o BatchMode=yes` on every call, so a user's `~/.ssh/config`
    with `accept-new` or a password prompt cannot weaken host-key checking or hang a run; (4) the
    engine's `SftpObjectStore` and SFTP read path go unused by the CLI, so E5's store half and
    E4's resume read have no CLI consumer (they still serve SDK users).
- **OQ-2. SFTP authentication in V1.** Recommended: SSH agent, a referenced `identity_file` path
  and the default key files; strict `known_hosts` only; no password and no key text in pipeline
  files; encrypted key files only through the agent. Alternative: also accept a password from an
  environment variable named in the config (`password_env:`), which keeps secrets out of files

- **OQ-3. Cloud scan input form and method.** Recommended: positional URIs (`s3://`, `gs://`,
  `sftp://`, the aws-cli, gsutil and rclone convention), each spooled whole before scanning, so a

  alternative is tenacity (Apache-2.0, new dependency) instead of the 90-line executor;
  recommended no.
- **OQ-5. `SDK_VERSION` 1.0 to 1.1 for the additive `WriteResult.sha256`.** Recommended: yes, so

- **OQ-6. SFTP integrity check.** Recommended: size check after upload and the SHA-256 of the

    false-positive class stays.

    local name bound exactly once, in the same function, from `hashlib.<constructor>(...)` or

    constructor, outer function, attribute receiver, a real `blob.update()`) stay findings

    shared sentry, reviewed with E2; a hashlib call through an attribute receiver
    (`self.h.update`, the quarantine sink) still needs its row. Reason for recommending it: it

    adding to a shrink-only list, which is the house rule for a class of finding.

    stored bound method, or `getattr`. Each hides the call from the sentry rather than proving it
    is not a GCS call.
- **OQ-9. Stale SFTP lock after a killed run.** Recommended: refuse (`conflict`, exit 3) and
  document manual removal of `<dir>/<pipeline>/.decoy-lock`; no automatic expiry in V1, because
  a time-based expiry can break a slow live writer. Alternative: a lock that records a run id and
  creation time and is broken after a configured age.

## 18. Pre-mortem

- **"The retry executor double-retried and stalled runs for minutes."** Prevented by the
  one-layer table, the client split (AT-E1-7) and the deadline (AT-E1-4).
- **"An SFTP target got half a file."** Prevented by the staging core and the open-mode sentry
  (AT-E4-1, AT-E4-7).
- **"A customer's SFTP server refuses rename."** Some managed SFTP services refuse or emulate
  rename (rclone forum reports). The run fails with a classified error and no partial target; the
  docs list OpenSSH-compatible servers as supported. No in-place fallback.
- **"Scan of a 40 GB object filled the disk."** The spool bound refuses it before the first byte
  (`runtime.spool_disk_full`, exit 3); a disk filled by another process mid-write gives the same
  reason. The docs say remote scan downloads the object; a configurable spool cap stays a
  CLI-CLOUD V2-LOG line.
- **"paramiko changed its API again."** The `sftp-gate` job runs the SFTP tests with
  `DECOY_REQUIRE_SFTP=1`, so a lock bump that breaks SFTP turns CI red (AT-E3-7).
- **"Adding the SFTP lane decertified DP on the gate hosts."** The lane is its own CI job and its
