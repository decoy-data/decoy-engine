Rev 8.6 G1 to G6 carry unchanged. After the last slice here (S4b) merges:

- R1. `SCRATCH_NATIVE_PENDING` is empty. Every DuckDB connection call, Arrow or Parquet scratch read and footer read in an engine module runs through `scratch_native`, `scratch_native_iter` or an adapter, so a native failure leaves the boundary as a value-free error (rev 8.6 G6).
- R2. - R5. No scratch cleanup in the converted code swallows a failure. A child that cannot be removed is reported `RETAINED` through the sink in section 3.0, never ignored.

Non-goals: at-rest encryption (V2-LOG; criterion (d) records it); the sweep (row 74); byte quotas (row 58b); same-UID interference (rev 8.6 L6); Windows arenas before S1w (section 9.2).

### 3.0 Three shared pieces

Recursive child removal. `ScratchArena.remove` (`fileaccess/_scratch.py:309-323`) unlinks a file or calls `rmdir` on an empty directory; it is not recursive. The converted cleanups remove whole trees. New `ScratchArena.remove_tree(component) -> CleanupReport`: open the child by descriptor with no-follow (as `remove` already checks it at :319), clear it with `_rmtree_fd` (`fileaccess/_fdtree.py:127`, already imported at `fileaccess/_scratch.py:32` and used by `_reclaim` at :131), then `rmdir` the name. It never raises `OSError`: a failure returns `CleanupReport(disposition=Disposition.RETAINED)`, success returns `REMOVED`. It lands in S2a-1c-ii-a, its first user. It does not follow a symlinked child (a planted link is removed as a link, its target untouched).

The `RETAINED` sink. Every converted tree in section 3 lives inside an arena whose opener reclaims it at the end (the runner arena, `execution/out_of_core/_runner.py:249-252`, or a G6-2 stage scope). So an early `remove_tree` that fails is not a leak by itself: the opener's `reclaim()` retries the whole tree. The sink is that final report. Today the runner drops it (`owned.reclaim()` at `_runner.py:387`, "a failure reports RETAINED; the run's own outcome stands"). After S2b-1, the runner keeps the report and, when it is `RETAINED`, appends a value-free `QualityWarning(code="scratch_retained")` to the run's `warnings` list (`_runner.py:259`), which already reaches the result (`_runner.py:366`, :372). The warning holds the disposition only: no path, no size, no name. For a handed arena, the opener (a G6-2 stage scope) owns the report; S3b names the snapshot's sink. `CleanupReport` and the result types do not change.

The stage-child contract. G6-2's `stage_scratch()` yields a `ScratchArena` on POSIX and, on win32, the fallback in `fileaccess/_scratch_win32.py` (G6/G7 plan B3a), which is not a `ScratchArena`. `scratch_arena()` (`execution/out_of_core/_scratch.py:62-66`) would send that fallback, or its path, to `_adopt`, which opens with `_osflags.DIRECTORY`; that flag is 0 on Windows (`fileaccess/_osflags.py:26-31`, :51), and `os.open` on a directory does not work there. So a stage child cannot reach `connect_duckdb` on win32 today. This plan adds a `StageDir` protocol in fa `_scratch.py`: `local_path()`, `create_dir(component) -> StageDir`, `remove_tree(component) -> CleanupReport` and `reader()`. `ScratchArena` satisfies it as is (plus `remove_tree`); the win32 fallback must satisfy it too. Until S1w:

- `connect_duckdb(temp_dir=)` accepts `ScratchArena | StageDir | Path`; `scratch_arena()` returns any `StageDir` unchanged (the connection reads only `local_path()`), and only a bare `Path` goes to `_adopt`. S4b drops `Path`; S1w folds the fallback into `ScratchArena` and drops `StageDir` from the annotations.
- `key_facts(scratch=)` and `column_distinct(scratch=)` accept `StageDir | Path` after S2a-1c-iii-a and `StageDir` only after S2a-1c-iii-b.

If G6-2 merges before S2a-1c-iii-a with a fallback that lacks one of the four methods, S2a-1c-iii-a adds it to `_scratch_win32.py`. The G6-2 builder is told about the protocol through the orchestrator so the gap is closed once.

### 9.4 Choke point

The rule "every native scratch call is value-free" is enforced by construction at `scratch_native` (`fileaccess/_scratch.py:409`). The guard is the derived-membership sentry in `tests/sentry/test_file_access_boundary.py`, which walks the AST of every engine module for DuckDB connection calls and scratch reads, and fails on any call outside `scratch_native` in a module not in `SCRATCH_NATIVE_PENDING`. The allowlist is that set: 13 names now, a ratchet (`test_pending_set_only_shrinks`), zero after S4b-0. Mutation: M-3 (unwrap one call; the sentry fails).

Its guard is a seeded check added in S2b-1 to the existing scratch sentry: no `shutil.rmtree(..., ignore_errors=True)` under `execution/out_of_core/` or `connectors/` (allowlist empty after S3b; S2b-1 lists `postgres_snapshot.py:430` as the one entry, S3b removes it). ## 10. Design notes, established solutions, placement
