## 0. What row 81 adds, and what it does not

Nothing of row 81 is merged. Today:

- A disguise is a YAML bundle (`src/decoy_engine/disguises/schema.py:45`, `FieldRule`: `detectors`,
  `mask`, `params`, `why`, first match wins). Nothing in the engine applies one to a config. The only
  consumers are `load_disguises` readers: CLI `list disguises`, tab completion, the platform router,
  and the platform web `MaskInspector`, which applies rules in the browser.
- The bundle vocabulary is not the pipeline vocabulary. A rule says `mask: faker` with
  `params.faker_type: email`, or `date_shift` with `jitter_days: 30`. A pipeline column says
  `strategy: faker`, `provider: person_email`, or `provider_config: {min_days: -30, max_days: 30}`.
  The CLI keeps a hand-written map between the two in `tests/unit/test_template_disguise_drift.py`.
- Four shipped rules cannot run at all: `faker_type: ipv4` in `hipaa`, `gdpr` and `ccpa` (no ipv4
  provider; the CLI templates already substitute `redact`) and `faker_type: zipcode` in `default`
  (the provider is `address_zip`).
- Several rule `why` texts promise "deterministic" fakes or joins that survive (for example
  `default.yaml:36`, `cpni.yaml:171`, `glba.yaml:51`). A bundle rule has no `deterministic` field
  today, so a faker rule applied as written would be random per run.
- CONFIG-EXPLICIT (row 22, done) makes every source column a declared `columns:` entry with a
  `strategy`. So the set of fields is known from the config alone, with no source read.

Row 81 adds four things:

1. **Disguises applied in the engine.** Bundle rules are rewritten in the pipeline column
   vocabulary (new dated versions), including `deterministic` and `allow_collisions`, and a
   pipeline names a disguise and a version. A column that the user classifies
   (`classification: email`, the PII type the user picks, per the presets decision) gets that
   disguise's rule. The engine does it inside the one validation choke point, so every caller sees
   an explicit config.
2. **Selector grammar.** One closed, bounded selector over table and column names (globs),
   classification, tag, declared logical type and relationship role.
3. **Prohibition predicates.** `forbid` or `require` a strategy set on selected fields. They are
   checked after expansion against every field, explicit ones included. A violation refuses the
   config and names the prohibition id.
4. **5-level precedence** with a per-field explanation and fingerprint: exact field, exact
   object or classification, scoped pattern, classification default (the disguise), global
   default.

## 1. Guarantee

- A config with no `policy` block, no `classification` and no `tags` validates, dumps, hashes and
  masks exactly as on today's main (same `model_dump()`, same plan hash, same output bytes).
- With a `policy` block, `PipelineConfig.model_validate(raw).model_dump()` is an explicit config:
  every mask column carries the `strategy`, `provider`, `provider_config`, `namespace`,
  `deterministic` and `allow_collisions` the precedence decided. Nothing downstream of the choke
  point knows a policy existed.
- `classification` and `tags` are labels on mask columns. Adding them to an explicit mask column
  never changes output bytes.
- The decision for each mask field is the highest-precedence level that matches it (section 3.3).
  Two different decisions at the same level refuse the config with `config.policy_rule_conflict`
  naming both sources. Decisions are compared after normalizing to `ColumnConfig` defaults, so a
  rule that omits a key equals one that writes the default. A rule that selects no field refuses
  with `config.policy_selector_unmatched`. A mask field with no decision at any level refuses with
  `config.policy_field_undecided`. Nothing falls back to passthrough.
- A prohibition violated by any decided field, explicit or expanded, refuses the config with
  `config.policy_prohibited`, naming the prohibition id, the `table.column` and the strategy.
- The disguise pin is exact: `policy.disguise.version` must equal the shipped bundle's `version`,
  or the config is refused with `config.policy_disguise_version_mismatch`.
- Every shipped disguise rule, applied to a column, compiles and masks a small frame. Every rule
  that is deterministic (by `deterministic: true`, or a keyed strategy: `hash`, `fpe`, `tokenize`)
  gives the same output for the same input across two runs with the same key, and no `why` text
  claims determinism or join survival for a rule that does not have it.
- Validation is idempotent: validating the dump of a validated config gives the same dump. The
  caller's input dict is never changed.
- `PipelineConfig.policy_expansion` explains the expansion of the input it was validated from. It
  gives, per mask field, the decision, its level, its source (column, rule id,
  `disguise id@version`, or default), the rule ids it overrode, and a decision digest, plus one
  fingerprint over all fields. After a round trip, every field reads as level 1 (column) with the
  same decisions and the same fingerprint.
- No cell value is read. Refusals and the explanation carry config identifiers only (section 3.9).

## 2. Established solutions

Search run (2026-11-17): web search for Delphix masking domain default algorithms and column
override, and for AWS Lake Formation LF-tag expressions; codebase search
`git grep -n -i "disguise|field_rules|selector|precedence|prohibit"` over engine `src/`, CLI
`src/` and platform `api/` and `web/src`; the vault (`qmd search "F16 selector precedence"`,
`qmd vsearch "selector grammar prohibition predicates precedence disguises"`).

Found:

- **Classification default with column override.** Delphix assigns each inventory column a domain.
  The domain's default algorithm fills the column and follows later default changes; an algorithm
  picked on the column is an override that does not follow them
  ([Delphix ruleset docs](https://dcs.delphix.com/docs/latest/customize-a-ruleset)). This is level
  4 (disguise rule for the classification) under level 1 (the column's own strategy).
- **Bounded tag expressions.** AWS Lake Formation LF-tag expressions AND across keys and OR within
  one key's values, with fixed limits on keys and values
  ([LF-tag expressions](https://docs.aws.amazon.com/en_us/lake-formation/latest/dg/TBAC-creating-tag-expressions.html)).
  Kubernetes `matchLabels` has the same form. The selector follows it: keys AND, list values OR,
  no negation, no nesting.
- **Specificity precedence.** CSS specificity and dbt's config hierarchy (in-model config over
  path-scoped project config over project defaults) pick the more specific source. Both break a
  tie at equal specificity by order. The F16 spec says conflicts fail compilation, so a tie here
  is refused instead.
- **Deny after resolution.** OPA Gatekeeper and Kyverno `validate` rules run on the resolved
  object and name the policy that denied it. Prohibitions run after expansion and name their id.
- **Globs.** Python `fnmatch.fnmatchcase`: case-sensitive and anchored (it compiles to a regex
  ending in `\Z`), so it meets recurring defect 1 with no hand-written matcher.
- **Digests.** `decoy_engine._canonical.canonical_json_bytes` is the one canonical JSON form, and
  SHA-256 over it is how records and F22 descriptors are identified.
- **In the code.** `registered_detector_ids()` (`src/decoy_engine/detection/domains.py:87`) is the
  closed classification vocabulary; every detector id the ten bundles use is in it (checked
  2026-11-17). `contracts/distribution_behavior.py` keys every mask strategy. `problem_details`
  (`config/_generate_options.py`) reports many config problems at once at their locations. The
  F06 `LOGICAL_TYPES` tuple (`config/_declared_casting.py:24`) is the logical type vocabulary.
  Faker locale is a `provider_config` key (`generation/pool/_identity.py:57`).

Choice: the precedence and selector semantics above; one engine expansion run inside
`PipelineConfig` validation; bundle rules rewritten in the column vocabulary so a rule is a
column decision and no translation table exists. The custom code is the expansion itself (about
250 lines); no library offers it for this config shape.

## 3. Behaviour

### 3.1 Config surface

```yaml
version: 2
policy:
  disguise: {id: hipaa, version: "2026-11-20"}   # optional; pin required when present
  rules:                                          # optional
    - id: visit-dates
      select: {table: visits, column: "*_date"}
      strategy: date_shift
      namespace: visit_dates
      provider_config: {min_days: -30, max_days: 30}
  prohibit:                                       # optional
    - id: no-clear-ssn
      select: {classification: ssn}
      forbid: [passthrough]
    - id: keys-keyed
      select: {role: child_key}
      require: [hash, fpe, tokenize]
  default: {strategy: redact}                     # optional, level 5
tables:
  - name: patients
    columns:
      - {name: email, classification: email}      # decided by the disguise (level 4)
      - {name: ssn, classification: ssn, tags: [direct_id]}
      - {name: notes, strategy: passthrough}      # level 1
```

- `PolicyConfig` (strict, `extra="forbid"`): `disguise` (`id` slug, `version` `YYYY-MM-DD`
  fullmatch), `rules` (each: `id` slug unique across rules and prohibitions, `select`, the
  decision keys, optional `why`), `prohibit` (each: `id`, `select`, exactly one of `forbid` or
  `require`, a non-empty list of strategy names, optional `why`), `default` (a decision without
  `id` or `select`). Strict strings and strict bools throughout (recurring defect 2). At most 200
  rules and 200 prohibitions, lists of at most 50 values.
- `ColumnDecision` (the one canonical decision form): `strategy` (required), `provider`
  (default `None`), `provider_config` (default `{}`), `namespace` (default `None`),
  `deterministic` (default `False`), `allow_collisions` (default `False`). The defaults are the
  `ColumnConfig` defaults (`config/_tables.py:83` to `:120`); a test pins the two sets equal. Rules,
  `default` and the level 4 source all produce a `ColumnDecision`, so normalization happens once.
- `ColumnConfig` gains `classification` (one id from the classification vocabulary, checked by a
  field validator against `registered_detector_ids()` whether or not a policy is present) and
  `tags` (up to 20 slugs). Both are omitted from dumps when unset, as `when` is today. Generate
  columns do not get them.
- A column with no `strategy` is allowed only when `policy` is present. It may carry only `name`,
  `classification`, `tags` and the F06 declared-casting keys. Any strategy-shaping key (the
  `ColumnDecision` keys, `cardinality_mode`, `scale`, `coherent_with`, `backend_type`,
  `backend_version`, `pool_size`, `vault`, `when`) refuses with `config.policy_column_partial`. To
  tune a field, write its strategy (level 1).
- Without `policy`, a column without `strategy` fails exactly as today (pydantic `missing`).

### 3.2 Selector grammar (engine, slice E2a)

`Selector` keys, all optional, at least one present; keys AND, list values OR:

| Key | Value | Matches |
|---|---|---|
| `table` | glob or literal | `fnmatchcase(table_name, value)` |
| `column` | glob or literal | `fnmatchcase(column_name, value)` |
| `classification` | id or list of ids | the column's `classification` |
| `tag` | slug or list | any of the column's `tags` |
| `logical_type` | one of `LOGICAL_TYPES` (imported, not copied) | the column's declared `logical_type` |
| `role` | `parent_key` or `child_key`, or a list | the column is in a `relationships` parent or child column list |

A glob is a value holding `*`, `?` or `[`. Values are strict strings of 1 to 128 printable
characters. An empty selector, an unknown key or a bad value refuses with
`config.policy_selector_invalid` at the selector's location. A classification outside the
vocabulary refuses with `config.policy_unknown_classification`.

### 3.3 Precedence (the one registry, `config/policy/_precedence.py`)

| Level | Name | Sources |
|---|---|---|
| 1 | `exact_field` | the column's own `strategy`; a rule whose selector is a literal `table` and a literal `column` and nothing else |
| 2 | `exact_object_or_classification` | a rule with no glob whose selector is a literal `table` alone, `classification` alone, or literal `table` plus `classification` |
| 3 | `scoped_pattern` | every other rule selector |
| 4 | `classification_default` | the pinned disguise's first rule whose `detectors` holds the column's `classification` |
| 5 | `global_default` | `policy.default` |

`selector_level(selector)` is the only function that assigns a level to a rule. It walks one
ordered tuple of `(predicate, level)` entries, first match wins, with a final catch-all to level 3.
The tuple is the registry; `PrecedenceLevel` is the only enum. F16-T2 enumerates every combination
of the six keys present or absent, each with literal and glob values where the key allows a glob,
and pins the level of each. Worked cells: `table` + `column` literal is 1; `table` + `column` glob
is 3; `column` without `table` is 3 (a column literal with no table is a pattern over all tables);
`table` + `tag` is 3; `table` + `role` is 3; `classification` + `column` glob is 3; `table` +
`column` literal + `tag` is 3 (an extra filter makes it a pattern); `classification` list is 2.

For each mask field, the expansion takes the lowest-numbered level with at least one matching
source. If two sources at that level give different normalized decisions (compared as the
canonical JSON of the full `ColumnDecision`), the config is refused with
`config.policy_rule_conflict` naming both. Equal decisions merge, and the explanation lists both.
A disguise is one source, so its internal first-match order is not a conflict. A column's own
`strategy` and a level 1 rule are both level 1, so a rule that names a column which also writes a
different strategy is a conflict, not a silent override.

### 3.4 Expansion and prohibitions (E2a, E2b)

`expand_policy(raw, inputs: ExpansionInputs) -> tuple[dict, PolicyExpansion]` is pure.
`ExpansionInputs` carries the validated `PolicyConfig`, the strategy vocabulary, and
`classification_default: Callable[[str], ColumnDecision | None]` (the level 4 source). In
production the callable wraps `decision_for(pinned_disguise, classification)`; in E2a tests it is a
stub, so E2a needs no bundle change. The function reads only the config. For each mask table it
walks `columns` in order, computes the decision, and writes the decided keys into a new column dict
in a new tables list. It collects every problem and raises them together through `problem_details`
at their config locations. A malformed structure (tables not a list, a column without a string
`name`) is skipped, so the model's own error reports it.

Prohibitions run on the explicit result over every mask field. `forbid` refuses a field whose
strategy is in the list; `require` refuses a field whose strategy is not. A prohibition that
selects no field is not an error; the explanation shows `matched: 0`.

### 3.5 Disguises (slice E1)

`FieldRule` becomes `detectors`, `strategy`, `provider`, `provider_config`, `namespace`,
`deterministic`, `allow_collisions`, `why`, with `extra="forbid"`, strict types and `frozen=True`
(`Disguise` too). All ten bundles are rewritten and each gets a new dated `version`:

- `faker` with `faker_type: X` becomes `provider: <the provider whose Faker method is X>`, from
  `providers_v2/_faker_adapter.py:49`. Picks: `name` is `person_full_name`, `zipcode` is
  `address_zip`, and the others map one to one. `locale` moves into `provider_config` (the key the
  faker pool reads), so gdpr's `en_GB` rules keep their locale.
- A faker rule whose purpose is joins or repeat stability gets `deterministic: true` (and
  `allow_collisions: true` where the provider pool is small, per the existing faker column rule).
  Each rule's `why` is rewritten to state only what the rule does.
- `date_shift` with `jitter_days: N` becomes `provider_config: {min_days: -N, max_days: N}` and a
  bundle namespace `<id>_dates`, so all date columns of one pipeline shift together, as the CLI
  hipaa template does.
- The three `ipv4` rules become `redact` (the CLI templates' documented exception).
- Other strategies keep their parameters, moved to `provider_config` (`fpe` `charset`,
  `validate_luhn`, `checksum`; `truncate`; `redact` `redact_with`; `code_set`;
  `geo_generalize`).

`decision_for(disguise, classification) -> FieldRule | None` stays in `disguises/schema.py`.
`config/policy` turns the rule into a `ColumnDecision` (the layer contract lets `config` import
`disguises`, not the other way round).

Built-in bundles are loaded once per process: `disguises.builtin_disguises()` is an
`functools.cache` wrapper over `load_disguises()` that returns a tuple of frozen models. The loader
logs and skips a malformed bundle file today; for built-ins, F16-T7 and F16-T11 prove all ten load,
so a skip cannot hide a pinned bundle in a release.

Closing RGF1-KL-3: `disguises/_versions.json` pins the SHA-256 of each bundle file per
`(id, version)`. A test fails when a bundle's bytes change and its version does not, or when a
known `(id, version)` changes digest. A new version adds a row; rows are never edited.

### 3.6 The choke point (slice E3)

`PipelineConfig` gets `policy: PolicyConfig | None = None` (omitted from dumps when `None`) and a
`model_validator(mode="before")` that, when `policy` is present:

1. makes a shallow copy of the top-level raw mapping (never writes to the caller's dict;
   `expand_policy` builds new table and column containers, so no nested object is shared and then
   written);
2. validates `policy` into `PolicyConfig`, checking strategy names against `mask_strategy_names()`;
3. takes the pinned bundle from `builtin_disguises()` by `id` and `version`;
4. calls `expand_policy`;
5. puts the explicit tables and the validated `PolicyConfig` (carrying the expansion as a private
   attribute) into the copy and returns it.

Field validation then runs on the explicit columns, so every existing column check sees the
decided strategy as if a person wrote it. `PipelineConfig.policy_expansion` returns the expansion
(or `None`). Re-validating the dump re-expands: filled columns are now level 1 with the same
decisions, so the dump is unchanged.

Raw-mapping readers outside the choke point. Engine and CLI code that reads `strategy` from a raw
mapping sees nothing for a policy-decided column. Engine: `secret_requirements_for_config`
(`src/decoy_engine/secret_providers/_requirements.py:270`) is a public, config-only classifier, and
the CLI calls it on raw YAML. E3 makes it validate through `PipelineConfig` first when the mapping
holds `policy`, so a policy-decided keyed column counts as keyed (F16-T13). The builder lists every
other engine function that takes a raw config mapping and reads `strategy`, and records for each
that its callers pass the validated dump. CLI: section 8, Fields.

`mask_strategy_names()` returns the keys of the existing strategy table in
`contracts/distribution_behavior.py`. A new test asserts it equals the `SCALAR_HANDLERS` key set
both ways (the existing test checks one direction).

JSON schema: `ColumnConfig.__get_pydantic_json_schema__` drops `strategy` from `required` (the
description says "required unless the pipeline has a policy block"); runtime keeps it required.

### 3.7 Explanation document

`expansion_to_dict` writes `policy-expansion/v1`:

- `schema`, `disguise` (`{id, version}` or null), `fingerprint` (SHA-256 hex of the canonical JSON
  of the sorted `[table, column, decision_digest]` list plus the disguise pin);
- `fields`: `table`, `column`, `strategy`, `provider`, `deterministic`, `level`, `level_name`,
  `sources` (a non-empty list of `{kind: column|rule|disguise|default, id}`: every source that agreed on the winning decision (3.3), ordered column first, then rules in policy order, then disguise, then default), `overridden` (rule ids),
  `classification`, `decision_digest` (SHA-256 of the normalized decision's canonical JSON;
  `provider_config` itself is not copied);
- `rules` (`id`, `level`, `matched`), `prohibitions` (`id`, `matched`).

It is write-only in V1 (no reader), so it has one strict writer model and a tag. A reader is added
with its first consumer that reads it back (recurring defect 4).

### 3.8 Plan hash

The plan hash covers the dump, and the dump holds the `policy` block. So editing any rule text,
including a `why` or a rule that now matches nothing different, changes the plan hash, and a run
resumed across that edit is treated as a different plan, as for any config edit today. The C2 guide
page says so.

### 3.9 Refusal messages

Each refusal is a `PydanticCustomError(code, template, context)`. Context values are config
identifiers only: rule and prohibition ids, `table.column` names, level names, strategy and
provider names, the disguise id, and the pinned and shipped version dates. Version dates are config
and bundle metadata, not data, so they may appear. `provider_config` values, `why` text and any
other free text never appear. F16-T12 sweeps every one of the ten codes with canary literals.

### 3.10 CLI (slices C1, C2)

- C1: repin to the release carrying E3 (repin checklist). The compliance templates `hipaa`, `pci`
  and `gdpr` become `policy.disguise` pins plus per-column `classification`; columns the disguise
  does not cover keep an explicit strategy. `test_template_disguise_drift.py` is rewritten: each
  template validates, every classified column decides at level 4, and the `x-derived-from-disguise`
  marker equals the pin. The hand map and `_STRICTER_EXCEPTIONS` are deleted. Raw-YAML strategy
  and keyed-ness readers (section 8, Fields) read the validated dump instead, each with a
  policy-config test.
- C2: `decoy validate compile --explain` shows each column's level and source from
  `policy_expansion` instead of the fixed "declared in pipeline config" rationale, plus the
  fingerprint; `--json` gains a `policy` member holding the `policy-expansion/v1` document.
  `decoy explain disguises` text is corrected (it says two disguises ship; ten do) and describes
  the pipeline policy block. Docs: cli-reference and a guide page with the worked example of
  section 3.1 and the plan-hash note of 3.8.

## 4. Failure modes

| Case | Result |
|---|---|
| Unknown disguise id | `config.policy_unknown_disguise` at `policy.disguise.id` |
| Pin differs from shipped version | `config.policy_disguise_version_mismatch`; the message names both dates |
| Classification not in the vocabulary | `config.policy_unknown_classification` at the column or selector, with or without a policy block |

## 5. Design notes and choke points

- New structure: a `config/policy/` sub-package. `config/` holds 25 direct modules, the fan-out
  limit, and the counter (`tests/sentry/layout/_layout.py:99`) does not count sub-packages, so a
  named sub-package is the layout rule's answer. Policy is config validation, so it belongs under
  `config/`: it imports `LOGICAL_TYPES` and `problem_details` from its parent package instead of
  copying them, and `registered_detector_ids()` from `detection` (a sibling in the same import-linter
  layer). `config/policy/` holds 5 modules (cap 25).
- One place per fact: levels and the level registry in `_precedence.py`; the selector model and
  matching in `_selectors.py`; the YAML models and `ColumnDecision` in `_policy.py`; expansion,
  conflicts and the explanation in `_expand.py`; prohibitions in `_prohibit.py`; bundle schema,
  `decision_for` and the bundles in `disguises/`. Principle applied: single responsibility for the
  precedence rule, which changes for policy reasons and must not be copied into the CLI or the
  platform. House style: a typed context (`ExpansionInputs`) instead of long parameter lists; no
  flag arguments.
- Choke point: `expand_policy` and `selector_level` are called only from `config/_pipeline.py` and
  inside `config/policy/`. Guard: new sentry `tests/sentry/test_policy_expansion_choke_point.py`,
  built on `tests/sentry/_call_resolution.py` and added to `SENTRIES` in
  `tests/sentry/test_sentry_manifest.py`. It walks `src/decoy_engine/` and fails on an import or
  call of either name elsewhere. Covered shapes (recurring defect 5): `from decoy_engine.config.policy
  import x`, `from decoy_engine.config.policy._expand import x`, `as` aliases, `import
  decoy_engine.config.policy as m` with attribute access, each also inside a function body.
  Mutation MS1: a second call in `execution/_pipeline_context.py`.
- CLI. The CLI never expands; it reads `policy_expansion` from the validated model. No new CLI
  sentry: the existing `tests/sentry/test_engine_internal_boundary.py` already refuses the private
  `config.policy._*` modules, and a CLI call to the public `expand_policy` would re-run the same
  pure function on an already explicit dump (every field level 1), so it cannot change a decision.
  Logged in V2-LOG.

### Exit paths

- Each refusal in section 4: a pydantic `ValidationError` with the code at its location; CLI exit 1.
- Success: explicit dump; `policy_expansion` set.
- `decoy validate compile --explain`: exit 0 with the explanation; exit 1 on a refusal.
- `decoy.mask()`: raises the same `ValidationError` before any source read.

### FK shapes

- Single-column FK: `role: parent_key` or `child_key` selects the key columns. The decided
  strategy then meets the existing namespace and FK checks unchanged.
- Composite FK: every member column carries the role. A rule that selects one member and not the
  others is allowed, and the existing composite checks judge the result.
- Self-referencing and multi-parent relationships: roles are per column, so a column can have
  both; `role` lists OR.
- Join survival from a disguise rule depends on `deterministic` (faker) or a keyed strategy;
  F16-T7 proves each rule that claims it.

### Output surfaces

- The explicit config dump (and the plan hash over it).
- `policy-expansion/v1` via `PipelineConfig.policy_expansion` and `expansion_to_dict`.
- Refusal messages and locations (3.9).
- CLI `validate compile --explain` text and `--json` `policy`; `decoy explain disguises`; the
  `decoy init` keyed hint.
- Logs: none added. Expansion runs at config load, before the job log opens; refusals reach the
  user as the config error.
