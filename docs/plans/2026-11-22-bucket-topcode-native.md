## 1. Frame

`bucketize` and `top_code` have no entry in the operator registry (`execution/_operator_registry.py:131-312` lists passthrough, redact, truncate, text_redact, text_mask, hash, faker, categorical, bucket_perturb, group_key, date_shift, fpe). Today:

- `top_code` is row-local and CHUNK_SAFE, but excluded from the native route for lack of a kernel (`execution/native/_capabilities.py:281-302`); the unified slice sends it to full frame (`execution/physical/_shadow_full_frame.py:113-121`, `ADMITTED_GLOBAL_STRATEGIES`).
- `bucketize` runs chunked pandas only when the source is null-free numeric, because its pandas output type depends on chunk content (`execution/_chunked.py:21-33`; gate at `execution/_planner.py:508-526`). A column with nulls runs full frame. This plan keeps that gate.

Since E3, both strategies read only typed numbers: a typed integer or float column, a declared (F06) text column cast before masking, and for `bucketize` a decimal of precision 15 or less (`contracts/strategy_requirements.py:198-232`). Both are pure functions of the row's own value and config literals: the bucketize width from `width` or a preset through `contracts/bucketize_width.py`; the top_code `cap`, `over_label`, `floor`, `under_label` from config or the `hipaa_age` preset (`_top_code.py:396-460`). No threshold is ever derived from data. This plan keeps it that way and makes a test of it.

Oracle semantics on typed input (read at the anchor and probed with pandas 2.3.3, pyarrow 24.0.0):

- bucketize (`_bucketize.py:66-134`): `nums = pd.to_numeric(col, errors="coerce")`; `lower_f = np.floor(nums / width) * width`. Integer against float handling is decided by the width (`is_int_width`), not the source dtype. Integer width: `lower = lower_f.astype("Int64")`, range upper `lower + w - 1`, midpoint `lower_f + w / 2` cast to `Int64` only for an even width. Float width: float labels through `astype(str)`. An unknown format becomes `lower`. `declared_integer_output` keeps `lower` as `Int64`. Output is `formatted.where(nums.notna(), col)`, so the reconstructed pandas dtype determines missingness.
- top_code (`_top_code.py:148-268`): bounds finite with magnitude below 2**53. A numeric column: over is `nums > cap`; under is `nums < floor` only when both `floor` and `under_label` are set; in range renders `astype(str)` for an integer dtype, and for a float dtype `str(int(v))` for an integral finite value, else `astype(str)`. top_code columns are in `lossless_int_columns` (`_fk_keys.py:369-395`), so a null-bearing integer column arrives as `Int64` and renders exactly. On a numeric column it never emits `format_error`. A `top_code_generalized` warning carries `over_count` and `under_count` for the frame it ran on.

Probed oracle behavior the design must keep or name:

1. Integer width over `int64` `2**63 - 1`, or a float `1e19`: `TypeError` crash. Over `inf` or `-inf`: `OverflowError` crash. Over `2**53 + 1`: label from the rounded float, `9007199254740990`. Over `-2**63`: label `-9223372036854775808`.
2. Float width over `inf`: `inf`, range `inf-inf`. No crash.
3. Degenerate types, every route, int and float sources: empty column `null`, all-null column `null`, otherwise `string`.
4. Float mirror: Arrow `cast(int64 -> float64, safe=False)`, `divide`, `floor`, `multiply` equal numpy's `np.floor(nums / w) * w` on 1,000,000 values (random full-range int64, random int64 within 2**53, random finite doubles from raw bits, uniform and normal floats) for widths 1, 3, 7, 10, 1000, 2.5, 0.1, 0.3: zero mismatches. pandas' float64 ingest of a null-bearing int64 rounds the same way as the Arrow cast.
5. Float width over an integer source depends on the reconstructed pandas dtype. NumPy `int64` and nullable `Int64` holding 9007199254740993 at width 2.5 round to float64 and label `9007199254740992.0`. `int64[pyarrow]` raises `ArrowInvalid` and the message quotes the value. Below 2**53 all three give the same labels (20 at 2.5 gives `20.0`).
6. Pandas schema metadata changes values only through extension dtypes. On a physical `double` column, NumPy `float32` or `int32` metadata reconstructs float64 unchanged; `Float64` and `double[pyarrow]` keep the value; `Float32` and `float[pyarrow]` round 16777217.0 to 16777216.0; `Int32`, `int64[pyarrow]` and other integer extension dtypes raise. On a physical `int64` column, NumPy `int8` or `float64` metadata reconstructs int64 unchanged; `Int32`, `Int8`, `UInt8`, `Float32` and `int32[pyarrow]` raise on 300 or 2**40. `Table.set_column` keeps the old metadata, so a later chunk can carry any of these.

### Measurement (decides Rust against Arrow)

Probe on the Dell node through `vm-run`, 1,000,000 rows, minimum of five runs (pyarrow 24.0.0, pandas 2.3.3):

| Case | pandas oracle logic | Arrow compute | Ratio |
|---|---|---|---|
| bucketize int64 with 1% nulls, width 10, `range` | 783 ms | 82 ms | 9.5x |

Arrow compute is 48 to 82 ns per row; writing and reading the label column alone is about 149 ns per row. A Rust kernel could save at most the compute, below the I/O floor. ### Missingness and row exits

Arrow null stays null. A physical valid NaN never counts as B2 or B3. Ordinary pandas float metadata treats it as missing. A reconstructed pandas `Float64` or `double[pyarrow]` column can treat it as present. Top_code and float-width bucketize lower then emit `"nan"`, and float-width range emits `"nan-nan"`. Integer-width bucketize can render a valid NaN differently again depending on dtype, format and width parity.

Detect valid NaNs with Arrow validity and `is_nan`. Carry the raw table's pandas metadata into the adapter. For each chunk use the current raw chunk before null-column normalization. For unified use the corresponding batch of the resident frame or its metadata-preserving source slice. On valid NaN positions only, select from the oracle's reconstructed series with its dtype intact, use the handler's shared numeric rendering with the resolved settings and scatter its typed output back. Reuse the resident frame when available. For the sparse chunk case select the float column and NaN rows from the metadata-bearing raw table, then use its pandas conversion. This is the float branch of the oracle conversion in `internal/pandas_compat.py::table_to_pandas_exact_ints` (line 116; whole-table reconstruction at line 132): only integers receive a types_mapper override. No new caller of a sentry-allowlisted ingest helper is needed. Preserve dtype and use positional indices when scattering. For ordinary missing NaN the replacement is null. Keep the vector path for the remaining positions. A bare-array kernel uses ordinary missingness unless supplied these sparse replacements. Reconcile the degenerate output type after scattering.

The NaN rule above is only sound when the metadata dtype keeps every finite value. That is the pandas-metadata identity gate:

- Scope: each admitted bucketize or top_code column. Chunked: each raw chunk before null-column normalization, the same object the NaN rule reads. Unified: the resident frame's reconstructed dtype, checked before the round-trip comparison.
- Rule: reconstruct the column's pandas dtype from a zero-row slice of the raw chunk (`chunk.select([col]).slice(0, 0).to_pandas()`, the same pyarrow metadata path the oracle's line-132 conversion uses, so no metadata parsing is copied). Map it back to Arrow: a NumPy dtype through `pa.from_numpy_dtype`, a pandas masked dtype through its `numpy_dtype`, an `ArrowDtype` through `pyarrow_dtype`. Admit only when the result equals the physical type. An absent metadata entry admits. A reconstruction that raises declines.
- Decision: decline that chunk (chunked, through the existing per-chunk real-type downgrade to the oracle) or that table (unified) with `fallback_policy_not_native` and detail `pandas_metadata_not_identity:{column}`. The oracle then reproduces whatever pandas does, including a crash.
- It is value-independent: it reads only types and metadata, never values, so it adds no scan and puts no value in any reason.

Use one vector exit-mask function on a float64 Arrow array for the handler and the kernel. S1a introduces this function in `kernel/_bucket.py` and exposes it through the kernel package. The handler supplies only its comparison view and takes back positional booleans. For integer widths, B2 selects finite magnitude at or above the exact limit and B3 selects positive or negative infinity. Fill null predicates with false. Mask bad positions and physical NaNs before integer casts. Float-width arithmetic can itself produce NaN. Render the computed float at present source positions, preserving the distinction from source missingness.

## 10. Frozen contracts and byte changes

**B2.** With an integer width, a finite numeric value whose float64 magnitude is at least 2**53 produces one format_error row and a null cell. This replaces rounded labels or an uncoded cast failure.

**B3.** With an integer width, positive and negative infinity produce the same single error and null cell. This replaces an uncoded overflow. Neither change includes a valid NaN. The reason text is `value is out of range under bucketize`. In quarantine the record carries null for this masked cell. With fail policy the job fails before publishing the transactional output.

**B4.** With a float width, an integer source is converted to float64 with round-to-nearest before division for every pandas integer dtype. An `int64[pyarrow]` value of magnitude above 2**53 now gets the label NumPy `int64` and nullable `Int64` already get (9007199254740993 at width 2.5 gives lower `9007199254740992.0`) instead of an uncoded `ArrowInvalid` whose text quotes the value. Values below 2**53 and float sources are unchanged.
