## 0. What V1 gets, and what it does not

Row 72 is "F33 CLI verifier and engine signature envelope". In CLI V1 nothing produces a signed
bundle: the producer (platform P3 to P6a) is parked with the platform. V1 therefore ships the
verifier and the signer primitive, and the CLI command that runs the verifier offline. A V1 user
can verify a bundle a later platform produces, and the CLI tests prove it on bundles a test helper
signs with the engine's own `sign_evidence`. Owner question OQ-1 asks whether this is still the
V1 scope; the plan is written for "yes" (the 2026-11-11 decision kept row 72 in V1).

### 1.2 Pinned guarantee (V1 bar rules only)

After C1 merges, `decoy report verify --signed DIR --trust-policy FILE --trust-policy-sha256 HEX
--expect FILE --expect-sha256 HEX` exits 0 only when: the signature over the JCS statement is
valid under a key that the digest-pinned trust policy lists as ACTIVE or RETIRED for the
statement's tenant, signer and key version; every expected artifact exists under `DIR/artifacts`
as a regular file (no symlink, no directory redirect) and is byte-equal to its expected digest;
the catalog checks are OK; and the pinned expectations say no output is unbound
(`unbound_outputs` is 0; the statement has no such field, so the expectations are its only
source). It exits 4 for a flipped output byte, an
edited statement, a swapped `kid`, a revoked key or an unbound output. It exits 1 for a digest
mismatch on the policy or the expectations, a missing field, or a malformed file. Every
non-success prints one fixed message per result class, with no path, no file bytes, no exception
text and no data value (the unbound-output count is reported only as `none` or `present`). The
command opens no network connection. `decoy report verify MANIFEST`
(the `cli-local-1` route) is unchanged byte for byte.

Rules: rule 1 (function): a valid bundle verifies; rule 2 (data integrity): a changed byte is
reported, never accepted; rule 3 (non-admin surfaces): no value reaches CLI output.

### 1.3 Non-goals

- Producing a signed bundle in the CLI (`decoy run` signing its own evidence). That is a new
  feature; it is not in the row text.
- Platform P-OWN, P0 to P6b, E1c, KMS-held keys, rotation and revocation administration.
- The strict release gate (`_release.py`) and `evidence_release/` (left out of E1a; they stay in
  #335's history for Platform V1).
- Any change to the `cli-local-1` manifest, `manifest_hash`, or `records/` codecs.

## 2. Established solutions

Search run for this revision: the #335 design record (`docs/security/signed-evidence.md` at
`06877527b`), RFC 7515 (JWS), RFC 7797 (unencoded detached payload), RFC 8785 (JCS), RFC 7493
(I-JSON), the TUF specification (pinned root of trust), Sigstore bundle verification (offline
verification against a pinned trust root), and the engine `_canonical` and `fileaccess` packages.

- Detached JWS with ES256 over JCS canonical bytes, through `joserfc` and `rfc8785` (maintained
  libraries), exactly as #335. No custom crypto.
- Digest-pinned trust root and pinned expectations, as TUF and Sigstore do: the verifier takes the
  policy and the expectations by content digest, so a swapped file is refused before it is read
  for meaning.
- Strict JSON intake per RFC 8259 with the I-JSON limits: duplicate members refused, no
  non-finite numbers, integers inside the IEEE double safe range.
- Rooted no-follow reads under a held directory descriptor: the engine's own `fileaccess` layer
  (one mechanism, not a second walk).

Custom code left: the statement and expectations schemas and the decision table, which are Decoy
formats and were reviewed on #335.

## 3. Design notes

1. **One rebase branch, not a merge of #335.** E1a starts from engine main and brings over, by
   path, `src/decoy_engine/signed_evidence/` (minus `_release.py` and `_canonical.py`), its tests
   (`ET:unit/signed_evidence/`, `ET:sentry/test_evidence_signing_boundary.py`), the conformance
   corpus, `docs/security/signed-evidence.md` and the `docs/methodology-registry.yaml` lines.
   `evidence_release/` and `ET:unit/evidence_release/` are not brought over. #335 is closed with a
   pointer to the E1a PR. Reason: a 19-day-old merge base would drag `uv.lock` and unrelated
   conflicts into a security review.
2. **JCS joins `_canonical` as a third named form.** New `E:_canonical/_jcs.py` with
   `jcs_bytes(value) -> bytes` (the `rfc8785.dumps` call and its exception mapping, moved from
   `signed_evidence/_canonical.py`), exported from `E:_canonical/__init__.py`. Its refusal is a
   `CanonicalJsonError` subclass with a registered code. `signed_evidence` imports it from the
   facade. The two existing forms are unchanged. Choke point: the existing sentry
   `ET:sentry/defects/test_canonical_json_choke_point.py` gains one rule: `rfc8785` is imported
   only in `_canonical/_jcs.py`.
3. **One strict reader, one profile on top.** `signed_evidence/_strict_json.py` keeps its
   pre-parse limits (UTF-8 without BOM, `MAX_BYTES` 4 MiB, `MAX_DEPTH` 32, `MAX_NODES` 200,000)
   and its post-parse walk (no float, integers within `2**53 - 1`, no unpaired surrogate), and
   delegates the parse itself to `_canonical.strict_json_loads` (duplicate keys, NaN and
   Infinity). It no longer calls `json.loads` or builds its own `object_pairs_hook`. The
   pre-parse limits must run before the decoder, which is why the profile stays a module.
4. **Artifact reads: ambient-only, registered, race-checked.** The CLI is the only V1 caller and
   runs under the ambient policy, whose directory handle follows symlinks. So the verifier keeps
   #335's no-follow walk (each component opened with `O_NOFOLLOW` beneath the parent's
   descriptor, leaf `fstat` must be a regular file), and its public entry calls
   `fileaccess.require_ambient("signed evidence verify")` before any I/O, so a strict policy
   fails closed instead of being bypassed. Each `os.open` in `_artifacts.py` gets a
   `file_access_registry.toml` entry with `ambient_only = true`, its rule ("relative path from
   the pinned expectations, lexically checked, opened no-follow beneath `DIR/artifacts`"), owner
   and reason; the registry count rises by that number. This is the existing choke point for
   engine file sinks; its sentry fails on an unlisted `os.open`. Rooted-policy support (the
   platform's case) is a Platform V1 follow-up. Race check, replacing #335's byte-count check:
   The `artifacts` directory itself is opened beneath the bundle directory's descriptor with
   `O_DIRECTORY | O_NOFOLLOW` and checked with `fstat` to be a directory; #335 opens it without
   `O_NOFOLLOW` (`_artifacts.py:233-236` at `06877527b`), which E1a changes.
   `fstat` the open descriptor before hashing; hash in bounded chunks; `fstat` again and require
   equal size, `st_mtime_ns` and `st_ctime_ns` (a write through any descriptor moves `ctime`,
   which a user cannot set back); then re-resolve the same relative path with the same no-follow
   walk and require its `(st_dev, st_ino)` to equal the hashed descriptor's (a rename swap). Any
   difference is `ARTIFACT_CHANGED_DURING_READ`. Pattern: git's racy-index check (compare `ctime`
   and `mtime` around a read). Limit: a filesystem with coarse `ctime` can miss a same-size write
   inside one tick; recorded in Not verified.
5. **Errors join the registry under their own profile.** `E:reasons/_catalog.py` gains one
   profile, `evidence(owner)`: kind FAILURE, phase VERIFY, severity ERROR, retry NEVER, namespace
   `evidence`. Its identities live in `E:reasons/evidence/_signed.py`, one symbol per raised token.
   `SignedEvidenceError` becomes a `DecoyError` subclass whose `code` is one of them. Input
   refusals and signer failures are not "findings", so the `verification` profile is not used. The message stays the
   fixed summary. The verification result's own status and reason tokens (for example
   `ARTIFACT_NOT_EXPECTED`) are not raised errors: they are fields of the frozen result contract,
   pinned by the conformance corpus, and are not registered.
6. **Layer.** `signed_evidence` imports only `_canonical`, `_error_base`, `reasons` and
   `fileaccess` (for `require_ambient`) from the engine. It goes in the `.importlinter` tier with `run_result`, and in the
   snapshot in `ET:sentry/layout/test_import_layers.py`.
7. **Public surface is what a caller uses.** The facade exports `verify_signed_evidence`,
   `VerificationContext`, `ExpectedArtifact`, `Purpose`, `TrustPolicy`, `RequiredCatalog`,
   `VerificationResult` and its status enums, `ExitClass`, `SignedEvidenceError`, and for the
   signer side `sign_evidence`, `SigningIdentity`, `LocalEs256Signer`, `EVIDENCE_FILENAME`,
   `SIGNATURE_FILENAME`. Names nothing calls after `_release.py` is left out are not exported.
   This keeps row 24zj (PROP-SURFACE) from flagging the package on arrival.
8. **CLI command home.** The `report verify` command body (`_VERIFY_EPILOG` and `_verify`, about
   110 lines at `C:cli/report.py:1408-1520`) moves unchanged into a new sub-package
   `C:cli/evidence_verify/` (`_manifest.py`), and the signed route goes in `_signed.py` there.
   `report.py` keeps only the registration line, so it shrinks by about 100 lines and its size
   ceiling is lowered to the new count in the same slice. With `--signed` absent, the moved code
   path is the old one: AT-C9 pins it.
9. **CLI exit mapping.** The engine's `ExitClass` maps to CLI exits through one table in
   `_signed.py`: OK to `EXIT_OK` (0), every verification failure class to `EXIT_FINDINGS` (4),
   input and digest refusals to `EXIT_USAGE` (1). No new exit integer; the RG-X exit table
   (`C:cli/exit_codes.py`) is unchanged and its sentry stays green.
10. **One strict, versioned expectations reader, in the engine.** New
    `E:signed_evidence/_expectations.py`: `parse_expectations(data: bytes) -> Expectations` (a
    frozen dataclass holding a `VerificationContext` and a `RequiredCatalog`). It reads through the
    strict profile (design note 3), then requires: `v` is the integer 1 (not `true`, not `"1"`);
    the member set is exactly `v`, `tenant`, `job_id`, `attempt_id`, `bundle_id`, `snapshot_id`,
    `artifacts`, `unbound_outputs`, `catalog` (unknown or missing member refused); each id is a
    non-empty string matching `_context.py`'s id rule; `snapshot_id` may be `null` only where
    `VerificationContext` allows it; `artifacts` is a non-empty list of objects with exactly
    `id`, `sha256` (64 lowercase hex), `media_type` (string), ids unique; `unbound_outputs` is a
    non-negative integer and not a bool; `catalog` goes to `RequiredCatalog.from_bytes`. Every
    refusal is one registered `evidence` code. The shape is the platform plan's P6a writer
    contract (revision 9, `api/evidence/expectations.py`), frozen here as
    `expectations` version 1 so the platform writer must match it. The CLI calls only this
    reader; it never builds a context itself. Normalization happens here and nowhere else: each
    wire `sha256` becomes `ExpectedArtifact.sha256 = "sha256:" + hex` (the form `_context.py`
    requires); the parsed `catalog` object is turned back into bytes with `_canonical.jcs_bytes`
    and passed to `RequiredCatalog.from_bytes`; `unbound_outputs` goes to the new context field
    of design note 11.
11. **Unbound outputs are an engine decision.** `VerificationContext` gains
    `expected_unbound_outputs: int = 0`, and `_verifier._decide` returns `ExitClass.PARTIAL` when
    it is above 0, after every other check (a valid signature over a statement that does not
    cover every output is not full success). This changes one reviewed #335 module
    (`_verifier.py`) and `_context.py`; the review re-reads both. The CLI maps PARTIAL to exit 4
    and prints `unbound outputs: present`.

## 4. Behavior

- `decoy report verify --signed DIR` requires all four of `--trust-policy`,
  `--trust-policy-sha256`, `--expect`, `--expect-sha256`; any missing one is exit 1 with one fixed
  line naming the missing flag (flag names are not user data).
- The policy and expectations files are read as bytes and their SHA-256 compared with the given
  hex before parsing. A mismatch is exit 1, "trust policy digest does not match" or "expectations
  digest does not match".
- The engine verifier runs with `Purpose.CONSUMER_ACCEPTANCE` and a context built only from the
  expectations document (tenant, job id, attempt id, expected artifacts, required catalog). No
  context value comes from a flag.
- `--json` prints `{"command": "report verify", "mode": "signed", "status": ..., "exit_class":
  ..., "signature": ..., "trust": ..., "artifacts": ..., "checks": ..., "unbound_outputs": ...}`,
  each a closed enum token; `unbound_outputs` is `none` or `present`, never a count. No path, no digest of a user file, no key material.
- Human output: one line per dimension with a fixed word (valid, invalid, mismatch, missing),
  then the verdict line.

## 8. Enumerations

  `KeyboardInterrupt` keeps the CLI's existing handling.
