## 1. Frame

Three user-visible problems, all from one cause: the lanes do not say why they declined, so the CLI guesses.

1. **Wrong label.** At 120k rows a table of `passthrough`, `redact`, `truncate` or `text_redact` columns runs every column as `arrow_python` on the chunked lane, but the run card says `pandas (streamed lane)`. `CLI:src/decoy/_native_gate.py:482-497` (`classify_route`) labels any auto-chunk run with no compiled call as pandas. `route_summary` exposes only `native_executed` (`execution/pipeline/_route_summary.py:60`), not the per-column executed backend that both lanes already record.
2. **Silent decline.** `cheap_admission` (`execution/_unified_slice_admission.py:196`) and `resident_contract_admission` (`:410`) return `None` at about 40 sites. The table then runs on the pandas oracle and nothing records why (docstring at `:212-216`: "the coded reason is a nice-to-have"). The chunked lane already records coded per-column declines (`execution/native/_route_decline_codes.py`, OBS-2b, `quality_metrics["chunked_route"]["decline_records"]`), but `route_summary` never reads them.
3. **A copy of the rules in the CLI.** `CLI:src/decoy/_native_gate.py:210-301` (`static_native_eligibility`, audit J3) and `_NATIVE_STRATEGIES` (`:74`) mirror the engine's admission. They are already stale: `faker`, `date_shift` and `fpe` are native operators in `execution/_operator_registry.py`, but not in the CLI set.

Two audit defects sit in the same code:

- **A5.** `execution/_unified_slice.py:370`: `except Exception` logs a class name and reruns the table on pandas. A real defect in the default-on lane becomes a slower run with no evidence.
- **A6.** `execution/physical/_compiler.py:442-450`: `except Exception: return None` around `post_scan_resident_for`. That function (`execution/_transforms_gate.py:80-83`) only calls `post_scan_resident_reason` (`config/_post_scan.py:225-234`), which returns a code or `None` and raises nothing of its own, so the catch hides only defects.

Kernel-less families (owner, 2026-11-22: named exceptions in V1): `shuffle`, `geo_generalize`, `formula` and the derived kinds, `nested`, `joint_mask`, `tokenize`, and non-poolable Faker providers. Today they decline under generic codes (`fallback_policy_not_native`, `no_native_kernel_or_pool`) or under no code at all.

## 2. Established solutions

Search run: how query engines report why a fast path was not taken (Spark, Gluten/Velox, Polars, DataFusion, DuckDB); how error registries carry a stable code with a fixed message (RFC 9457, gRPC status). In-codebase: OBS-2b decline records, the F29 reason registry, F06 `declared_casting/_refusals.py`.

- **Fallback reasons per operator: Apache Gluten.** Gluten's validation marks each Spark plan node that cannot offload with a fallback reason and reports them (`spark.gluten.sql.fallbackReport`, the `GlutenPlanFallbackEvent` with `fallbackNodeToReason`). The reason is attached at the node that declined, and the summary shows the node and the reason. This plan follows that: the decline is attached to the column (node) that caused it and carries a registered code.
- **Polars** marks nodes its streaming engine cannot run and falls back for them; **DuckDB** and **DataFusion** report the physical operator chosen per node in `EXPLAIN`. All of them show the executed operator, not the requested one. The label in this plan reads the executed backend per column.
- **Stable code plus fixed summary: RFC 9457** (problem type separate from occurrence detail). The engine's F29 registry (`reasons/`) already does this; codes go there, not into a second taxonomy.

The admit or decline outcome of every job is unchanged; only the recorded first code changes, and only for a job that has causes in two blocks.

## 7. Design notes

- Principles: one place per fact. The family map lives once beside `RouteDeclineCode`, cross-checked against the capability table; the code choice for a column lives once in `column_decline_code`; the config-only admission rules live once in `_native_outlook.config_decline`, called by `cheap_admission` and by `native_config_outlook` (and so by the CLI); each config-rejection reason has one enum member, returned by the function that decides it. Each removes a real copy: J3 is a copy today, and the chunked lane and the slice would otherwise grow two family tables.
- Pattern: Gluten fallback reasons per plan node (section 2).
- Typed results over `None`: each admission stage returns `T | RouteDeclineRecord`. No flag argument.
- Choke point: `RouteDeclineRecord.code` is a `RouteDeclineCode` member, and every member's value is a registered `reasons.route` code. The guard is the existing reason-registry sentry plus a new test that every `RouteDeclineCode` value is registered. Mutation: add a member with an unregistered string (guard red).
- E14 in `tests/sentry/defects/test_config_rejection_codes.py` walks all nine producers plus `prepare_categorical` and `_date_shift_bound_rejection`. Resolve imports, aliases, assignments, tuple elements and forwarded helper results by qualified identity. Verify every refusal originates at a member, a checked registry/table lookup or a checked producer, and every legacy string projection uses .reason. Its guard `test_no_rejection_prefix_split_in_src` walks all of `src/` for colon splits on a rejection or its projected reason, including aliases, positional/keyword separators and optional maxsplit. Ordinary strings outside that flow do not trigger the guard. Seed the old `rejection.reason.split(":", 1)[0]` in the bucket adapter and a raw f-string in the bound helper: each must make E14 red; a correct delegated member or unrelated split stays green.
- Choke point for designed reroutes (H1): `DESIGNED_SLICE_REROUTES` plus the handler list of `_execute_admitted`. Guard: E13 (guarantee 8). Before trusting the walk, the builder seeds one bypass in a scratch copy and shows the count rises (cross-cutting-concerns: "prove the walk sees a bypass").
- Sameness questions. Does this do what another module already does differently? The chunked lane already codes its declines (OBS-2b); this plan feeds both lanes from `NodeRequirements.rejection` instead of adding a second decline table. Could it live in one place? Yes, and it does: one enum, one registry, one rejection field, one config block, one reroute allowlist.
- Coverage guard for families: `tests/sentry/defects/test_kernel_less_families.py` asserts every mask strategy in `execution._strategies.SCALAR_HANDLERS` (and the composite strategies) is a key of `OPERATORS`, a key of `KERNEL_LESS_FAMILY`, or in the test's explicit `NO_NATIVE_OPERATOR` set, and checks `KERNEL_LESS_FAMILY` against `is_global` and `CHUNK_SAFE_STRATEGIES` (guarantee 4). A new strategy cannot ship without a decline name. Mutation: drop `shuffle` from `KERNEL_LESS_FAMILY` (guard red).
