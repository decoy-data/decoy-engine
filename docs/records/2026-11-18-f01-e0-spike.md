# F01 E0: Postgres write spike results

Date: 2026-11-18. Branch `feat/f01-e0`, PR #667. Plan: `docs/plans/2026-11-17-f01-postgres-target.md` (revision 3), AT-E0 and slice E0. Test file: `tests/connectors/test_postgres_write_spike.py`, run by the `pg-gate` job (postgres:16 service, DuckDB 1.5.4, Python 3.10). All cells use raw DuckDB calls. A second DuckDB connection is the other application session.

## Verdict

The transaction design holds: cells a, b, c, d, f, g, h, i and j pass. Cell e fails. `interrupt()` on the DuckDB connection does not cancel a running `postgres_query` or `postgres_execute` statement, and does not stop a connect attempt. The plan's deadline design (section 4.4, "a timer interrupts DuckDB at `deadline_s`") needs another mechanism before E1 starts. Per the plan's rule, E1 does not start until the owner or planner decides.

## Cells

| Cell | Result | What was observed |
|---|---|---|
| a | pass | `postgres_execute(..., use_transaction := true)` DDL and `TRUNCATE`, plus an `INSERT ... SELECT FROM read_parquet`, stay invisible to a second session until `COMMIT`. `ROLLBACK` undoes all three. `COMMIT` makes all three visible together. |
| b | pass | Closing the connection mid-transaction ends the backend and releases its locks. |
| c | pass (recorded) | A DuckDB-side `SELECT count(*)` of a truncated table inside the transaction returns at once with the in-transaction state (0 rows). No hang, no stale read. |
| d | pass (recorded) | Without `pg_clear_cache()` the attached catalog stays stale after an outside `ALTER TABLE` (`stale_before_clear=True`). After `CALL pg_clear_cache()` the new column shows. The publisher must clear the cache after its own DDL. |
| e | FAIL | See below. |
| e2 | pass | Fallback: `pg_cancel_backend(<pid>)` from a second session stops a running `postgres_execute` inside the transaction. The client call returns with an error, the server statement is gone, and `ROLLBACK` works. The publisher already records `pg_backend_pid()` at step 1. |
| f | pass | `INSERT` with a column list works for a stored generated column (left out), an identity switched to `BY DEFAULT`, and enum, jsonb, uuid and array columns, given as plain Parquet strings and lists. |
| g | pass | `INSERT` returns the affected-row count. |
| h | pass | `connect_timeout=2` in the DSN and the `PGCONNECT_TIMEOUT=2` environment variable both stop a connect to a blackhole address (192.0.2.1) after 2.0 s with `IOException`. The wall-clock `interrupt()` does not: the attach was still blocked after 12 s and its child process was killed. The session helper can set the environment variable without editing the DSN text. |
| i | pass | A `DO` block running `ALTER SEQUENCE ... RESTART` is undone by `ROLLBACK` and kept by `COMMIT`. |
| j | pass | `pg_current_xact_id()` and `pg_backend_pid()` read inside the transaction equal `backend_xid` and `pid` in a second session's `pg_stat_activity`, and the state is `idle in transaction`. |

## Cell e detail

Four statements were interrupted one second after they reached the server: `postgres_query` of `pg_sleep(30)`, `postgres_execute` of the same, the same inside a transaction, and a `TRUNCATE` waiting on a lock held by another connection. In all four the client call did not return after `conn.interrupt()` (10 s wait) and the server statement was still active 5 s later. The plan's AT-E0 cell e and AT-E9 deadline test assume the opposite.

Options for the planner (not decided here):
- Cancel with `pg_cancel_backend(pid)` from a watchdog session at the deadline (cell e2 shows it works), plus a `statement_timeout` and `lock_timeout` set with `SET LOCAL` as the plan already does.
- Set the connect bound with `PGCONNECT_TIMEOUT` (cell h) instead of the timer.
