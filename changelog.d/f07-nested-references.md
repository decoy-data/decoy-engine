### Added (references for nested JSON paths, F07 82-E4a, 2026-11-18)

A rule of a `nested` column can set `references: {table, column}` to mask its leaf under the identity of a parent column. The leaf then gets the same masked value as the parent key, so a join on the masked values still matches. The rule needs a singular path of names (`$.customer_id`, `$.ref.customer_id`). The parent column must use `hash` or `tokenize` with the same strategy, config and namespace as the rule, and must not have a `when` condition. `compile_plan` reads the parent's profiled type and fixes the leaf kind: a JSON integer for an integer parent, a JSON string for a string parent. A leaf of another kind (`"42"` for an integer parent, an object, an array) fails the row, so `42` and `"42"` never hash to different tokens. `compile_plan(no_profile=True)` refuses a reference. The path relation is not an FK relationship: no FK route, subset or orphan remap sees it. Counting its orphans is part of a later slice.

New reason codes: `plan/nested_reference_path_not_singular`, `plan/nested_reference_parent_unknown`, `plan/nested_reference_strategy_not_join_safe`, `plan/nested_reference_strategy_mismatch`, `plan/nested_reference_namespace_mismatch`, `plan/nested_reference_parent_conditional`, `plan/nested_reference_key_kind_reserved`, `plan/nested_reference_parent_type_unsupported`, `plan/nested_reference_requires_profile`, `runtime/nested_reference_key_kind_unbound` and `warning/nested_reference_leaf_type_mismatch`.
